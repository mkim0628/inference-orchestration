## Activity A 아이디어

### 아이디어 A-1: DualPathStorageNICAwareKVLoadBalancer (DualPath 스토리지 NIC 유휴율 인식 KV 로드 밸런서)
- **가설**: DualPath(2602.21548)의 핵심 통찰 — 에이전틱 고히트율 환경에서 "저장소→프리필 노드" 단일 경로가 스토리지 NIC 포화를 유발하고 decode 노드의 스토리지 NIC는 유휴 상태로 낭비된다 — 를, P/D 분리 클러스터의 KV 로드 라우팅 정책에 적용하면, 스토리지 NIC 부하를 노드별로 실시간 모니터링하고 포화 노드의 KV 로드 요청을 idle NIC를 보유한 decode 노드를 경유하는 이중 경로로 우회시키는 "NIC-부하 인식 KV 이중 경로 라우터"를 구성할 수 있으며, 단일 경로 정책 대비 스토리지 I/O 병목을 최대 1.96× 제거해 처리량을 향상시킬 수 있다. 이전 모든 A 기법(KVRMCoalescingSegmentScheduler, NAtHDDROffloadingScheduler, HMAMultiConnectorScheduler, AMPDLazySegmentFetchScheduler, PrefillShareFanoutRouter, KVDriveAttentionPipelineScheduler, CONCURCongestionBasedAgentAdmissionScheduler, KVServeBayesianScheduler, PPDAppendFullPrefillClassifier, DualMapDualHashRouter, CPDWarmColdHitRateRouter, KaretoStorageTuner 등)은 스토리지 NIC 부하를 스케줄링 신호로 사용하지 않았으며, decode 노드의 유휴 NIC를 KV 전달 중계 경로로 활용하는 "이중 경로 라우팅" 메커니즘이 없었다.
- **접근 방법**:
  1. `DualPathNICLoadBalancer` 클래스 (`src/scheduler/dualpath_nic_load_balancer.py`): `BaseScheduler` 상속
  2. **스토리지 NIC 부하 모니터 (Storage NIC Load Monitor)**:
     - 각 노드(prefill 노드 + decode 노드)의 스토리지 NIC 대역폭 사용률(`nic_utilization_ratio = nic_bytes_in_use / nic_max_bandwidth`)을 주기적으로 수집.
     - 수집 주기: `nic_monitor_interval_ms`(기본 200ms) YAML 외부화. gRPC 경량 heartbeat 메시지로 클러스터 전체 NIC 상태를 마스터 스케줄러에 집계.
     - 포화 임계값: `nic_saturation_threshold`(기본 0.80) — 스토리지 NIC 사용률 ≥ 80%이면 "포화(saturated)" 상태.
     - 유휴 decode 노드 목록 유지: `idle_decode_nodes = [n for n in decode_nodes if nic_utilization(n) < idle_threshold(기본 0.30)]`.
  3. **KV 로드 경로 결정 로직 (Dual-Path Routing Decision)**:
     - **경로 1 (표준 단일 경로, 기본)**: 스토리지 NIC 포화 없음(`prefill_nic_utilization < nic_saturation_threshold`) → 기존 "저장소→프리필 노드" 직접 경로 유지.
     - **경로 2 (이중 경로 우회)**: 스토리지 NIC 포화 감지 AND `len(idle_decode_nodes) > 0` → 해당 KV 로드 요청을 이중 경로로 라우팅:
       - **경로 2a**: `저장소 → decode 노드(idle NIC) → prefill 노드 (RDMA)`. decode 노드가 스토리지에서 KV를 로드한 후 RDMA를 통해 prefill 노드로 전달.
       - 이중 경로 전달 RDMA는 모델 실행 통신과 네트워크 채널을 공유하지 않아 간섭 없음 (DualPath 원논문 설계 원칙 상속).
     - **경로 결정 오버헤드**: NIC 부하 상태 조회 O(1) + idle decode 노드 목록 탐색 O(N_decode) → < 0.1ms/요청.
  4. **글로벌 부하 균형 (Global Load Balancer)**:
     - 이중 경로 선택 시 여러 idle decode 노드 중 `nic_utilization`이 가장 낮은 노드를 중계 decode 노드로 선택 (`min_load_first` 정책).
     - 동시에 이중 경로를 사용하는 KV 로드 요청 수(`active_dual_path_count`)를 추적해 단일 decode 노드에 이중 경로 요청이 집중되지 않도록 라운드-로빈 분산.
     - `max_dual_path_per_node`(기본 4): decode 노드당 동시 이중 경로 KV 로드 수 상한.
  5. **이전 A 기법과의 차별점**:
     - PPDAppendFullPrefillClassifier(05-22): append/full 프리필 유형 분류로 KV 전송 자체를 우회 (유형 분류 기반, 전송 경로 변경 없음).
     - AMPDLazySegmentFetchScheduler(05-18): 세그먼트 확정 전 KV 전송 보류 (타이밍 제어, 경로 결정 없음).
     - KVServeBayesianScheduler(05-21): 압축 전략 공간 Bayesian 탐색 (전략 선택 메타-최적화, 전송 경로 무관).
     - DualPathNICLoadBalancer: **스토리지 NIC 부하를 실시간 모니터링해 포화 시 decode 노드 유휴 NIC를 중계 경로로 전환** — 네트워크 토폴로지 인식 KV 전달 경로 이중화가 이전 어느 A 기법에도 없었다.
  6. **TriAttention(C-1)과의 통합 경로**: 이중 경로로 전달되는 KV를 decode 노드에서 TriAttention 삼각함수 KV 선택으로 사전 필터링 후 prefill 노드로 전달하면, "중계 decode 노드의 유휴 GPU 자원(컴퓨팅)을 KV 압축에 활용"하는 추가 시너지가 가능 (Cross-1 참조).
- **대상 환경**: 멀티 노드 (P/D 분리 환경 필수)
- **멀티 노드 고려사항**: decode 노드와 prefill 노드 간 RDMA 대역폭(InfiniBand/NVLink)을 KV 이중 경로 전달에 활용. 스토리지 NIC(스토리지 네트워크)와 컴퓨트 NIC(모델 실행 RDMA)가 물리적으로 분리된 환경 가정(DualPath 원논문 DeepSeek V3.2 운영 환경 동일). 컴퓨트 네트워크와 스토리지 네트워크를 분리 운용해 이중 경로 KV 전달이 모델 실행 통신과 간섭하지 않도록 설계. `nic_type: ["storage_nic", "compute_nic"]` 노드별 NIC 타입 설정 YAML 외부화.
- **예상 효과**: 처리량 +40~96% (DualPath 원논문 오프라인 1.87× + 온라인 1.96× 기반, NIC 포화 환경에서 병목 해소), KV 스토리지 I/O 대역폭 활용률 +80~100% (유휴 decode NIC 가용 대역폭 추가 활용), Scheduling overhead TTFT +2% 이내 (NIC 부하 조회: O(1) + 이중 경로 결정: < 0.1ms)
- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 A-2: SideQuestModelDrivenTokenUtilityAdmissionController (SideQuest 모델-주도 토큰 효용 평가 기반 에이전틱 어드미션 컨트롤러)
- **가설**: SideQuest(2602.22603)의 핵심 패러다임 — 추론 모델 자체를 KV 관리 에이전트로 활용해 보조 태스크 프레이밍으로 토큰 효용성을 평가하고 피크 토큰을 65% 절감 — 을, Activity A의 에이전틱 스케줄링에서 "스케줄러가 요청 배치 결정을 내리기 전에 현재 컨텍스트의 토큰 효용 분포를 모델-주도로 평가해 새 요청의 KV 수요를 사전 추정"하는 "모델-주도 KV 수요 예측 어드미션 컨트롤러"로 구현하면, CONCUR의 반응적 혼잡 제어(사후 퇴거 방지)와 PBKV의 확률적 예측을 넘어 "추론 모델의 실제 컨텍스트 이해를 기반으로 한 결정론적 토큰 필요성 평가"가 가능해져, 에이전틱 워크로드에서 KV 풀 혼잡 사전 방지와 처리량 최적화를 동시에 달성할 수 있다. 이전 모든 A 기법 중 "추론 모델 보조 태스크로 토큰 효용 평가 결과를 어드미션 결정에 사용"하는 기법은 없었다 — CONCURCongestionBasedAgentAdmissionScheduler(05-20)는 KV 풀 점유율 기반 반응적 제어, ThunderAgentProgramScheduler(05-19)는 정적 Program 분석 기반 쓰래싱 방지로 근본 원리가 다르다.
- **접근 방법**:
  1. `SideQuestTokenUtilityAdmissionController` 클래스 (`src/scheduler/sidequest_token_utility_admission.py`): `BaseScheduler` 상속
  2. **보조 태스크 기반 토큰 효용 평가기 (Auxiliary-Task Token Utility Evaluator)**:
     - 새 에이전틱 요청 수신 시, 요청 컨텍스트를 SideQuest 스타일 "보조 태스크" 프레이밍으로 래핑해 추론 모델에 전달.
     - 보조 태스크 프롬프트 템플릿: `"[Auxiliary] Evaluate token utility for the following context. Identify which segments are critical for the next N steps. Context: {context}. Response: [utility_scores]"`.
     - 출력: 컨텍스트 세그먼트별 효용 점수 벡터 `utility_scores[seg_i] ∈ [0, 1]`. 점수 임계값 `low_utility_threshold`(기본 0.2) 이하 세그먼트는 "제거 가능(evictable)"으로 분류.
     - SideQuest 원논문: 215개 샘플로 충분히 훈련 가능 → 보조 태스크 파인튜닝된 "경량 평가 모델"(`utility_model_path` YAML 외부화)을 별도 GPU 슬롯에서 실행 (메인 추론과 분리).
     - 평가 오버헤드: 경량 평가 모델(< 7B) 보조 추론 → < 50ms/요청 (메인 추론과 비동기 병렬 실행).
  3. **토큰 효용 기반 KV 수요 사전 추정 (Pre-Admission KV Demand Estimation)**:
     - 평가 결과에서 "고효용(high-utility) 세그먼트 토큰 수"를 추정: `estimated_kv_demand = Σ_{utility_scores[i] ≥ high_utility_threshold} token_count(seg_i)`.
     - 현재 KV 풀 여유(`kv_pool_free_capacity`)와 비교:
       - `estimated_kv_demand ≤ kv_pool_free_capacity × admission_safety_ratio`(기본 0.85): 요청 즉시 어드미션.
       - `estimated_kv_demand > kv_pool_free_capacity × admission_safety_ratio`: 요청을 대기 큐에 배치 + 저효용 세그먼트 우선 퇴거 요청.
  4. **저효용 세그먼트 선제 퇴거 (Pre-Eviction of Low-Utility Segments)**:
     - 어드미션 거부 시 현재 KV 풀의 저효용 세그먼트(`utility_scores < low_utility_threshold`)를 선제적으로 퇴거해 공간 확보.
     - `CLCPositionalBiasGatedSegmentCache(05-23 B-1)` 연동: 위치 편향 큰 세그먼트(재인코딩 비용 큰 것)를 우선 퇴거.
     - 퇴거 후 `estimated_kv_demand ≤ kv_pool_free_capacity × admission_safety_ratio` 조건 재확인 → 충족 시 요청 어드미션.
  5. **비동기 평가 + 스케줄러 통합**:
     - 보조 태스크 평가를 메인 배치 사이클과 비동기 실행: `asyncio.create_task(evaluate_token_utility(request))`.
     - 평가 완료 이벤트 수신 시 스케줄러 배치 큐를 갱신. 평가 미완료 요청은 기존 CONCUR 혼잡 제어 정책(fallback)으로 처리.
     - 평가 신뢰도 추적: 실제 KV 사용량 vs. 예측 `estimated_kv_demand` 오차를 EMA로 추적해 `admission_safety_ratio` 자동 보정.
  6. **이전 A 기법과의 차별점**:
     - CONCURCongestionBasedAgentAdmissionScheduler(05-20): KV 풀 점유율 임계값 기반 반응적 어드미션 제어 (현재 혼잡 상태에 반응).
     - ThunderAgentProgramScheduler(05-19): 정적 Program 분석으로 워크플로우 구조에서 KV 수요를 결정론적 추출.
     - PBKVConcurPredictiveReactiveDualLayerScheduler(05-20): 확률적 MLP 예측기 기반 선제 보존.
     - SideQuestTokenUtilityAdmissionController: **추론 모델 자체가 보조 태스크로 컨텍스트의 토큰 효용성을 동적으로 평가 → 결과를 어드미션 결정에 사용** — 모델-주도 효용 평가를 스케줄러 신호로 사용하는 것이 이전 어느 A 기법에도 없었다.
- **대상 환경**: 단일 노드 / 멀티 노드 양쪽
- **멀티 노드 고려사항**: 경량 평가 모델을 별도 "유틸리티 평가 노드"로 분리해 메인 추론 노드 부하 영향 제거. 멀티 노드에서 마스터 스케줄러가 클러스터 전체 KV 풀 상태를 집계해 `kv_pool_free_capacity` 계산. 평가 결과(utility_scores)를 마스터 스케줄러에서 중앙 관리해 노드 간 어드미션 결정의 일관성 보장.

### 아이디어 B-1: DualPathSegmentStorageNICRoutedNonContiguousCache (DualPath 이중 경로 통합 비연속 세그먼트 분산 스토리지 캐시)
- **가설**: DualPath(2602.21548)의 "저장소→decode→prefill RDMA" 이중 경로를 Activity B의 비연속 세그먼트 캐시에 적용하면, 분산 스토리지에 저장된 비연속 세그먼트를 prefill 노드의 스토리지 NIC 포화 없이 decode 노드의 유휴 NIC를 경유해 효율적으로 전달하는 "이중 경로 비연속 세그먼트 로드 캐시"가 가능하다. 기존 B 기법들(AMPDAdapShotLazyLoadPipeline 05-18, BlockUnionNonContiguousReuseIndex 05-21, CLCPositionalBiasGatedSegmentReuse 05-23 등)은 모두 비연속 세그먼트가 이미 메모리에 있거나 단일 경로로 로드된다고 가정했으며, "스토리지 NIC 이중 경로를 통한 비연속 세그먼트 분산 로드"라는 데이터 흐름 설계는 없었다.
- **접근 방법**:
  1. `DualPathNonContiguousSegmentCache` 클래스 (`src/cache/dualpath_noncontiguous_segment_cache.py`): `CacheStore` 인터페이스 상속
  2. **비연속 세그먼트 스토리지 위치 레지스트리**:
     - 각 세그먼트의 저장 위치(스토리지 노드 ID + 파일 경로 + 오프셋)를 `SegmentStorageRegistry`에 등록: `Dict[segment_hash → StorageLocation(node_id, path, offset, size_bytes)]`.
     - 로드 경로 결정: `DualPathNICLoadBalancer(A-1)`의 NIC 부하 상태를 기반으로 단일 경로(저장소→prefill) vs. 이중 경로(저장소→decode→prefill) 중 선택.
  3. **이중 경로 세그먼트 로드 파이프라인 (Dual-Path Segment Load Pipeline)**:
     - **단일 경로 (NIC 여유 시)**: `storage → prefill_node` 직접 전송. `AMPDAdapShotLazyLoadPipeline(05-18 B-1)`의 pull-on-demand + AdapShot RoPE 재인코딩 파이프라인 연동.
     - **이중 경로 (prefill NIC 포화 시)**:
       - **Step 1 (Storage → decode NIC)**: decode 노드의 스토리지 NIC로 세그먼트 KV를 로드 (`async_storage_read(segment_id, decode_node_id)`).
       - **Step 2 (decode → prefill, RDMA)**: decode 노드에서 prefill 노드로 RDMA 전달 (`rdma_send(kv_data, prefill_node_id, target_slot)`).
       - 두 단계는 비동기 파이프라인: Step 1 완료 즉시 Step 2 시작 (decode 노드 버퍼 최소화).
     - 이중 경로 vs. 단일 경로 비교 지표: `{single_path_latency_ms, dual_path_latency_ms, nic_utilization_delta}` 기록.
  4. **세그먼트 분할 병렬 로드 (Parallel Segment Shard Loading)**:
     - 대형 세그먼트(> `large_segment_threshold`, 기본 128K 토큰)를 N개 샤드로 분할해 N개 decode 노드를 병렬 중계 경로로 활용.
     - 각 decode 노드가 세그먼트의 서로 다른 레이어 범위를 로드 + RDMA 전달 → 총 전달 시간 ≈ 단일 노드 전달의 1/N.
     - 샤드 결합: prefill 노드에서 N개 RDMA 수신 완료 후 레이어 순서로 재조합 (`torch.cat` 레이어 차원).
  5. **AdapShot RoPE 재인코딩 통합**:
     - 이중 경로 세그먼트가 prefill 노드에 도착 후 `CLCPositionalBiasGatedSegmentReuse(05-23 B-1)`의 위치 편향 게이트 적용 → 재인코딩 필요성 판단 → AdapShot 재인코딩 또는 직접 재사용.
  6. **이전 B 기법과의 차별점**:
     - AMPDAdapShotLazyLoadPipeline(05-18 B-1): 세그먼트 확정 후 단일 경로 지연 로드 + AdapShot 재인코딩 오버랩 (단일 경로, 타이밍 최적화).
     - BlockUnionNonContiguousReuseIndex(05-21 B-1): GQA-aware 블록 테이블 변환으로 memcpy 제거 (이미 HBM에 있는 세그먼트 처리 최적화).
     - CLCPositionalBiasGatedSegmentReuse(05-23 B-1): 위치 편향 크기 측정 기반 선택적 재인코딩 3단계 게이트 (재인코딩 오버헤드 최적화).
     - DualPathNonContiguousSegmentCache: **분산 스토리지에서 비연속 세그먼트를 로드할 때 decode 노드의 유휴 스토리지 NIC를 중계 경로로 활용하는 이중 경로 로드** — 세그먼트 로드의 네트워크 경로 자체를 이중화하는 것은 이전 어느 B 기법에도 없었다.
- **예상 효과**: 비연속 히트율 +15~30% (스토리지 NIC 포화로 인한 세그먼트 로드 타임아웃/실패 방지), 세그먼트 로드 대기 시간 −40~60% (이중 경로 병렬 활용), TTFT −20~35% (이중 경로 + 병렬 샤드 로드로 로드 병목 해소)

### 아이디어 C-1: TriAttentionPreRoPEConcentrationKVSelectorCodec (TriAttention pre-RoPE Q/K 집중도 삼각함수 KV 선택 코덱)
- **가설**: TriAttention(2604.04921)의 핵심 발견 — "pre-RoPE 공간에서 Q·K 벡터가 고정 비제로 중심 주변에 고도로 집중(concentration)되어 위치에 무관하게 안정적이며, 이 집중도가 삼각함수 급수로 결정되는 위치-거리 선호도를 형성한다" — 을 `src/cache/` 레이어에 구현하면, pre-RoPE Q 중심과 삼각함수 급수로 키 중요도를 계산하고 Q/K 집중도 메트릭으로 두 신호를 자동 균형 조정하는 training-free KV 선택 코덱을 구성할 수 있으며, AIME25 기준 풀-어텐션 동등 정확도(40.8%)를 유지하면서 최대 10.7× KV 메모리 절감을 달성할 수 있다. 이전 모든 C 기법 중 pre-RoPE 공간의 Q/K 벡터 집중도를 삼각함수 급수로 수학적으로 정형화해 키 중요도를 계산하는 방법은 없었다 — DapQPositionAwareEvictionCodec(05-22 C-3)가 "위치-인식 유사 쿼리(post-RoPE 회전)"를 사용했다면, 이 기법은 "pre-RoPE 공간의 Q/K 집중도"라는 완전히 다른 신호 공간을 활용한다.
- **접근 방법**:
  1. `TriAttentionPreRoPEKVSelectorCodec` 클래스 (`src/cache/triattention_pre_rope_kv_selector_codec.py`): `CompressionCodec` 인터페이스 구현
  2. **pre-RoPE Q/K 집중도 측정 (Q/K Concentration Metric)**:
     - pre-RoPE 쿼리 벡터 집합 `{q_1, ..., q_T}` (RoPE 적용 이전)에서 평균 중심 벡터 `μ_Q = (1/T) Σ_t q_t` 계산.
     - Q 집중도: `conc_Q = ||μ_Q||_2 / (1/T) Σ_t ||q_t||_2` — 중심이 비제로이고 벡터들이 중심 주변에 집중된 정도.
     - K 집중도: 동일 방식으로 `conc_K = ||μ_K||_2 / (1/N) Σ_i ||k_i||_2`.
     - 집중도가 높을수록(conc_Q, conc_K → 1) Q/K 중심 기반 거리 선호도가 신뢰할 수 있음.
     - 오버헤드: 평균 벡터 계산 O(T × d_k) — 프리필 단계 1회 계산 후 캐싱 → 디코딩 단계 재사용.
  3. **삼각함수 급수 기반 거리 선호도 점수 (Trigonometric Series Distance Preference Score)**:
     - TriAttention의 수학적 핵심: pre-RoPE Q 중심 `μ_Q`가 RoPE 주파수 집합 `{θ_d}_{d=1}^{d_k/2}`와 상호작용해 키의 "선호 거리(preferred distance)"를 삼각함수 급수로 결정.
     - 키 `k_i` (위치 `pos_i`)에 대한 거리 선호도 점수:
       ```
       dist_pref(k_i) = Σ_{d=1}^{d_k/2} [|μ_Q[2d-1]| × cos(θ_d × |pos_i - pos_q|) +
                                            |μ_Q[2d]|   × sin(θ_d × |pos_i - pos_q|)]
       ```
       - `pos_q`: 현재 디코딩 위치, `θ_d = base^{-2d/d_k}` (RoPE 주파수, base=10000).
     - Q/K 노름 보조 신호: `norm_score(k_i) = ||k_i||_2 / max_j ||k_j||_2`.
     - **집중도 가중 결합 점수**:
       ```
       importance(k_i) = conc_Q × dist_pref(k_i) + (1 - conc_Q) × norm_score(k_i)
       ```
       집중도가 높으면 삼각함수 거리 선호도 우선, 낮으면 Q/K 노름 기반 점수로 fallback.
     - 계산 오버헤드: 키당 `d_k/2` 삼각함수 계산 → GPU 병렬화로 O(N × d_k) → < 1ms/디코딩 스텝 (N=128K, d_k=128 기준 Triton 커널 가속).
  4. **KV 선택 및 캐시 저장**:
     - 상위 `kv_budget_ratio`(기본 0.10 = 상위 10%) importance 점수 키만 유지, 나머지 퇴거.
     - 추론(reasoning) 워크로드 감지: `is_reasoning_task`(`<think>` 태그 포함 여부) 시 `kv_budget_ratio = 0.093` (TriAttention 원논문 AIME25 10.7× 절감 기준). 비추론 태스크: `kv_budget_ratio = 0.20` (보수적 설정).
     - 동적 예산 조정: KV 풀 점유율 > `high_pressure_threshold`(기본 0.80) 시 `kv_budget_ratio` 10% 추가 감소.
     - `configs/triattention_budget_policy.yaml` 외부화.
  5. **NAtH DDR 오프로딩(05-16 A-2)과의 통합**:
     - TriAttention으로 선택되지 않은 KV를 즉시 퇴거하는 대신 DDR로 오프로딩(NAtH 제로 근사 오류 오프로딩 원칙) → 필요 시 복원 가능.
     - 오프로딩 조건: `importance(k_i) < eviction_threshold AND cumul_attn(k_i) > 0` → DDR 오프로딩 (추후 복원 가능). `cumul_attn(k_i) ≈ 0` → 영구 퇴거.
  6. **이전 C 기법과의 차별점**:
     - DapQPositionAwareEvictionCodec(05-22 C-3): post-RoPE 공간에서 위치-인식 유사 쿼리 내적으로 중요도 추정 (RoPE 적용 후 쿼리 회전 기반).
     - RuntimeCertifiedQuantizedAttentionCodec(05-23 C-1): INT8/INT4 양자화 + 런타임 오류 경계 수학적 인증 (양자화 정밀도 제어, 선택/퇴거 아님).
     - TriAttentionPreRoPEKVSelectorCodec: **pre-RoPE Q 중심의 삼각함수 급수로 키의 위치-거리 선호도 수학적 계산 + Q/K 집중도 메트릭으로 두 신호 자동 균형** — pre-RoPE 공간 활용 + 삼각함수 정형화가 이전 어느 C 기법과도 다른 중요도 계산 기반이다.
- **예상 효과**: 메모리 −89~91% (10.7× KV 절감, 추론 태스크 기준, TriAttention 원논문), accuracy delta ±0.0% (AIME25 풀-어텐션 40.8% 동등, 원논문), 처리량 +150% (2.5× 처리량, 원논문), non-reasoning 태스크 메모리 −60~70% (kv_budget_ratio=0.30 보수적 설정)
- **accuracy-preserving 근거**:
  (1) TriAttention 원논문(2604.04921)에서 AIME25 32K 토큰 생성에서 풀-어텐션과 동등한 정확도(40.8%)를 달성하면서 10.7× KV 메모리 절감을 실험적으로 검증. pre-RoPE Q/K 집중도 기반 중요도 계산이 의미론적으로 중요한 키를 정확히 선택함이 입증됨.
  (2) 집중도 가중 결합 점수: 집중도가 낮은 경우(불안정한 삼각함수 근사) 자동으로 Q/K 노름 기반 보수적 점수로 fallback → 추론 불안정 환경에서 정확도 저하 방지.
  (3) DDR 오프로딩 통합(NAtH 원칙): 선택 안 된 KV를 즉시 퇴거하지 않고 DDR 오프로딩 → 어텐션 연산 시 필요 시 복원 가능 → "zero-approximation-error" 오프로딩으로 accuracy delta 추가 보호.
  (4) non-reasoning 태스크에서 `kv_budget_ratio=0.20` 보수적 설정: 20% 유지로 Activity C 목표 ±1% 이내 달성을 보수적으로 보장.
  검증: WikiText-2 perplexity ±1% + AIME25(추론 태스크, kv_budget_ratio=0.093) + LongBench 8개 서브태스크 + 예산 비율(5%/9.3%/15%/20%/30%) 별 정확도 곡선 + pre-RoPE vs. post-RoPE 중요도 신호 대조 실험 + 집중도 메트릭(conc_Q, conc_K) 분포 측정.
- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 C-2: AttentionMatchingClosedFormLatentKVCompactionCodec (Attention Matching 닫힌 형태 최소제곱 잠재 공간 KV 압착 코덱)
- **가설**: Attention Matching(2602.16284)의 핵심 아이디어 — 레퍼런스 쿼리 집합에 대해 어텐션 출력과 어텐션 매스를 보존하는 소규모 콤팩트 K·V 쌍을 잠재 공간에서 직접 최적화하며, 일부 서브 문제에 닫힌 형태 최소제곱 해가 존재해 반복 최적화 없이 수백 배 빠른 속도로 Cartridges 수준 압축 품질을 달성 — 을 `src/cache/` 레이어에 구현하면, 기존 KVSculpt 증류 코덱(05-23 C-2, L-BFGS 반복 최적화 기반)과 달리 닫힌 형태 최소제곱 해로 50× 압축을 수 초 내 달성할 수 있으며, 비연속 세그먼트 캐시(Activity B)에 적용 시 동일 메모리 예산에서 유지 가능한 세그먼트 수를 대폭 확장할 수 있다. KVSculptDistillationCodec(05-23 C-2)가 L-BFGS 반복 최적화 + 레이어별 KL 발산 난이도 프로파일을 핵심 메커니즘으로 사용한다면, 이 기법은 어텐션 출력/매스 보존 목표 함수 + 닫힌 형태 최소제곱 해라는 근본적으로 다른 최적화 경로를 취한다.
- **접근 방법**:
  1. `AttentionMatchingClosedFormCodec` 클래스 (`src/cache/attention_matching_closed_form_codec.py`): `CompressionCodec` 인터페이스 구현
  2. **레퍼런스 쿼리 집합 구성 (Reference Query Construction)**:
     - 압축 대상 컨텍스트에서 레퍼런스 쿼리 집합 `Q_ref ∈ R^{m × d_k}` 구성. m = 레퍼런스 쿼리 수 (기본 m=32 쿼리).
     - 구성 방법: 컨텍스트의 균등 샘플링 쿼리(위치 간격 `context_len / m`) + 어텐션 가중치 상위 쿼리(최대 중요도) 혼합.
     - `configs/attention_matching_ref_query_config.yaml` 외부화.
  3. **목표 함수 1 — 어텐션 출력 매칭 (Attention Output Matching)**:
     - 레퍼런스 쿼리 `Q_ref`에 대해 원본 KV `(K_orig, V_orig)`와 압착 KV `(K_c, V_c)` 간 어텐션 출력 차이 최소화:
       ```
       min_{K_c, V_c} ||softmax(Q_ref K_orig^T / √d) V_orig - softmax(Q_ref K_c^T / √d) V_c||_F
       ```
     - 압착 KV 크기: `m_c` 토큰 (m_c << N, 기본 m_c = N / compression_ratio).
  4. **목표 함수 2 — 어텐션 매스 매칭 (Attention Mass Matching)**:
     - 어텐션 가중치 분포(소프트맥스 출력) 보존:
       ```
       min_{K_c} ||softmax(Q_ref K_orig^T / √d) - softmax(Q_ref K_c^T / √d)||_F
       ```
     - **닫힌 형태 해 (Closed-Form Solution)**:
       - 어텐션 매스 매칭은 `softmax(Q_ref K_c^T / √d) = A_orig`를 만족하는 `K_c`를 찾는 문제.
       - 로그-소프트맥스 역변환: `K_c = argmin ||Q_ref K_c^T / √d - log(A_orig)||_F` → **최소제곱 문제**.
       - 닫힌 형태: `K_c = d^{1/2} × Q_ref^† × log(A_orig)` (의사역행렬 사용). `Q_ref^† = (Q_ref^T Q_ref)^{-1} Q_ref^T`.
       - 계산 오버헤드: `(Q_ref^T Q_ref)^{-1}` 역행렬 = O(m^3) = O(32^3) = 32768 연산 → < 0.1ms.
  5. **Value 최적화 (Value Optimization)**:
     - `K_c` 고정 후 Value 최적화: `min_{V_c} ||A_orig V_orig - A_c V_c||_F`. `A_c = softmax(Q_ref K_c^T / √d)`.
     - 닫힌 형태 최소제곱 해: `V_c = A_c^† A_orig V_orig`. 오버헤드: `A_c^†` 의사역행렬 = O(m_c^3) → < 1ms (m_c = 100 기준).
  6. **두 목표 함수 교대 최적화 (Alternating Optimization)**:
     - Attention Mass Matching(K_c 업데이트) → Attention Output Matching(V_c 업데이트) → 반복 (기본 3회).
     - Cartridges 대비 2 오더(100×) 빠른 이유: 닫힌 형태 해 + 의사역행렬 계산이 반복 경사 하강보다 압도적으로 빠름.
  7. **비연속 세그먼트 캐시와의 통합 (B+C 시너지)**:
     - `DualPathNonContiguousSegmentCache(B-1)` 또는 `SessionAwareTurnLevelSegmentCache(05-22 B-1)`의 각 세그먼트에 Attention Matching 압축 적용.
     - 압착된 세그먼트(m_c 토큰) 저장 + 재사용 시 레퍼런스 쿼리 `Q_current`로 어텐션 출력 복원.
     - 동일 메모리에서 유지 가능한 세그먼트 수: `compression_ratio`에 비례 증가 (50× 압축 시 50배 더 많은 세그먼트 캐싱 가능).
  8. **이전 C 기법과의 차별점**:
     - KVSculptDistillationCodec(05-23 C-2): L-BFGS 5-10회 반복 Key 최적화 + 최소제곱 Value 최적화 교대 → KL 발산 최소화 목적 함수 (반복 최적화, Key에 L-BFGS 사용).
     - CompactAttentionBlockUnionCodec(05-21 C-1): 청크드 프리필 블록-스파스 마스크 → GQA-aware 블록 테이블 변환 (블록 선택 방식, 잠재 공간 최적화 아님).
     - AttentionMatchingClosedFormCodec: **어텐션 출력/매스 보존 목표 함수 + 닫힌 형태 최소제곱 해 → 잠재 공간에서 m_c 토큰으로 K·V 직접 최적화** — 닫힌 형태 해가 반복 최적화 불필요라는 설계 원칙이 이전 어느 C 기법과도 다른 최적화 경로다.
- **예상 효과**: 메모리 −96~98% (50× 압축, Attention Matching 원논문 일부 데이터셋 기준), accuracy delta ±0.5% (Cartridges 수준 품질, 원논문), 압축 속도 1000×+ 향상 (Cartridges 대비, 닫힌 형태 해 기반)
- **accuracy-preserving 근거**:
  (1) Attention Matching 원논문(2602.16284)에서 어텐션 출력 매칭과 어텐션 매스 매칭이 레퍼런스 쿼리에 대해 원본 KV와 동등한 어텐션 출력을 보장함을 수학적으로 분석하고 실험적으로 검증. 50× 압축에서 Cartridges 수준 압축 품질을 달성함.
  (2) 어텐션 출력 보존 목표 함수(`||attn_output_orig - attn_output_compact||_F` 최소화)가 모델 출력에 직접 영향을 미치는 어텐션 출력 벡터를 직접 최소화 → 가장 직접적인 accuracy-preserving 보장.
  (3) 닫힌 형태 해가 존재하는 서브 문제의 경우 최소제곱 잔차가 이론적 최솟값(해당 파라미터화 범위 내 전역 최솟값)으로 수렴 → 반복 최적화 대비 최적성 보장.
  (4) `compression_ratio` 파라미터(기본 50×)를 10×/20×/50×로 조정해 accuracy delta vs. 압축률 트레이드오프 탐색 가능. 10× 설정에서 accuracy delta는 ±0.2% 이내(추정).
  검증: WikiText-2 perplexity ±1% + LongBench 8개 서브태스크 + NIAH(128K 컨텍스트) + 압축 비율(5×/10×/20×/50×) 별 정확도 곡선 + KVSculptDistillationCodec(05-23 C-2) 대비 동일 압축률에서 accuracy delta 비교 + 닫힌 형태 해 vs. 반복 최적화 수렴 속도 비교.
- **구현 난이도**: medium
- **우선순위**: 2

### 아이디어 C-3: CodeCompDomainStructurePriorHybridEvictionCodec (CodeComp 도메인 구조 프라이어 하이브리드 퇴거 코덱)
- **가설**: CodeComp(2604.10235)의 핵심 원칙 — Code Property Graph(CPG) 정적 분석 프라이어를 KV 퇴거 정책에 통합해 어텐션 점수만으로는 보존하기 어려운 구조적으로 핵심적인 토큰을 보호 — 을 코드 도메인을 넘어 일반화하면, 다양한 도메인의 구조적 프라이어(HTML DOM 트리, SQL 스키마 그래프, 수식 파싱 트리, 에이전틱 역할 분류 등)를 "도메인 구조 중요도(domain structural importance)"로 모듈화해 어텐션 점수와 하이브리드 결합하는 "플러그인 형태의 도메인-특화 KV 퇴거 코덱"을 구성할 수 있으며, 코드 에이전트뿐 아니라 HTML/SQL/수학 등 구조화된 컨텍스트를 처리하는 모든 에이전틱 태스크에서 accuracy-preserving KV 압축을 달성할 수 있다. 이전 C 기법 전체(SP-KV, GlobalRetentionGate, DapQPositionAware, SpecAttn, TriAxialKV 등)는 도메인-무관 어텐션 신호 기반이었으며, "도메인별 정적 분석 구조 프라이어를 퇴거 결정에 플러그인으로 통합"하는 방법은 없었다.
- **접근 방법**:
  1. `DomainStructurePriorHybridEvictionCodec` 클래스 (`src/cache/domain_structure_prior_hybrid_eviction_codec.py`): `CompressionCodec` 인터페이스 구현
  2. **도메인 구조 중요도 인터페이스 (Domain Structural Importance Interface)**:
     - 추상 플러그인 인터페이스: `DomainStructurePriorPlugin` — `compute_structural_importance(tokens: List[str], context_type: str) → List[float]`.
     - 각 플러그인이 토큰 목록을 입력받아 구조적 중요도 점수 `[0, 1]` 반환.
     - 플러그인 등록: `register_domain_plugin(domain_type: str, plugin: DomainStructurePriorPlugin)`.
  3. **구현된 도메인 플러그인들**:
     - **코드 플러그인 (Code CPG Plugin)**: CodeComp(2604.10235) 원칙 적용. Joern/Tree-sitter로 Code Property Graph(CPG) 추출. call_site, 분기 조건(`if/for/while`), 할당문(`=`, `+=`) 토큰에 높은 구조적 중요도 할당.
       ```
       struct_importance(token) = base_score + cpg_role_weight[cpg_role(token)]
       cpg_role_weight = {call_site: 0.8, branch: 0.9, assignment: 0.7, comment: 0.1, other: 0.3}
       ```
     - **HTML/DOM 플러그인 (HTML DOM Plugin)**: BeautifulSoup4 기반 DOM 파싱. 구조 토큰(`<tag>`, `</tag>`, `id=`, `class=`, `href=`, `src=`)에 높은 중요도. 내용 텍스트 토큰은 DOM 깊이에 반비례 중요도.
     - **SQL 플러그인 (SQL Schema Plugin)**: sqlparse 기반 SQL 파싱. `SELECT`, `FROM`, `WHERE`, `JOIN`, `ON`, `GROUP BY` 절 키워드 + 테이블명/컬럼명 토큰에 최고 중요도. `SELECT *`의 `*`는 중간, `ORDER BY` 절은 낮은 중요도.
     - **수식 플러그인 (Math Formula Plugin)**: sympy 기반 수식 파싱. 연산자 우선순위 기반 구조적 중요도: 분모(`/` 분모), 지수 베이스, 등호(`=`) 토큰 최고 중요도.
     - **에이전틱 역할 플러그인 (Agentic Role Plugin)**: `TriAxialKVMixedPrecisionCodec(05-23 C-3)`의 채팅 템플릿 파싱 결과(의미적 역할 태그)를 구조적 중요도로 변환: `reasoning` → 1.0, `tool_call` → 0.9, `observation` → 0.6, `system` → 0.8, `response` → 0.5.
  4. **하이브리드 퇴거 기준 (Hybrid Eviction Criterion)**:
     - 최종 퇴거 점수: `eviction_score(token) = α × attn_importance(token) + (1 - α) × struct_importance(token)`.
     - `α`(기본 0.6): 어텐션 신호 vs. 구조적 중요도 균형 파라미터. `configs/domain_structure_prior_config.yaml` 외부화.
     - 도메인 자동 감지: 토큰 어휘 분포 기반 도메인 감지기 → 코드/HTML/SQL/수식/에이전틱 자동 분류.
     - 도메인 감지 실패 시: `α = 1.0` (순수 어텐션 기반 퇴거, 기존 방식과 동일).
  5. **DapQPositionAwareEvictionCodec(05-22 C-3)와의 통합**:
     - 어텐션 중요도 `attn_importance(token)` 계산에 DapQ의 위치-인식 유사 쿼리 기반 점수 사용: `attn_importance = softmax(q_pseudo · K)[i]`.
     - 구조적 중요도와 위치-인식 어텐션 점수를 하이브리드 결합해 DapQ의 "위치 정보 > 의미 정보" 원칙을 구조적 중요도로 보완.
  6. **이전 C 기법과의 차별점**:
     - DapQPositionAwareEvictionCodec(05-22 C-3): 위치-인식 유사 쿼리 기반 순수 어텐션 점수 퇴거 (도메인-무관, 위치 신호 단독).
     - SpecAttnVerificationGuidedKVSparseCodec(05-20 C-1): 추측 디코딩 검증 로짓 기반 KV 희소화 (도메인-무관, 어텐션 사이드채널).
     - TriAxialKVMixedPrecisionCodec(05-23 C-3): 채팅 템플릿 역할 태그 기반 혼합 정밀도 양자화 (역할 분류 → 비트폭 할당, 퇴거가 아닌 양자화).
     - DomainStructurePriorHybridEvictionCodec: **도메인별 정적 분석 구조 프라이어를 플러그인으로 등록하고 어텐션 점수와 하이브리드 결합한 퇴거 기준** — 코드/HTML/SQL/수학 등 구조화된 컨텍스트의 도메인 지식을 퇴거 결정에 활용하는 최초의 C 기법.
- **예상 효과**: 메모리 −40~60% (하이브리드 퇴거 기준으로 불필요 토큰 퇴거, 도메인별 압축률 차이), accuracy delta ±0.4% (구조적 핵심 토큰 보호로 도메인-특화 태스크 정확도 향상, CodeComp 원논문 기반)
- **accuracy-preserving 근거**:
  (1) CodeComp 원논문(2604.10235)에서 Code Property Graph 구조 프라이어를 KV 퇴거에 통합했을 때 fault localization과 patch generation 정확도가 순수 어텐션 기반 퇴거 대비 향상됨을 실험적으로 검증. 구조적으로 핵심적인 토큰(call site, 분기, 할당)을 보존하면 모델의 코드 이해 능력이 유지됨.
  (2) 하이브리드 결합(`α × attn + (1-α) × struct`): α=0.6 기본값으로 어텐션 신호가 주도하되 구조 프라이어가 보완 → 어텐션 신호가 놓치는 구조적 토큰을 구조 프라이어가 보호.
  (3) 도메인 감지 실패 시 `α=1.0` fallback → 기존 DapQ 어텐션 기반 퇴거와 동일한 정확도 보장.
  (4) 플러그인 인터페이스로 도메인별 독립 검증 가능: 각 플러그인(코드/HTML/SQL/수학)에 대해 도메인-특화 벤치마크에서 accuracy delta를 독립적으로 측정.
  검증: WikiText-2 perplexity ±1% (도메인-무관 기반 성능) + 도메인별 특화 벤치마크: (1) 코드 — HumanEval/EvalPlus, (2) HTML — WebArena HTML 태스크, (3) SQL — Spider 벤치마크, (4) 수학 — MATH 벤치마크 + AIME25 부분집합 + 도메인 감지 정확도 측정 + α=0.0/0.3/0.6/1.0 별 accuracy delta 곡선.
- **구현 난이도**: medium
- **우선순위**: 3

### 아이디어 Cross-1: DualPathTriAttentionNICRoutedCompressedKVPipeline (A+C) — DualPath 이중 경로 + TriAttention 압축 KV 전달 파이프라인
- **조합 근거**: `DualPathNICLoadBalancer(A-1)`이 스토리지 NIC 포화 시 decode 노드 유휴 NIC를 KV 중계 경로로 전환하고, decode 노드가 KV를 수신하는 순간 `TriAttentionPreRoPEKVSelectorCodec(C-1)`으로 10.7× 압축을 적용한 후 prefill 노드로 RDMA 전달하면, "중계 decode 노드의 유휴 GPU 컴퓨팅을 KV 압축에 활용"하는 새로운 자원 활용 패턴이 성립한다. A-1의 "이중 경로 KV 전달"과 C-1의 "KV 크기 10.7× 축소"가 결합되어 prefill 노드로 전달되는 KV 데이터 크기가 이중 경로 대역폭 증가 효과에 더해 추가로 10.7× 감소하는 곱연산적 개선이 가능하다.
- **구체 설계**:
  1. `DualPathTriAttentionCompressPipeline` 모듈 (`src/engine/dualpath_triattention_pipeline.py`)
  2. **통합 처리 흐름**:
     - **Step 1 (NIC 부하 감지, A-1)**: `DualPathNICLoadBalancer`가 prefill 노드 스토리지 NIC 포화 감지 → 유휴 decode 노드 선택.
     - **Step 2 (스토리지 → decode 노드 KV 로드)**: decode 노드의 스토리지 NIC로 원본 KV 로드 (FP16 전체 토큰).
     - **Step 3 (TriAttention pre-RoPE 선택, C-1)**: decode 노드에서 `TriAttentionPreRoPEKVSelectorCodec.compress(kv_full)` 실행 → 상위 10% 중요도 키만 유지 (10.7× 압축).
     - **Step 4 (압축 KV → prefill 노드 RDMA)**: 압축된 KV(전체의 9.3%)를 decode→prefill RDMA로 전달. 전달 데이터 크기 = 원본의 9.3% → RDMA 대역폭 소비 대폭 감소.
     - **Step 5 (prefill 노드 어텐션 계산)**: 압축된 KV 수신 후 `BlockUnionNonContiguousReuseIndex(05-21 B-1)` 블록 테이블로 표준 어텐션 커널 투입.
  3. **decode 노드 GPU 유휴 자원 활용**:
     - TriAttention 압축 계산이 decode 노드의 현재 디코딩 연산 사이의 유휴 슬롯에서 실행 (CUDA Stream 병렬화).
     - 중계 decode 노드의 GPU 메모리: 임시 전체 KV 버퍼(Step 2) → 압축 후 즉시 해제 (decode 노드 HBM 점유 최소화).
  4. **처리량 복합 향상 정량화**:
     - DualPath(A-1) 단독: 스토리지 I/O 병목 해소로 처리량 +96% (1.96×).
     - TriAttention(C-1) 단독: KV 메모리 10.7× 절감으로 배치 크기 증가 + 처리량 +150% (2.5×).
     - A+C 결합: 스토리지 NIC 이중화 × KV 전송 크기 10.7× 감소 = RDMA 대역폭 효율 극대화. 예상 처리량 +200~350%.
- **예상 복합 효과**: 처리량 +200~350% (DualPath 이중 경로 + TriAttention 압축 KV 전달 결합), P→D KV 전송 크기 −89% (10.7× 압축), 메모리 −89~91% (TriAttention KV 절감), accuracy delta ±0.0% (TriAttention 풀-어텐션 동등 정확도, 추론 태스크)
- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 Cross-2: AttentionMatchingCompressedNonContiguousSegmentCache (B+C) — Attention Matching 압착 비연속 세그먼트 캐시
- **조합 근거**: `AttentionMatchingClosedFormCodec(C-2)`의 50× 잠재 공간 KV 압착이 Activity B의 비연속 세그먼트 캐시에 적용되면, 동일 메모리 예산에서 유지 가능한 비연속 세그먼트 수가 50배 증가한다. `DualPathNonContiguousSegmentCache(B-1)` 또는 `SessionAwareTurnLevelSegmentCache(05-22 B-1)`의 각 세그먼트를 Attention Matching으로 `m_c` 토큰으로 압착 저장하고, 재사용 시 현재 쿼리 `Q_current`로 어텐션 출력을 직접 복원하는 "압착 비연속 세그먼트 캐시"가 가능하다. `CLCPositionalBiasGatedSegmentReuse(05-23 B-1)`의 위치 편향 게이트와 결합하면 "압착 세그먼트 복원 → 위치 편향 게이트 판단 → AdapShot 재인코딩 또는 직접 재사용"의 3단계 재사용 파이프라인이 구성된다.
- **구체 설계**:
  1. `AttentionMatchingCompressedSegmentCache` 모듈 (`src/cache/attention_matching_compressed_segment_cache.py`)
  2. **세그먼트 압착 저장 (Segment Compaction on Store)**:
     - 세그먼트 저장 시 Attention Matching 압착 자동 적용: `store(segment_kv) → store(compact_kv, ref_queries)`.
     - `compact_kv ∈ R^{m_c × d_k}` (m_c << segment_len), `ref_queries ∈ R^{m × d_k}` (레퍼런스 쿼리, m=32 기본).
     - 압착 후 메모리: `m_c / segment_len` 비율 → 50× 압축 시 `m_c = segment_len / 50`.
     - 압착 오버헤드: 닫힌 형태 최소제곱 해 → < 10ms/세그먼트 (segment_len=2048 기준).
  3. **세그먼트 재사용 시 복원 경로**:
     - 현재 쿼리 `Q_current`로 압착 KV의 어텐션 출력 계산: `attn_output = softmax(Q_current × compact_kv_K^T / √d) × compact_kv_V`.
     - 레퍼런스 쿼리 `Q_ref` 기반 압착이므로 `Q_current ≠ Q_ref` 시 근사 오차 발생 → `CLCPositionalBiasGatedSegmentReuse(05-23 B-1)` 위치 편향 게이트로 재인코딩 필요성 판단.
     - 위치 편향 낮음(ΔPos ≤ 0.15): 압착 KV 직접 사용. 중간(0.15 < ΔPos ≤ 0.40): 부분 레이어 재인코딩. 높음(ΔPos > 0.40): 전체 복원(AttentionMatching 역압착) 후 AdapShot 재인코딩.
  4. **메모리 용량 확장 정량화**:
     - 기존 FP16 세그먼트 대비 50× 압착 → 동일 메모리에서 50× 더 많은 세그먼트 캐싱.
     - 비연속 히트율 향상: 더 많은 과거 세그먼트를 메모리에 보존 → 히트 기회 증가.
     - 최적 압착 비율 탐색: `compression_ratio` = 10×/20×/50× 별 히트율 vs. accuracy delta 실험.
- **예상 복합 효과**: 처리량 +35~55% (비연속 세그먼트 50× 더 많이 캐싱 → 히트율 대폭 향상 + 어텐션 계산 가속), 메모리 −92~98% (50× Attention Matching 압착), 비연속 히트율 +40~60% (더 많은 세그먼트 캐싱으로 과거 컨텍스트 히트 기회 증가), accuracy delta ±0.5%
- **구현 난이도**: medium
- **우선순위**: 2

### 아이디어 Cross-3: SideQuestDualPathTriAttentionAgentic3WayPipeline (A+B+C) — SideQuest 모델-주도 효용 평가 + DualPath 이중 경로 + TriAttention 압축 에이전틱 3-Way 파이프라인
- **조합 근거**: 에이전틱 추론 서빙에서 `SideQuestTokenUtilityAdmissionController(A-2)`가 추론 모델로 컨텍스트의 토큰 효용을 평가해 고효용 세그먼트만 어드미션 → `DualPathNonContiguousSegmentCache(B-1)` 이중 경로로 분산 스토리지에서 해당 세그먼트를 로드 → `TriAttentionPreRoPEKVSelectorCodec(C-1)` 또는 `AttentionMatchingClosedFormCodec(C-2)`로 압축 후 prefill 노드 전달. 세 Activity가 에이전틱 KV의 "어떤 세그먼트가 필요한지(A, 효용 평가) → 어떻게 가져올지(B, 이중 경로 로드) → 어떻게 줄일지(C, 압축)"를 계층적으로 해결하는 완전한 스택을 형성한다.
- **구체 설계**:
  1. `SideQuestDualPathTriAttentionStack` 모듈 (`src/engine/sidequest_dualpath_triattention_stack.py`)
  2. **통합 처리 흐름**:
     - **Step 1 (SideQuest 토큰 효용 평가, A-2)**: 에이전틱 요청 수신 → 보조 태스크로 컨텍스트 세그먼트 효용 점수 계산. 고효용 세그먼트 목록 확정 (`utility_scores[seg] ≥ 0.5`).
     - **Step 2 (DualPath 이중 경로 로드, B-1)**: 확정된 고효용 세그먼트를 DualPath 이중 경로로 분산 스토리지에서 로드. NIC 부하에 따라 단일/이중 경로 동적 선택.
     - **Step 3 (TriAttention 압축, C-1)**: 로드된 세그먼트 KV를 decode 노드에서 TriAttention pre-RoPE 선택으로 10.7× 압축 → prefill 노드 RDMA 전달.
     - **Step 4 (CLCBiasGate + AdapShot 재인코딩, B)**: prefill 노드에서 위치 편향 게이트 → 재인코딩 정책 결정 → BlockUnionNonContiguousReuseIndex 블록 테이블 구성.
     - **Step 5 (어텐션 계산)**: 표준 PagedAttention 커널 투입.
  3. **SideQuest 저효용 세그먼트 처리**:
     - 저효용 세그먼트(`utility_scores[seg] < 0.3`): Attention Matching 50× 압착으로 압착 저장 (AttentionMatchingCompressedSegmentCache, Cross-2).
     - 중간 효용(0.3~0.5): TriAttention 20% 예산으로 압축 저장.
     - 효용 기반 압축 강도 계층화: 효용이 낮을수록 더 강한 압축 적용.
- **예상 복합 효과**: 처리량 +250~400% (SideQuest 65% 피크 토큰 절감 + DualPath 1.96× I/O 개선 + TriAttention 2.5× 처리량 향상 복합), 메모리 −89~93% (TriAttention 10.7× + SideQuest 저효용 세그먼트 제거), accuracy delta ±0.0~0.5% (고효용 세그먼트 TriAttention 풀-어텐션 동등 + 저효용 Attention Matching 근사)
- **구현 난이도**: high
- **우선순위**: 3
