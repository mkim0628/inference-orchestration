KV Packet의 "소프트-토큰 어댑터 제로-FLOPs 비연속 재사용(B)"과 VeriCache의 "투기적 실행 무손실 압축(C)"은 서로 직교적 방향에서 Activity C의 핵심 제약(accuracy-preserving ±1%)을 보강한다 — B가 재사용 오버헤드를 제거하면 C의 압축이 더 많은 세그먼트에 적용될 수 있다. Predictive Multi-Tier의 Bayesian 헤드-단위 퇴거는 비연속 세그먼트(B)의 우선순위 결정에도 직접 활용 가능하다. Stochastic KV Routing의 깊이 축 압축은 시간 축(토큰 퇴거/양자화)과 곱연산 효과를 내는 직교 차원이다. Activity A에서는 Randomization Boosts KV Caching이 현재 스케줄러의 LRU 퇴거 정책 교체를 위한 강력한 이론 기반을 제공하고, TokenDance가 멀티-에이전트 워크로드에서의 새로운 최적화 차원을 열어 시너지를 형성한다.

## Activity A 아이디어

### 아이디어 A-1: RandomizedCompetitiveEvictionLearningBasedQueryRouter (확률적 경쟁 퇴거 + 학습 기반 쿼리 라우팅 통합 스케줄러)
- **가설**: KV 캐시 퇴거와 쿼리 라우팅을 최초의 통합 수학 모델로 정형화한 Randomization Boosts KV Caching(2601.18999, ICLR 2026)의 핵심 원리 — 결정론적 LRU 퇴거가 동적 요청 도착 패턴에서 이론적 하한을 달성하지 못하며, 확률적 무작위 퇴거(provably competitive randomization)가 LRU 대비 더 높은 경쟁 비율(competitive ratio)을 보장한다 — 를 `src/scheduler/`에 구현하면, 현재 스케줄러의 LRU 기반 퇴거 정책을 이론적으로 최적화된 확률적 퇴거 알고리즘으로 교체하고, 학습 기반 쿼리 라우팅으로 진화하는 쿼리 패턴에 온라인 적응해, 캐시 히트율과 로드 밸런싱을 동시에 향상시킬 수 있다. 과거 A 기법 전체(LRU/LFU/DualMap/Bayesian/Pareto 기반)에서 확률적 경쟁 알고리즘(competitive randomization) 기반 퇴거를 도입한 기법이 없었다 — DualMapDualHashRouter(05-22)는 라우팅 O(1) 후보 선택이었고, CPDWarmColdHitRateRouter(05-23)는 예측 히트율 기반 경로 분기였으며, 모두 결정론적 정책이었다.
- **접근 방법**:
  1. `RandomizedCompetitiveEvictionRouter` 클래스 (`src/scheduler/randomized_competitive_eviction_router.py`): `BaseScheduler` 상속
  2. **확률적 경쟁 퇴거 알고리즘 (Provably Competitive Randomized Eviction)**:
     - KV 블록 퇴거 시 각 블록에 경쟁 알고리즘 기반 퇴거 확률을 부여: `evict_prob(block) = f(recency, access_freq, size) × randomization_factor`.
     - 핵심 수식: `evict_prob(block_i) = C × exp(-λ × access_recency(block_i))` — 지수 감쇠 기반 확률적 퇴거. `λ`는 요청 도착률 추정치로 온라인 갱신.
     - **확률적 선택 메커니즘**: 퇴거 대상 후보 집합에서 `evict_prob`에 비례한 가중 무작위 샘플링(weighted reservoir sampling). 항상 가장 오래된 블록을 퇴거하는 LRU와 달리 확률적으로 분산된 퇴거.
     - 이론적 보장: 논문(2601.18999) Section 3 알고리즘에서 도출된 경쟁 비율 하한 — 동적 도착 패턴에서 LRU의 경쟁 비율을 이론적으로 초과.
     - `randomization_factor` 스케줄: 낮은 KV 풀 압박(`pool_utilization < 0.5`)에서 낮은 무작위성(λ 높게), 높은 압박(`pool_utilization ≥ 0.8`)에서 높은 무작위성(λ 낮게) — 압박 상황에서 더 공격적으로 퇴거.
     - `configs/randomized_eviction_policy.yaml` 외부화: `{lambda_init, lambda_update_rate, randomization_mode: ["exponential", "uniform", "zipf"]}`.
  3. **학습 기반 쿼리 라우팅 (Learning-Based Query Routing)**:
     - 온라인 학습 라우터: 각 요청에 대해 `predict_best_instance(request) → instance_id`. 입력 피처: `{prefix_hash_similarity_to_instances, instance_cache_hit_rate_ema, instance_queue_depth, request_context_length}`.
     - 모델: 경량 다층 퍼셉트론 (입력 4개, 은닉 16개, 출력 N개 인스턴스 로짓). 총 파라미터: < 5K — 추론 오버헤드 < 0.1ms.
     - 온라인 갱신: 라우팅 결정 후 실제 캐시 히트 여부로 강화학습 스타일 업데이트 (REINFORCE, 학습률 0.001). 실제 캐시 히트 발생 → 양의 보상 +1, 미스 → 보상 -0.5.
     - 탐색(exploration)-활용(exploitation) 균형: ε-greedy (ε=0.05) — 5% 확률로 무작위 인스턴스 선택해 미탐색 인스턴스의 캐시 상태 갱신.
     - 논문 Section 4의 "evolving query patterns"에 온라인 적응하는 분산-로드밸런싱 통합 라우팅 구현.
  4. **통합 퇴거-라우팅 파이프라인**:
     - 퇴거 정책과 라우팅 정책의 공유 상태: `{instance_cache_states: Dict[instance_id → CacheState]}`. 퇴거 결정이 캐시 상태를 업데이트하고 라우팅 정책이 이를 즉시 반영.
     - 라우팅 결정 → 캐시 히트 → 퇴거 트리거(캐시 풀 고갈 시) → 확률적 퇴거 → 캐시 상태 갱신 → 다음 라우팅 결정에 반영: 닫힌 피드백 루프.
  5. **A/B 비교 실험 설계**:
     - 기존 LRU 퇴거 + 캐시-어피니티 라우팅 vs. 확률적 퇴거 + 학습 기반 라우팅을 동일 워크로드에서 비교.
     - 지표: `{cache_hit_rate, throughput_tps, load_balance_variance, scheduling_overhead_ms}`.
  6. **이전 A 기법과의 차별점**:
     - DualMapDualHashRouter(05-22): O(1) 이중 해시 후보 선택 (결정론적 캐시-어피니티 근사).
     - CPDWarmColdHitRateRouter(05-23): 예측 히트율 기반 warm/cold 분기 (결정론적 임계값 분류).
     - KVServeBayesianScheduler(05-21): 압축 전략 선택 Bayesian 최적화.
     - RandomizedCompetitiveEvictionRouter: **이론적 최적성이 증명된 확률적 퇴거 + 온라인 학습 라우팅 — ICLR 2026 통합 수학 모델에서 직접 도출된 이론 보장 기반 구현이 이전 어느 A 기법에도 없었다.**
- **대상 환경**: 단일 노드 / 멀티 노드 양쪽
- **멀티 노드 고려사항**: 학습 기반 라우터는 마스터 스케줄러에 단일 인스턴스로 유지하고, 노드별 캐시 상태를 gRPC heartbeat(100ms 주기)로 집계. 확률적 퇴거는 각 노드에서 독립 실행 (로컬 퇴거 정책) — 분산 퇴거 조율 불필요.
- **예상 효과**: 처리량 +15~25% (ICLR 2026 논문의 "실질적 향상" 기반, 동적 도착 패턴 환경), 캐시 히트율 +5~10% (LRU 대비 확률적 퇴거의 이론적 우위), Scheduling overhead TTFT +2% 이내 (학습 라우터 < 0.1ms + 확률적 퇴거 가중 샘플링 < 0.5ms)
- **구현 난이도**: medium
- **우선순위**: 3

### 아이디어 A-2: TokenDanceAllGatherCollectiveDiffAwareKVShareScheduler (TokenDance All-Gather 집합적 KV 공유 + Diff-Aware 스토리지 에이전틱 스케줄러)
- **가설**: 멀티-에이전트 LLM 애플리케이션의 동기화 라운드(All-Gather) 패턴 — 중앙 스케줄러가 모든 에이전트 출력을 수집 후 결합된 컨텍스트를 재배포 — 에서 발생하는 거대한 KV 캐시 중복을, TokenDance(2604.03143)의 두 핵심 기술 — (1) KV Collector: 라운드 전체의 KV 재사용을 집합적 1회 연산으로 처리해 에이전트 수에 무관하게 공유 블록 재사용 비용 1회만 지불, (2) Diff-Aware Storage: 형제 캐시를 단일 마스터 복사본에 대한 블록-스파스 차이로 인코딩해 11~17× 스토리지 압축 — 을 `src/scheduler/`와 `src/cache/`에 구현하면, SLO 조건 하에 vLLM prefix caching 대비 2.7× 더 많은 동시 에이전트를 지원하면서 에이전트당 KV 스토리지를 17.5× 감소시킬 수 있다. 과거 A 기법의 에이전틱 스케줄링 5축(CONCUR/CacheTTL/ThunderAgent/SideQuest/RelayCaching) 중 All-Gather 동기화 라운드 패턴의 집합적 KV 공유 및 블록-스파스 diff 인코딩을 도입한 기법이 없었다.
- **접근 방법**:
  1. `TokenDanceAllGatherScheduler` 클래스 (`src/scheduler/tokendance_allgather_scheduler.py`): `BaseScheduler` 상속
  2. `TokenDanceDiffAwareStorage` 클래스 (`src/cache/tokendance_diff_aware_storage.py`): `CacheStore` 인터페이스 구현
  3. **All-Gather 동기화 라운드 감지 (Round Detection)**:
     - 에이전틱 워크로드 패턴 분류기: `detect_all_gather_pattern(request_batch) → bool`.
     - 감지 기준: 동일 세션의 N개 요청이 동시에 수신되고 컨텍스트의 공통 접두사 비율이 `shared_prefix_threshold`(기본 0.70) 이상인 경우 "All-Gather 라운드"로 분류.
     - 세션 메타데이터: `{session_id, round_id, agent_ids: List[str], shared_context_hash}`.
  4. **KV Collector — 집합적 KV 재사용 (Collective Reuse)**:
     - 라운드 내 공유 KV 블록 식별: `shared_blocks = {b : b in all_agents' contexts}`. 집합 연산으로 O(N × B) — N개 에이전트, B개 블록.
     - 공유 블록을 단일 마스터 복사본(`master_kv_block`)으로 통합: `N × shared_block_size → 1 × shared_block_size`.
     - 각 에이전트의 어텐션 계산 시 마스터 복사본 참조 (포인터 공유, 데이터 복사 없음).
     - 공유 블록 재사용 비용: 에이전트 수 N에 무관하게 1회만 지불 (TokenDance KV Collector 원리).
  5. **Diff-Aware Storage — 블록-스파스 차이 인코딩**:
     - 에이전트별 KV = 마스터 복사본 + 에이전트-특화 차이(diff): `agent_kv = master_kv + sparse_diff`.
     - `sparse_diff` 표현: 블록-스파스 행렬 — 비제로 블록만 저장. 스파스도 임계값: `sparsity_threshold`(기본 0.95) — 95% 이상 제로인 경우 스파스 인코딩 적용.
     - 스토리지: `Dict[agent_id → SparseBlockDiff(nonzero_blocks: Dict[block_idx → block_data])]`.
     - 비제로 블록 비율: 원논문 11~17× 압축 → 전체 블록의 6~9% 비제로.
     - 마스터 복사본 + diff 복원: `restore_agent_kv(agent_id) = master_kv + sparse_diff[agent_id]`. 필요 시 O(sparse_nnz)로 복원.
  6. **TokenDance + CONCURCongestionBasedAgentAdmissionScheduler(05-20) 연동**:
     - CONCUR이 KV 풀 혼잡 시 에이전트 어드미션을 제한하는 반면, TokenDance는 All-Gather 패턴에서 KV 풀 압박 자체를 17.5× 감소시켜 CONCUR의 어드미션 거부 빈도를 구조적으로 줄임.

  7. **이전 A 기법과의 차별점**:
     - CONCURCongestionBasedAgentAdmissionScheduler(05-20): KV 풀 점유율 임계값 기반 반응적 어드미션 제어.
     - ThunderAgentProgramScheduler(05-19): 정적 Program 분석 기반 쓰래싱 방지.

- **대상 환경**: 단일 노드 / 멀티 노드 양쪽

## Activity B 아이디어

### 아이디어 B-1: KVPacketSoftTokenAdapterZeroFLOPsNonContiguousCache (KV Packet 소프트-토큰 어댑터 제로-FLOPs 비연속 캐시)
- **가설**: KV Packet(2604.13226)의 핵심 아이디어 — 캐시된 문서를 불변 "패킷"으로 취급하고 경량 훈련 가능한 소프트-토큰 어댑터로 감싸 컨텍스트 불연속성을 자기지도 증류로 보완, 새 컨텍스트에서도 재계산 FLOPs 없이 패킷을 직접 삽입 — 를 Activity B의 `src/cache/` 레이어에 구현하면, 비연속 세그먼트 재사용의 핵심 오버헤드 — 문맥 불연속성으로 인한 KV 재계산 FLOPs — 를 제거하면서 기존 CacheBlend/EPIC 대비 더 낮은 TTFT와 동등한 정확도를 달성할 수 있다. 과거 B 기법 전체(CLCPositionalBiasGatedSegmentReuse 05-23, DualPathNonContiguousSegmentCache 05-24, AMPDAdapShotLazyLoadPipeline 05-18, BlockUnionNonContiguousReuseIndex 05-21, AdapShot RoPE 재인코딩)는 모두 재계산 FLOPs 또는 RoPE 위치 인코딩 수정을 통해 컨텍스트 불연속성을 처리했으며, 어댑터 증류로 불연속성 자체를 흡수하는 방법이 없었다.
- **접근 방법**:
  1. `KVPacketAdapterCache` 클래스 (`src/cache/kv_packet_adapter_cache.py`): `CacheStore` 인터페이스 구현
  2. **KV Packet 포맷 정의 (Packet Format)**:
     - 각 캐시 세그먼트를 "KV Packet"으로 패키징: `KVPacket(segment_hash, kv_data, adapter_weights, adapter_config)`.
     - `kv_data`: 세그먼트의 불변 KV 텐서 (FP16, `[n_layers, n_heads, seq_len, head_dim]`).
     - `adapter_weights`: 경량 소프트-토큰 어댑터 가중치 (`[n_adapter_tokens, d_model]` — 기본 n_adapter_tokens=4, d_model=4096). 총 파라미터: 4 × 4096 × 2 (K, V) = 32768 파라미터/패킷.
     - `adapter_config`: `{distillation_loss: float, context_type: str, position_offset: int}`.
  3. **소프트-토큰 어댑터 증류 훈련 (Adapter Distillation)**:
     - 세그먼트 저장 시 어댑터 훈련 트리거: `store(segment_kv, context_sample) → KVPacket`.
     - 자기지도 증류 목표 함수 (KV Packet 원논문 방식):
       ```
       L_adapter = ||attn_output(kv_full, q) - attn_output(kv_packet + adapter, q)||_F
       ```
       `q`: 컨텍스트 샘플에서 추출한 레퍼런스 쿼리 (m=16개 랜덤 샘플링).
     - 옵티마이저: AdamW (lr=1e-4, 100 스텝). 훈련 오버헤드: < 500ms/패킷 (단발 훈련, 세그먼트 저장 시 1회).
     - GitHub 코드 참조: github.com/ChuangtaoChen-TUM/KVPacket.
  4. **제로-FLOPs 비연속 재사용 경로 (Zero-FLOPs Reuse)**:
     - 캐시 히트 시 재사용 경로: `get(segment_hash, current_context) → kv_packet + apply_adapter(adapter_weights, current_context_embedding)`.
     - 어댑터 적용 (`apply_adapter`): 소프트-토큰 어댑터를 현재 컨텍스트의 첫 N 위치에 삽입해 컨텍스트 불연속성 흡수. 연산량: `n_adapter_tokens × d_model` 행렬 조회 + 덧셈 — FLOPs 무시 가능.
     - **재계산 없음**: 어댑터 가중치는 사전 훈련되어 있으므로 재사용 시 gradient 계산, attention forward pass 재실행 불필요 → **재계산 FLOPs = 0**.
  5. **AdapShot(RoPE 재인코딩)과의 2단계 통합**:
     - 위치 불일치(RoPE 문제)는 AdapShot이 처리, 컨텍스트 불연속성은 KV Packet 어댑터가 처리 — 두 가지 불연속성 원인을 독립적으로 분리 처리.
     - 파이프라인: `get(segment_hash) → apply_kv_packet_adapter(adapter) → adapshot_rope_correction(position_offset)`.
     - 둘 다 재계산이 아닌 경량 변환 — 전체 파이프라인 추가 오버헤드 < 1ms.
  6. **패킷 퇴거 정책**:
     - 패킷 크기 = `kv_data_size + adapter_size`. adapter_size ≈ 32KB (32768 파라미터 × FP16) — kv_data_size(세그먼트 수백 MB)에 비해 무시 가능.
     - 퇴거 기준: LRU + `distillation_loss > loss_threshold`(기본 0.1) — 어댑터 품질이 낮은 패킷 우선 퇴거.
  7. **이전 B 기법과의 차별점**:
     - CLCPositionalBiasGatedSegmentReuse(05-23 B-1): 위치 편향 연속값으로 3단계 재인코딩 게이트 (재인코딩 최소화, 완전 제거 아님).
     - DualPathNonContiguousSegmentCache(05-24 B-1): 이중 경로 스토리지 NIC 중계 (네트워크 경로 이중화, 재계산 FLOPs 유지).
     - AMPDAdapShotLazyLoadPipeline(05-18 B-1): pull-on-demand 지연 로드 + AdapShot RoPE 재인코딩 (재인코딩 포함).
     - KVPacketAdapterCache: **훈련된 소프트-토큰 어댑터로 컨텍스트 불연속성을 사전 흡수해 재사용 시 재계산 FLOPs = 0** — 이전 어느 B 기법도 재계산을 완전히 제거하지 못했다.
- **예상 효과**: 비연속 히트율 +20~30% (재계산 오버헤드 제거로 비연속 재사용 실용성 증가), TTFT −30~50% (재계산 FLOPs 제거 + 경량 어댑터 적용만), 재계산 FLOPs −95~100% (어댑터 훈련 1회 후 재사용 시 제로)
- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 C-1: VeriCacheSpeculativeKVDraftVerifyLosslessCodec (VeriCache 투기적 KV 드래프팅-검증 무손실 압축 코덱)
- **가설**: VeriCache(2605.17613)의 투기적 실행 패러다임 — (1) 압축 KV 캐시로 드래프트 토큰 병렬 생성, (2) 전체 KV 캐시로 검증, (3) 압축 KV 디코딩(HBM 대역폭 바운드)과 전체 KV 스왑(PCIe/네트워크 바운드)의 병렬화 가능성 활용 — 을 `src/cache/` 레이어에 구현하면, Activity C의 핵심 제약 "accuracy-preserving ±1% 이내"를 결정론적 ±0%로 강화하면서, 압축 KV의 처리량 이점을 대부분 보존하는 "손실 없는 KV 압축 추론"을 달성할 수 있다. RuntimeCertifiedQuantizedAttentionCodec(05-23 C-1)이 런타임 오류 경계를 계산해 확률적 보장을 제공했다면, VeriCache는 전체 KV 검증으로 결정론적 동일 출력을 보장하는 더 강한 메커니즘이다 — 투기적 실행을 KV 압축에 적용하는 방법은 이전 어느 C 기법에도 없었다.
- **접근 방법**:
  1. `VeriCacheSpeculativeCodec` 클래스 (`src/cache/vericache_speculative_codec.py`): `CompressionCodec` 인터페이스 구현
  2. **드래프트 단계 (Draft Phase) — 압축 KV로 빠른 토큰 생성**:
     - 압축 KV 캐시 유지: `compressed_kv = any_compression_codec.compress(full_kv)`. 압축 코덱은 플러그인으로 교체 가능 (기본: TriAttentionPreRoPEKVSelectorCodec의 top-10% KV 선택).
     - 드래프트 토큰 생성: 압축 KV로 `draft_tokens = decode(compressed_kv, input_ids)` — 다수 토큰 병렬 드래프트 (`draft_length` 기본 4토큰).
     - 드래프트 실행은 HBM 내 압축 KV로만 이루어지므로 HBM 대역폭 바운드.
  3. **검증 단계 (Verify Phase) — 전체 KV로 드래프트 검증**:
     - 전체 KV 복원: `full_kv = load_from_offload_storage(segment_id)`. 오프로드 스토리지(DRAM/SSD)에서 PCIe/네트워크를 통해 전체 FP16 KV 스왑.
     - 검증: `verified_tokens = verify(full_kv, draft_tokens)`. 드래프트 토큰이 전체 KV의 어텐션 출력과 일치하는지 확인.
     - 수락 판정: 드래프트 토큰 `t`의 logit이 전체 KV 검증 logit과 일치하면 수락, 첫 불일치 위치에서 전체 KV 기반 토큰으로 수정.
     - **결정론적 동일 출력 보장**: 검증을 통과한 토큰은 전체 KV 어텐션 출력과 수학적으로 동일. 불일치 토큰은 수정 — 출력 분포 = 전체 KV 추론과 완전히 동일.
  4. **병렬화 — 드래프트와 검증 동시 실행 (Parallel Execution)**:
     - VeriCache의 핵심 통찰: 압축 KV 드래프팅은 HBM 대역폭 바운드, 전체 KV 스왑은 PCIe/네트워크 바운드 → 두 연산이 서로 다른 하드웨어 자원을 사용하므로 완전한 병렬화 가능.
     - 구현: CUDA Stream 2개 — `stream_draft`: 압축 KV 어텐션 계산, `stream_swap`: 전체 KV 비동기 prefetch (`torch.cuda.Stream.wait_stream`으로 동기화).
     - 전체 KV prefetch: `asyncio.ensure_future(prefetch_full_kv_from_offload(segment_id))` — 드래프트 생성 중 전체 KV 비동기 로드.
  5. **압축 코덱 플러그인 인터페이스**:
     - `VeriCacheSpeculativeCodec`는 압축 알고리즘에 무관하게 동작: `set_draft_codec(codec: CompressionCodec)`.
     - 지원 코덱: TriAttentionPreRoPEKVSelectorCodec(05-24 C-1), AttentionMatchingClosedFormCodec(05-24 C-2), INT8 양자화, H2O/SnapKV 퇴거 등 모든 기존 C 기법.
     - 드래프트 수락률(`acceptance_rate = n_accepted / n_draft`)이 높은 코덱을 선택해 처리량 최대화: `acceptance_rate` 온라인 추적 + `swap_best_codec(threshold=0.7)`.
  6. **P/D 분리 환경에서의 적용 (A+C 시너지)**:
     - VeriCache 논문의 "드래프트-HBM 바운드 + 검증-PCIe 바운드" 통찰을 P/D 분리에 적용:
       - 압축 KV를 프리필 노드에서 디코드 노드로 전송 (소형, 빠름).
       - 전체 KV를 DRAM 오프로딩에서 디코드 노드로 비동기 스트리밍.
       - 디코드 노드가 압축 KV로 드래프팅하면서 전체 KV 수신 → 검증.
  7. **이전 C 기법과의 차별점**:
     - RuntimeCertifiedQuantizedAttentionCodec(05-23 C-1): 런타임 오류 경계 계산 + 폴백 사다리 (확률적 보장, 투기적 실행 없음).
     - TriAttentionPreRoPEKVSelectorCodec(05-24 C-1): pre-RoPE 삼각함수 KV 선택 (압축 정확도 경험적 검증, 결정론적 보장 없음).
     - VeriCacheSpeculativeCodec: **투기적 실행으로 압축 KV 드래프팅 + 전체 KV 검증 → 결정론적 출력 동일 보장 — 투기적 실행을 KV 압축에 처음 적용하는 기법.**
- **예상 효과**: 메모리 −50~89% (선택한 압축 코덱에 따라, TriAttention 사용 시 −89%), accuracy delta ±0.0% (결정론적 전체 KV 검증으로 수학적 보장), 처리량 +50~150% (드래프트 수락률에 비례 — 수락률 0.7 기준 +70% 추정)
- **accuracy-preserving 근거**:
  (1) VeriCache(2605.17613)는 전체 KV 캐시 검증으로 출력 토큰이 전체 KV 추론과 결정론적으로 동일함을 수학적으로 보장. accuracy delta는 정의상 ±0.0%.
  (2) 드래프트 단계에서 수락 실패한 토큰은 전체 KV 기반 올바른 토큰으로 교체 — 출력 정확도 손실 없음.
  (3) 드래프트 수락률이 낮아도 (최악의 경우 0%) 처리량은 단순 전체 KV 추론과 동일 수준으로 fallback (처리량 이점만 손실, 정확도 손실 없음).
  (4) 압축 코덱 선택에 무관하게 정확도 보장 — 어떤 손실 압축을 드래프트에 사용해도 검증 단계가 오류를 수정.
  검증: WikiText-2 perplexity ±0.0% (전체 KV와 동일 출력 확인) + 드래프트 수락률 측정(다양한 압축 코덱별) + 드래프트 길이(1/2/4/8토큰) vs. 처리량 곡선 + AIME25 동등성 확인 + P/D 분리 환경 CUDA Stream 병렬화 효율 측정.

### 아이디어 C-2: PredictiveMultiTierBayesianHeadLevelEMAEvictionCache (Predictive Multi-Tier Bayesian 헤드-단위 EMA 퇴거 + 아키텍처-인식 KV 캐시)
- **가설**: Predictive Multi-Tier(2604.26968)의 세 가지 통합 원리 — (1) MLA/GQA/MHA 아키텍처별 정확한 KV 크기 산정(기존 범용 프레임워크의 최대 57× 오버프로비저닝 제거), (2) 16가지 (블록 유형, 전환 유형) 쌍에 대한 Beta conjugate prior Bayesian 재사용 예측(70~84% 캐시 히트율 달성), (3) EMA 기반 어텐션 헤드별 중요도 추적 + RoPE 위치 인코딩 지역성 활용 프리페치(LRU 대비 25% 미스율 감소) — 를 `src/cache/` 레이어에 구현하면, KV 캐시 메모리를 정확하게 관리하면서 예측적 퇴거-프리페치로 처리량과 히트율을 동시에 개선할 수 있다. KaretoStorageTuner(05-23 A-1)는 파레토 구성 최적화였고, KVServeBayesianScheduler(05-21)는 압축 전략 선택 Bayesian 탐색이었으며, 헤드-레벨 EMA 중요도 + RoPE 지역성 기반 퇴거-프리페치 파이프라인은 이전 어느 기법에도 없었다.
- **접근 방법**:
  1. `PredictiveMultiTierKVCache` 클래스 (`src/cache/predictive_multitier_kv_cache.py`): `CacheStore` 인터페이스 구현
  2. **아키텍처-인식 KV 크기 산정 엔진 (Architecture-Aware Sizing)**:
     - 모델 아키텍처 감지: `detect_attention_arch(model_config) → {"MHA", "GQA", "MLA"}`.
     - 아키텍처별 KV 메모리 계산:
       - MHA: `kv_size = 2 × n_layers × n_heads × seq_len × head_dim × bytes_per_element`.
       - GQA: `kv_size = 2 × n_layers × n_kv_heads × seq_len × head_dim × bytes_per_element` (n_kv_heads < n_heads).
       - MLA (DeepSeek 계열): `kv_size = n_layers × kv_lora_rank × seq_len × bytes_per_element` (저랭크 잠재 벡터).
     - `model_arch_registry.yaml`: 지원 모델 아키텍처 + KV 크기 공식 등록.
     - 오버프로비저닝 제거: 정확한 KV 크기로 메모리 할당 → 기존 57× 오버프로비저닝 → 1× (정확 산정).
  3. **Bayesian 재사용 예측 (Beta Conjugate Prior)**:
     - 16가지 (블록 유형, 전환 유형) 쌍 정의:
       - 블록 유형: `{system_prompt, user_turn, agent_output, tool_call}` (4종).
       - 전환 유형: `{session_continue, session_new, inter_request_same_prefix, cold_start}` (4종).
       - 총 16가지 (블록 유형, 전환 유형) 조합.
     - 각 쌍에 독립적인 Beta prior: `Beta(α_ij, β_ij)`. 초기값: `α=1, β=1` (균등 사전 분포).
     - 온라인 업데이트: 캐시 히트 → `α_ij += 1`, 미스 → `β_ij += 1`.
     - 재사용 예측 확률: `P_reuse(block_type=i, transition=j) = α_ij / (α_ij + β_ij)`.
     - 예측 기반 프리페치: `P_reuse > prefetch_threshold`(기본 0.75) 시 해당 블록을 낮은 계층(DRAM→HBM)으로 사전 이동.
  4. **RoPE-인식 헤드-단위 EMA 퇴거 (Head-Level EMA Eviction)**:
     - 어텐션 헤드별 중요도 EMA 추적: `importance_ema[layer][head] = γ × attn_weight_mean + (1-γ) × importance_ema[layer][head]`. `γ=0.9` (EMA 감쇠 계수).
     - RoPE 위치 지역성 통합: 최근 N 토큰에 대한 헤드별 어텐션 엔트로피 계산 — 엔트로피가 낮으면 특정 위치 집중 (RoPE 주파수와 상관), 높으면 균등 분포.
       ```
       rope_locality(head) = 1 - attn_entropy(head) / log(seq_len)
       ```
     - 헤드-단위 퇴거 점수: `evict_score(kv_block, layer, head) = α × importance_ema[layer][head] + β × rope_locality(layer, head)`.
       - `α=0.6, β=0.4` (YAML 외부화).
     - 퇴거: `evict_score` 최솟값 블록 우선 퇴거 (LRU 대비 25% 미스율 감소 목표).
  5. **3-티어 배치 최적화 (HBM/DRAM/SSD)**:
     - HBM: `importance_ema` 상위 `hbm_capacity_ratio`(기본 0.3) 블록.
     - DRAM: `P_reuse > 0.5` AND `importance_ema` 중간 구간.
     - SSD: 나머지 (`P_reuse < 0.5` OR `importance_ema` 하위).
     - 비동기 프리페치: Bayesian 예측으로 다음 요청에 필요한 블록을 현재 요청 처리 중 비동기 이동 (`asyncio.ensure_future(prefetch_block(block_id))`).
  6. **이전 C 기법과의 차별점**:
     - KaretoStorageTuner(05-23 A-1): 파레토 가지치기 스토리지 구성 최적화 (구성 탐색, 퇴거 정책 개선 아님).
     - DapQPositionAwareEvictionCodec(05-22 C-3): post-RoPE 유사 쿼리 기반 토큰-레벨 중요도 (헤드-레벨 EMA 아님).
     - PredictiveMultiTierKVCache: **아키텍처-인식 정확 크기 산정 + Bayesian Beta prior 재사용 예측 + 헤드-단위 EMA + RoPE 지역성 퇴거-프리페치 통합** — 세 원리의 통합 구현이 이전 어느 기법에도 없었다.
- **예상 효과**: 메모리 −30~50% (정확 크기 산정으로 오버프로비저닝 제거 + 헤드-단위 퇴거), 처리량 +100% (2.0× TensorRT-LLM 대비, 원논문 64-GPU H100 기준), 캐시 히트율 +15~20% (Bayesian 예측 프리페치, 70~84% 달성 목표), accuracy delta ±0% (퇴거만 수행, 양자화 없음 — 정확도 손실 없음)
- **accuracy-preserving 근거**:
  (1) Predictive Multi-Tier 원논문(2604.26968)에서 헤드-단위 EMA + RoPE 지역성 기반 퇴거는 어텐션 가중치 관련성이 낮은 KV 블록만 퇴거하며, 정확도 손실 없는 퇴거(eviction without accuracy loss)를 달성함을 64-GPU 실험에서 검증.
  (2) Bayesian 재사용 예측은 퇴거 결정에 사용되지 않고 프리페치 결정에만 사용 — 필요한 블록을 미리 이동하는 것이므로 정확도에 영향 없음.
  (3) 헤드-단위 퇴거에서 `importance_ema` 임계값 이상인 헤드의 KV는 절대 퇴거하지 않는 보호 정책 추가 — 중요 헤드의 KV가 유실되지 않도록 보장.
  (4) 아키텍처-인식 크기 산정: KV 크기를 정확히 계산하므로 과도한 퇴거를 방지 (오버프로비저닝 오류로 인한 불필요 퇴거 제거).
  검증: WikiText-2 perplexity ±1% + LongBench 8개 서브태스크 + MLA 모델(DeepSeek-V3) vs. GQA 모델(LLaMA-3) vs. MHA 모델 3종 아키텍처 비교 + EMA 감쇠 계수(γ=0.7/0.8/0.9/0.95) 별 정확도 곡선 + Bayesian 예측 정확도(hit rate 예측 오차) 측정 + HBM/DRAM/SSD 3-티어 히트율 분포.
- **구현 난이도**: medium
- **우선순위**: 2

### 아이디어 C-3: StochasticKVRoutingDepthAxisShareFinetuneCodec (Stochastic KV Routing 깊이 축 공유 파인튜닝 코덱)
- **가설**: Stochastic KV Routing(2604.22782, Apple ML Research)의 핵심 아이디어 — 훈련 중 레이어가 자신의 KV 상태 또는 이전 레이어의 KV 상태 중 무작위로 선택해 어텐션하는 확률적 크로스-레이어 학습으로 배포 시 다양한 깊이 방향 KV 공유 전략에 강건한 모델을 만든다 — 를 파인튜닝 단계에서 현재 사용 모델에 적용하면, 시간 축(토큰 퇴거, 양자화)과 독립적으로 깊이 축 KV 메모리 절감을 달성하는 "2축 KV 압축"이 가능하다. LRKV(공유 풀-랭크 기저, 과거 C 기법)가 훈련-시간 아키텍처 변경이었다면, Stochastic KV Routing은 파인튜닝만으로 기존 모델에 깊이 축 KV 공유를 부여하는 실용적 접근이다.
- **접근 방법**:
  1. `StochasticKVRoutingFinetuner` 클래스 (`src/cache/stochastic_kv_routing_finetuner.py`): `CompressionCodec` 인터페이스 구현 (파인튜닝 단계) + `src/cache/stochastic_kv_routing_cache.py` (추론 단계)
  2. **확률적 크로스-레이어 어텐션 파인튜닝 (Stochastic Cross-Layer Attention)**:
     - 파인튜닝 시 각 레이어 `l`에서 다음을 랜덤 선택:
       ```python
       if random.random() < cross_layer_prob:
           kv_used = kv_cache[l - k]  # k ∈ {1, 2, ..., K} 랜덤 선택
       else:
           kv_used = kv_cache[l]  # 자신의 KV 사용
       ```
       `cross_layer_prob`: 기본 0.3 (30% 확률로 이전 레이어 KV 참조). `K`: 최대 참조 레이어 거리 (기본 K=2).
     - 파인튜닝 목표: 원본 모델 출력 분포 유지 (KL 발산 최소화): `L_finetune = KL(p_original || p_stochastic)`.
     - 파인튜닝 규모: 전체 파라미터 동결 + 어텐션 레이어만 업데이트 (LoRA rank=8). 에폭 수: 3~5.
     - 데이터셋: `data/processed/` 내 도메인 대표 샘플 (최소 1K 샘플).
  3. **배포 시 깊이 축 KV 공유 전략 (Depth-Axis Sharing at Inference)**:
     - 파인튜닝된 모델을 다양한 KV 공유 전략으로 실행:
       - `every_k_layers`: 매 k번째 레이어만 독립 KV 계산, 나머지는 직전 독립 계산 레이어 KV 공유. k=2 → 50% 레이어 KV 절감.
       - `adaptive_sharing`: `importance_ema[l]` 낮은 레이어는 이전 레이어 KV 공유, 높은 레이어만 독립 KV 계산.
     - 메모리 절감: k=2 공유 시 총 KV 메모리 −50% (레이어 수 절반만 KV 저장).
     - `configs/stochastic_kv_routing_policy.yaml` 외부화: `{cross_layer_prob, K, sharing_strategy, every_k_layers}`.
  4. **시간 축 압축과의 곱연산 결합 (Multiplicative Compression)**:
     - 시간 축 압축(TriAttentionPreRoPEKVSelectorCodec 05-24 C-1, top-10% 토큰 유지): −90% 메모리 (10× 절감).
     - 깊이 축 공유(이 기법, k=2): −50% 메모리 (2× 절감).
     - 결합 효과: `1 × 0.10 × 0.50 = 0.05` → **총 KV 메모리 −95%** (20× 절감).
  5. **파인튜닝 후 정확도 인증 (Post-Finetuning Accuracy Certification)**:
     - 파인튜닝 완료 후 accuracy delta 측정 필수: WikiText-2 perplexity ±1% + LongBench.
     - accuracy delta > 1% 시 `cross_layer_prob` 감소 (0.3 → 0.2) 후 재파인튜닝.
  6. **이전 C 기법과의 차별점**:
     - LRKV(공유 풀-랭크 기저, 과거): 훈련-시간 아키텍처 변경 (새 아키텍처 필요).
     - TriAttentionPreRoPEKVSelectorCodec(05-24 C-1): 시간 축 토큰 선택 (깊이 축 무관).
     - StochasticKVRoutingFinetuneCodec: **파인튜닝만으로 기존 모델에 깊이 축 KV 공유 강건성 부여 + 배포 시 다양한 하드웨어 제약에 적응적 적용** — 시간 축 압축과 직교하는 깊이 축 압축이 이전 어느 C 기법에도 없었다.
- **예상 효과**: 메모리 −45~50% (깊이 축 k=2 공유 단독), 시간 축 압축과 결합 시 메모리 −90~95% (곱연산), accuracy delta ±0.5~1.0% (파인튜닝 후, 원논문 "다양한 모델 패밀리" 검증 기준)
- **accuracy-preserving 근거**:
  (1) Stochastic KV Routing 원논문(2604.22782, Apple ML Research)에서 확률적 크로스-레이어 훈련이 사전훈련 또는 파인튜닝으로 다양한 모델 패밀리에서 깊이 방향 KV 공유를 허용하면서도 성능을 보존함을 실험적으로 검증.
  (2) `cross_layer_prob=0.3`(30% 레이어가 이전 KV 공유): 70% 레이어는 독립 KV 사용 — 모델 표현력의 70%는 완전히 보존.
  (3) 파인튜닝 목표 함수 `KL(p_original || p_stochastic)` 직접 최소화: 원본 출력 분포 보존을 명시적 목표로 최적화.
  (4) LoRA rank=8 파인튜닝으로 전체 파라미터 동결 — 파인튜닝 범위 제한으로 성능 회귀 위험 최소화.
  (5) accuracy delta > 1% 시 자동 재파인튜닝 fallback 로직 포함.
  검증: WikiText-2 perplexity ±1% + LongBench 8개 서브태스크 + cross_layer_prob(0.1/0.2/0.3/0.4) 별 accuracy delta 곡선 + every_k_layers(k=1,2,3,4) 별 메모리 vs. 정확도 트레이드오프 + 시간 축(TriAttention top-10%) + 깊이 축(k=2) 결합 실험.
- **구현 난이도**: medium
- **우선순위**: 3

## 크로스 Activity 시너지 아이디어

### 아이디어 Cross-1: VeriCacheKVPacketZeroFLOPsLosslessNonContiguousPipeline (B+C) — KV Packet 제로-FLOPs 비연속 재사용 + VeriCache 무손실 압축 파이프라인
- **조합 근거**: `KVPacketAdapterCache(B-1)`가 소프트-토큰 어댑터로 비연속 세그먼트 재사용 시 재계산 FLOPs를 제거하고, `VeriCacheSpeculativeCodec(C-1)`이 압축 KV로 빠른 드래프팅 후 전체 KV로 결정론적 검증한다. 두 기법을 결합하면 "어댑터로 비연속 세그먼트 컨텍스트 불연속성 흡수(B) → 압축 KV로 드래프팅(C) → 전체 KV로 검증(C)"의 파이프라인이 성립한다. B가 비연속 세그먼트 재사용의 FLOPs 오버헤드를 제거하면, C가 더 많은 세그먼트에 대해 압축-검증을 적용할 수 있어 메모리와 처리량이 복합 개선된다.
- **구체 설계**:
  1. `KVPacketVeriCachePipeline` 모듈 (`src/engine/kv_packet_vericache_pipeline.py`)
  2. **통합 처리 흐름**:
     - **Step 1 (비연속 세그먼트 히트 감지, B-1)**: `KVPacketAdapterCache.get(segment_hash)` → 히트 시 `kv_packet + adapter` 반환.
     - **Step 2 (어댑터 적용, B-1)**: `apply_adapter(kv_packet, current_context)` → 컨텍스트 불연속성 흡수. 재계산 FLOPs = 0.
     - **Step 3 (VeriCache 드래프팅, C-1)**: 어댑터 적용된 KV Packet(압축 상태)로 드래프트 토큰 생성.
     - **Step 4 (전체 KV 비동기 로드, C-1)**: Step 2 실행 중 전체 KV를 오프로드 스토리지에서 비동기 prefetch.
     - **Step 5 (VeriCache 검증)**: 드래프트 토큰을 전체 KV로 검증 → 수락/교체.
  3. **메모리 효율화**:
     - KV Packet 저장: `kv_data(압축) + adapter(32KB)` — 전체 KV의 10~50%만 HBM에 상주.
     - 전체 KV는 DRAM/SSD 오프로딩 — 검증 시에만 PCIe로 로드 (VeriCache 방식).
     - 동일 HBM 예산에서 10~50× 더 많은 비연속 패킷 캐싱 가능.

- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 Cross-2: TokenDanceKVPacketAllGatherAdapterAwareAgenticPipeline (A+B) — TokenDance 집합적 KV 공유 + KV Packet 어댑터 에이전틱 비연속 재사용 파이프라인

- **구체 설계**:

  2. **통합 처리 흐름**:

- **우선순위**: 3

### 아이디어 Cross-3: VeriCachePredictiveMultiTierBayesianSpeculativeKVStack (A+B+C) — Bayesian 예측 + KV Packet 제로-FLOPs + VeriCache 무손실 통합 스택

- **예상 복합 효과**: 처리량 +150~250% (Bayesian 프리페치 × KV Packet 제로-FLOPs × VeriCache 드래프팅 복합), 메모리 −85~95% (헤드-단위 퇴거 + 깊이 축 공유 + 오프로딩), accuracy delta ±0.0% (VeriCache 결정론적 보장)
