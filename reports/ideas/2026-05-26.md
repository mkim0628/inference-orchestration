## Activity A 아이디어

### 아이디어 A-1: ObjectCacheS3TierBreakEvenRoutingPolicy (ObjectCache S3 티어 브레이크이븐 기반 동적 KV 라우팅 정책)
- **가설**: ObjectCache(2605.22850)의 레이어와이즈 S3 RDMA 전달이 64K 컨텍스트에서 5.6% TTFT 추가를 유발하지만, KV 히트율이 충분히 높으면 이 추가 지연이 KV 재계산 비용 절감으로 상쇄된다는 원리 — "S3 티어 사용의 브레이크이븐 히트율(break-even hit rate)" — 을 `src/engine/batch_runner.py`에서 온라인으로 계산하고, 실시간 히트율이 브레이크이븐 임계값을 초과할 때만 S3 티어로 라우팅하는 "S3-인식 4-티어 동적 라우팅 정책"을 구현하면, GPU/DRAM/SSD 3-티어의 용량 한계를 S3로 초과하면서도 불필요한 원격 전달 오버헤드를 구조적으로 회피해 스케줄링 오버헤드 TTFT p50 +5% 이내 제약을 S3 계층까지 유지할 수 있다. 과거 A 기법 전체(KVDriveAttentionPipelineScheduler 05-19, DualPathNICLoadBalancer 05-24, CPDWarmColdHitRateRouter 05-23, KaretoStorageTuner 05-23 등)에서 S3 오브젝트 스토리지를 4번째 계층으로 추가하면서 브레이크이븐 히트율 기반 동적 티어 전환을 구현한 기법이 없었다.
- **접근 방법**:
  1. `ObjectCacheS3TierRouter` 클래스 (`src/scheduler/objectcache_s3_tier_router.py`): `BaseScheduler` 상속
  2. **브레이크이븐 히트율 계산 (Break-Even Hit Rate)**:
     - 수식 도출: S3 사용 TTFT = `T_local × (1 - hit_rate) + T_s3 × hit_rate`. S3 미사용 시 TTFT = `T_local × (1 - hit_rate) + T_recompute × (1 - hit_rate)`.
     - 브레이크이븐 조건: `T_s3 × hit_rate ≤ T_recompute × (1 - hit_rate)`.
     - 브레이크이븐 히트율: `hit_rate_breakeven = T_recompute / (T_recompute + T_s3)`.
     - 측정값 입력: `T_s3` = ObjectCache의 레이어와이즈 RDMA 전달 지연(측정, 기본 S3 64K 컨텍스트 기준 약 5.6% TTFT 추가), `T_recompute` = 동일 세그먼트 KV 재계산 지연(측정, 온라인 EMA).
     - 결과: `{context_length: [4K, 8K, 16K, 32K, 64K]} → {hit_rate_breakeven}` 룩업 테이블. `configs/objectcache_breakeven_table.yaml` 외부화.
  3. **실시간 히트율 추적 + 동적 티어 전환 결정**:
     - 슬라이딩 윈도우 히트율 추적: `hit_rate_ema = γ × current_hit + (1-γ) × hit_rate_ema` (γ=0.9, 최근 1000 요청 EMA).
     - 티어 전환 로직:
       - `hit_rate_ema ≥ hit_rate_breakeven(context_length) + hysteresis_band(기본 0.05)`: S3 티어 활성화.
       - `hit_rate_ema < hit_rate_breakeven(context_length) - hysteresis_band`: S3 티어 비활성화 → SSD/DRAM 3-티어 유지.
       - 히스테리시스 밴드: 티어 전환의 과도한 진동(oscillation) 방지.
     - 전환 결정 오버헤드: EMA 갱신 O(1) + 브레이크이븐 테이블 조회 O(1) → < 0.01ms/요청.
  4. **ObjectCache 대역폭-인식 스케줄러 연동**:
     - ObjectCache 원논문의 공유 대역폭 하에서 레이어별 스톨 타겟 배분 알고리즘을 `src/engine/batch_runner.py`에 통합.
     - 배치 내 요청별 `context_length`와 현재 가용 RDMA 대역폭(`rdma_available_gbps`)을 입력으로 각 요청의 레이어별 S3 전달 타이밍 계산.
     - 배치 내 S3 라우팅 요청 수 상한: `max_s3_requests_per_batch`(기본 4) — 대역폭 집중 방지.
  5. **4-티어 계층 관리 통합**:
     - 기존 3-티어(HBM/DRAM/SSD): KVDriveAttentionPipelineScheduler(05-19)의 계층 관리와 호환.
     - S3 4번째 계층 추가: `S3TierDescriptor(s3_endpoint, rdma_target, layer_delivery_order)` — ObjectCache 프로토콜 확장 디스크립터.
     - 계층 퇴거 우선순위: HBM → DRAM → SSD → S3 단방향 하향 흐름 (S3에서 HBM으로 직접 상향 가능, RDMA 레이어와이즈).
  6. **이전 A 기법과의 차별점**:
     - KVDriveAttentionPipelineScheduler(05-19 A-1): GPU/DRAM/SSD 3-티어 I/O-컴퓨트 오버랩 파이프라인 (S3 없음).
     - KaretoStorageTuner(05-23 A-1): 3-티어 구성 파레토 최적화 (S3 계층 없음).
     - DualPathNICLoadBalancer(05-24 A-1): 스토리지 NIC 이중 경로 (S3 없음, decode NIC 중계).
     - ObjectCacheS3TierRouter: **S3 오브젝트 스토리지를 4번째 계층으로 추가하고 브레이크이븐 히트율 계산으로 동적 티어 전환 결정 — 레이어와이즈 RDMA 전달 지연과 재계산 비용의 정량적 균형을 실시간으로 계산하는 기법이 이전 어느 A 기법에도 없었다.**
- **대상 환경**: 멀티 노드 (S3 오브젝트 스토리지 접근 가능한 100 Gbps RoCE 또는 InfiniBand 환경)
- **멀티 노드 고려사항**: ObjectCache 원논문의 RoCE 100 Gbps 환경 가정. S3 서버(Ceph RGW/DAOS/MinIO)를 KV 스토리지 노드로 구성하고 RDMA 직접 전달로 추가 노드 없이 GPU로 전달. `rdma_target`을 요청별 GPU 노드 ID로 동적 설정해 특정 노드에 S3 전달이 집중되지 않도록 분산. 브레이크이븐 테이블을 클러스터 네트워크 토폴로지별로 사전 계산(`objectcache_breakeven_calibration.py`).
- **예상 효과**: 유효 컨텍스트 길이 2~10× (S3 용량 무제한 이론), KV 캐시 메모리 절감 −90% (HBM/DRAM/SSD 오버플로우를 S3로 전환), Scheduling overhead TTFT +5~6% (64K 컨텍스트, ObjectCache 원논문 5.6% 기준 + 브레이크이븐 로직 < 0.01ms), 히트율 ≥ 브레이크이븐 환경에서 처리량 +20~50%
- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 A-2: ObjectCacheDualPathThreeHopLayerwiseRDMARouter (ObjectCache + DualPath S3→Decode→Prefill 3-홉 레이어와이즈 RDMA 라우터)
- **가설**: ObjectCache(2605.22850)의 "S3→GPU 레이어와이즈 RDMA" 2-홉 경로와 DualPath(2602.21548, 이미 보고)의 "저장소→decode→prefill RDMA" 이중 경로를 결합하면, "S3→decode 노드(유휴 스토리지 NIC) → prefill 노드" 3-홉 경로에서 ObjectCache의 레이어와이즈 페이로드 조합이 DualPath의 NIC 비대칭 활용과 결합되어, S3 용량(ObjectCache) × NIC 이중 경로 대역폭(DualPath)의 복합 효과로 원격 KV 전달 처리량을 향상시킬 수 있다. DualPathNICLoadBalancer(05-24 A-1)는 2-홉(스토리지→decode→prefill)에서 로컬 DRAM/SSD를 소스로 사용했으며, S3 오브젝트 스토리지를 소스로 하는 3-홉 레이어와이즈 전달은 새로운 조합이다.
- **접근 방법**:
  1. `ObjectCacheDualPathThreeHopRouter` 클래스 (`src/scheduler/objectcache_dualpath_3hop_router.py`): `BaseScheduler` 상속, `DualPathNICLoadBalancer` 상속·확장
  2. **3-홉 경로 결정 로직**:
     - **조건**: prefill 노드 스토리지 NIC 포화(≥80%) AND S3 티어 활성화(A-1 ObjectCacheS3TierRouter 기준 충족) AND idle decode 노드 존재.
     - **3-홉 경로 실행**:
       - Hop 1: S3 서버 → decode 노드 (ObjectCache 레이어와이즈 RDMA 페이로드 조합, 스토리지 NIC 사용).
       - Hop 2: decode 노드 → prefill 노드 (컴퓨트 NIC RDMA, DualPath 원칙).
       - ObjectCache 레이어와이즈 조합: decode 노드에서 S3의 레이어별 청크를 조합해 GPU-소비 순서로 재정렬 후 prefill 노드로 전달.
     - **2-홉 경로 (fallback)**: decode 노드 idle 없음 → A-1의 S3→prefill 직접 2-홉.
     - **1-홉 경로 (fallback)**: S3 티어 비활성화 → 기존 로컬 티어.
  3. **decode 노드 레이어 조합 오버헤드 최소화**:
     - decode 노드에서의 레이어 조합은 비동기 처리 (`asyncio` + zero-copy 메모리 매핑).
     - 조합 오버헤드 추정: 레이어 수 × 청크 포인터 재정렬 = < 1ms (포인터 조작만, 데이터 복사 없음).
  4. **이전 A-2 기법과의 차별점**:
     - DualPathNICLoadBalancer(05-24 A-1): 로컬 DRAM/SSD 소스 2-홉 (S3 없음).
     - ObjectCacheDualPath3HopRouter: S3 소스 → decode 경유 → prefill의 3-홉으로 S3 용량 × DualPath 대역폭 결합. decode 노드에서 ObjectCache 레이어와이즈 페이로드 조합 수행이 새로운 역할.
- **대상 환경**: 멀티 노드 (P/D 분리 + S3 스토리지 노드 포함)
- **멀티 노드 고려사항**: S3 서버 — decode 노드 간 스토리지 네트워크(100 Gbps RoCE)와 decode — prefill 간 컴퓨트 네트워크(InfiniBand 200 Gbps) 물리적 분리 가정. decode 노드당 동시 3-홉 처리 수 상한: `max_3hop_per_decode_node`(기본 2).
- **예상 효과**: S3 전달 처리량 +60~100% (NIC 비대칭 활용 + 이중 경로, DualPath 1.87~1.96× 기반), Scheduling overhead TTFT +3~5% 이내 (decode 조합 < 1ms + 3-홉 추가 지연 < S3 직접 전달)
- **구현 난이도**: medium
- **우선순위**: 3

### 아이디어 B-1: IrminsulMLANativeDeltaRotationArchAwareNonContiguousRouter (Irminsul MLA-네이티브 δ-회전 아키텍처-인식 비연속 재사용 라우터)

  1. `IrminsulMLASegmentCache` 클래스 (`src/cache/irminsul_mla_segment_cache.py`): `CacheStore` 인터페이스 구현
  2. `ArchitectureAwareNonContiguousRouter` 클래스 (`src/cache/arch_aware_noncontiguous_router.py`): MLA vs GQA/MHA 분기 라우터
  3. **모델 아키텍처 감지 (Architecture Detection)**:
     - `detect_attention_arch(model_config) → {"MLA", "GQA", "MHA"}`.
     - MLA 감지 조건: `model_config`에 `kv_lora_rank`, `qk_rope_head_dim`(= 64, k_r 차원) 필드 존재.
     - 아키텍처 레지스트리: `configs/arch_registry.yaml` — 지원 모델 목록 + 아키텍처 유형.
  4. **CDC 청킹 + 콘텐츠-해시 키잉 (Irminsul 원칙)**:
     - 세그먼트 분할: CDC(Content-Defined Chunking) — Rabin 핑거프린트로 내용 기반 경계 탐지. 평균 청크 크기: `avg_chunk_size`(기본 256 토큰) YAML 외부화.
     - 세그먼트 키 생성: `segment_key = SHA256(token_content_bytes)` — 절대 위치와 무관.
     - 저장: `IrminsulKVEntry(segment_key, c_kv_tensor, k_r_tensor, source_position)`.
  5. **MLA 경로 — δ-회전 위치 수정 (MLA Path)**:
     - 세그먼트 재사용 시 위치 오프셋 계산: `δ = target_position - source_position`.
     - k_r 수정: `k_r_corrected = RoPE(k_r, δ)` — 단일 δ-회전 행렬 적용.
     - 수식: `k_r_corrected[i] = k_r[i] × cos(δ × θ_i) - k_r_perp[i] × sin(δ × θ_i)` (θ_i: RoPE 주파수, k_r_perp: 직교 성분).
     - c_KV는 위치-자유이므로 수정 불필요 — δ-회전은 k_r(64-dim)에만 적용.
     - 오버헤드: 64-dim × n_layers 행렬 조작 → < 0.1ms/세그먼트.
  6. **GQA/MHA 경로 — 기존 AdapShot RoPE 재인코딩 (GQA/MHA Path)**:
     - `AdapShotRoPEReencoder`(05-18 기구현)를 그대로 사용.
     - 위치 불일치 크기에 따라 CLCPositionalBiasGatedSegmentReuse(05-23)의 게이트로 재인코딩 여부 결정(선택적 오버헤드).
  7. **통합 라우팅 결정**:
     ```python
     def get(segment_key, target_position):
         arch = detect_attention_arch(model_config)
         if arch == "MLA":
             return IrminsulMLASegmentCache.get_with_delta_rotation(segment_key, target_position)
         else:  # GQA/MHA
             return AdapShotRoPEReencoder.get_with_reencoding(segment_key, target_position)
     ```
  8. **이전 B 기법과의 차별점**:
     - CLCPositionalBiasGatedSegmentReuse(05-23 B-1): 위치 편향 임계 게이트 기반 선택적 재인코딩 (GQA/MHA, 편향 크기 측정).
     - KVPacketAdapterZeroFLOPs(05-25 B-1): 소프트-토큰 어댑터 증류로 컨텍스트 불연속성 흡수 (아키텍처 무관, 훈련 필요).
     - IrminsulMLASegmentCache: **MLA 아키텍처의 c_KV/k_r 구조적 분리를 활용한 무훈련 수학적 δ-회전 위치 수정 — GQA/MHA 기법과 완전히 다른 MLA 전용 경로, 훈련 없이 수학적 보장.**
- **예상 효과**: 비연속 히트율 +77.2~82.7% (Irminsul 원논문 추가 회수율, 에이전틱 세션), TTFT −30~50% (재인코딩 오버헤드 없는 δ-회전만 적용), MLA 모델 63% 프리필 에너지 절감 (Irminsul 원논문 기준)
- **구현 난이도**: medium

### 아이디어 B-2: CDCContentHashUnifiedSegmentIDInterfaceForIrminsulObjectCache (CDC 콘텐츠 해시 통합 세그먼트 ID 인터페이스 — Irminsul + ObjectCache 주소 체계 통일)
- **가설**: Irminsul(2605.05696)의 CDC 청킹 + 콘텐츠-해시 키잉과 ObjectCache(2605.22850)의 S3 해시-주소화 청크 스토리지가 동일한 기본 추상화(CDC 청크 + SHA256 콘텐츠 해시)를 공유한다는 구조적 일치를, `src/cache/segmented.py`의 세그먼트 키 체계를 "세그먼트 ID = CDC 청크의 SHA256 콘텐츠 해시"로 통일하면, Irminsul의 위치-독립 세그먼트 인덱스가 자연스럽게 ObjectCache의 S3 오브젝트 키가 되어 — 인덱스 변환 없이 Irminsul이 발견한 재사용 가능 세그먼트를 ObjectCache가 S3에서 직접 로드하는 통합 파이프라인 — 을 구현할 수 있다. 이전 B 기법 전체는 로컬 메모리(HBM/DRAM/SSD) 내 세그먼트 주소 체계를 사용했으며, S3 원격 스토리지와 통합된 통일 세그먼트 ID 인터페이스를 설계한 기법이 없었다.
- **접근 방법**:
  1. `CDCContentHashSegmentIDInterface` 모듈 (`src/cache/cdc_content_hash_interface.py`)
  2. **통일 세그먼트 ID 규격**:
     - `SegmentID = SHA256(CDC_chunk_token_bytes)` — 32바이트 해시.
     - `SegmentMetadata(segment_id, source_position, n_tokens, model_arch, storage_tier)`.
     - `storage_tier ∈ {"HBM", "DRAM", "SSD", "S3"}` — 계층 정보 포함.
  3. **Irminsul 인덱서 → ObjectCache 키 직접 매핑**:
     - Irminsul 세그먼트 발견: `IrminsulMLASegmentCache.find(session_tokens) → List[SegmentID]`.
     - ObjectCache S3 조회: `ObjectCache.get(segment_id: SegmentID)` — 동일 segment_id로 S3 오브젝트 직접 참조.
     - 캐시 계층 워터폴: HBM 히트 → DRAM 히트 → SSD 히트 → S3 원격 조회 → 재계산.
  4. **S3 오브젝트 저장 형식**:
     - S3 키: `f"{model_name}/{segment_id.hex()}.kvcache"` — 모델별 네임스페이스 분리.
     - S3 오브젝트 내용: `{c_kv_tensor(FP16, 레이어별), k_r_tensor(FP16, MLA only), n_tokens, model_arch}` — MessagePack 직렬화.
  5. **캐시 일관성 보장**:
     - 세그먼트 ID가 콘텐츠 해시이므로 동일 내용 = 동일 ID → 자동 중복 제거.
     - S3에 저장된 KV는 불변(immutable) — 토큰 내용이 변하지 않는 한 유효.
     - `segment_id` 충돌 확률: SHA256 → 2^{-256} 무시 가능.
  6. **이전 B 기법과의 차별점**:
     - BlockUnionNonContiguousReuseIndex(05-21 B-1): 비연속 PA 블록을 연속 블록 테이블로 변환하는 로컬 인덱스 (S3 없음).
     - CLCPositionalBiasGatedSegmentReuse(05-23 B-1): 로컬 세그먼트 해시 테이블 (S3 없음).
     - CDCContentHashSegmentIDInterface: **CDC 콘텐츠 해시를 통일 키로 사용해 로컬 인덱스(Irminsul)와 S3 원격 스토리지(ObjectCache)를 동일 주소 체계로 통합 — 계층 투명 세그먼트 접근이 이전 어느 B 기법에도 없었다.**
- **예상 효과**: 비연속 세그먼트 S3 히트 지원 (기존 로컬 계층만 지원하던 비연속 재사용을 원격 S3까지 확장), 구현 오버헤드 최소 (Irminsul과 ObjectCache의 기존 키 체계가 이미 SHA256 기반으로 통일)
- **구현 난이도**: low
- **우선순위**: 2

### 아이디어 C-1: IrminsulStochasticKVRoutingMLA2AxisCompressionCodec (Irminsul + Stochastic KV Routing MLA 2축 압축 코덱 — 위치 축 × 깊이 축)
- **가설**: Irminsul(2605.05696)의 MLA c_KV 위치-자유 공유(위치 축 절감)와 Stochastic KV Routing(2604.22782, 이미 보고)의 깊이 방향 크로스-레이어 c_KV 공유(깊이 축 절감)가 MLA 모델에서 직교하는 두 압축 차원이라는 통찰 — c_KV는 (1) 어느 위치에서도 재사용 가능하고(위치-자유), (2) 인접 레이어의 c_KV와 충분히 유사해 깊이 방향으로도 공유 가능 — 를 MLA 모델 전용 2축 압축 코덱으로 구현하면, 단독 적용 시의 메모리 절감을 곱연산으로 달성(위치 축 절감 × 깊이 축 절감)하면서 accuracy-preserving ±1% 이내를 유지할 수 있다. StochasticKVRoutingFinetuneCodec(05-25 C-3)이 아키텍처 무관 깊이 축 파인튜닝을 제안했다면, 이 기법은 MLA c_KV의 위치-자유성과 깊이 방향 공유를 동시에 활용하는 MLA 전용 2축 통합으로 이전 어느 C 기법과도 다른 접근이다.
- **접근 방법**:
  1. `MLATwoAxisCompressionCodec` 클래스 (`src/cache/mla_two_axis_compression_codec.py`): `CompressionCodec` 인터페이스 구현
  2. **위치 축 압축 (Position Axis — Irminsul 재사용 지분)**:
     - 에이전틱 세션에서 CDC 청크 단위로 c_KV를 저장.
     - 반복 청크 감지: `segment_id = SHA256(token_content)` 기반 히트 확인.
     - 히트된 청크는 c_KV를 저장하지 않고 포인터만 유지 (위치 축 중복 제거).
     - 위치 축 절감: 원논문 기준 에이전틱 세션에서 최대 48% 시프트 반복 토큰 → 위치 축 최대 48% c_KV 중복 제거.
  3. **깊이 축 압축 (Depth Axis — Stochastic KV Routing c_KV 레이어 공유)**:
     - 레이어 간 c_KV 유사도 측정: `cos_sim(c_kv[l], c_kv[l-1])` — 유사도 ≥ `depth_sharing_threshold`(기본 0.90)이면 레이어 l의 c_KV를 레이어 l-1과 공유.
     - 파인튜닝(선택적): StochasticKVRoutingFinetuneCodec(05-25 C-3)의 크로스-레이어 확률적 훈련 적용 → 깊이 방향 공유 내성 강화.
     - 파인튜닝 없이도 MLA 모델은 c_KV의 저랭크 잠재 구조로 인해 레이어 간 유사도가 높을 것으로 예상.
     - 깊이 축 절감: k=2 공유 시 50% 레이어 c_KV 절감.
  4. **2축 결합 메모리 절감**:
     - 결합 절감율: `total_reduction = (1 - position_axis_reduction) × (1 - depth_axis_reduction)`.
     - 예: 위치 축 30% 절감 × 깊이 축 50% 절감 = 총 65% 절감 (`0.7 × 0.5 = 0.35`, 즉 −65%).
     - MLA 모델 특화: c_KV에만 2축 적용, k_r(64-dim)은 δ-회전으로 수정 후 독립 유지.
  5. **accuracy-preserving 설계**:
     - 위치 축: c_KV는 위치-자유이므로 재사용 시 정확도 손실 없음 (Irminsul 수학적 보장).
     - 깊이 축: 유사도 임계값 0.90 이상에서만 공유 → 낮은 유사도 레이어는 독립 KV 유지.
     - 파인튜닝 적용 시 accuracy delta > 1% 시 `depth_sharing_threshold` 상향(0.90 → 0.95) 후 재적용 fallback.
  6. **이전 C 기법과의 차별점**:
     - StochasticKVRoutingFinetuneCodec(05-25 C-3): 아키텍처 무관 깊이 축 파인튜닝 (MLA 전용 아님, 위치 축 없음).
     - PredictiveMultiTierBayesianHeadLevelEMAEvictionCache(05-25 C-2): MLA-인식 크기 산정 + Bayesian 퇴거 (압축 아닌 퇴거 기반).
     - MLATwoAxisCompressionCodec: **MLA c_KV의 위치-자유성(Irminsul) + 깊이 방향 공유(Stochastic KV Routing)를 MLA 전용으로 통합한 2축 곱연산 압축 — MLA 아키텍처 특화 2축 설계가 이전 어느 C 기법에도 없었다.**
- **예상 효과**: 메모리 −50~70% (위치 축 30~48% + 깊이 축 50%, 곱연산), accuracy delta ±0.3~0.8% (위치 축 수학적 무손실 + 깊이 축 유사도 임계 기반)
- **accuracy-preserving 근거**:
  (1) 위치 축 c_KV 재사용: Irminsul(2605.05696)에서 MLA c_KV는 위치-자유이므로 재사용 시 정확도 손실이 수학적으로 없음. k_r 성분은 δ-회전으로 정확히 수정.
  (2) 깊이 축 c_KV 공유: 유사도 ≥ 0.90 임계값에서만 공유하므로 레이어 표현력 손실 최소화. Stochastic KV Routing(2604.22782)에서 깊이 방향 공유가 다양한 모델 패밀리에서 ±1% 이내 accuracy를 실험적으로 검증.
  (3) 두 축의 결합이 독립적으로 작용: 위치 축은 세션 내 시간 차원에서 중복 제거, 깊이 축은 레이어 차원에서 중복 제거 — 서로 다른 차원이므로 오류 누적 없음.
  (4) Fallback: accuracy delta > 1% 감지 시 `depth_sharing_threshold` 자동 상향 + 파인튜닝 재적용으로 안전망 보장.
  검증: WikiText-2 perplexity ±1% + LongBench 8개 서브태스크 + MLA 모델(DeepSeek-V2-Lite, Kimi Moonlight-16B) 전용 + 위치 축 단독 / 깊이 축 단독 / 2축 결합 3-way 비교 + depth_sharing_threshold(0.85/0.90/0.95/1.0) 별 accuracy-memory 트레이드오프 + 에이전틱 세션 반복 토큰 비율별 위치 축 절감 측정.
- **구현 난이도**: medium

### 아이디어 Cross-2: IrminsulStochasticKVMLATwoAxisVeriCacheLosslessPipeline (B+C) — Irminsul MLA 2축 압축 + VeriCache 무손실 검증 파이프라인
- **조합 근거**: `MLATwoAxisCompressionCodec(C-1)`이 MLA 모델에서 위치 축(Irminsul) + 깊이 축(StochasticKV) 2축 동시 절감으로 c_KV 메모리를 50~70% 줄이면, `VeriCacheSpeculativeCodec(05-25 C-1, 기구현)`이 압축된 c_KV로 드래프팅하면서 전체 KV 검증으로 결정론적 accuracy 보장을 제공한다. 2축 압축 코덱을 VeriCache의 드래프트 코덱으로 플러그인하면 MLA 전용 압축-검증 파이프라인이 완성된다. C-1(MLA 2축 압축)이 VeriCache(05-25 기구현)의 드래프트 코덱 플러그인 인터페이스(`set_draft_codec`)를 통해 즉시 연동 가능하다는 점에서 구현 부담이 낮다.
- **구체 설계**:
  1. `MLATwoAxisVeriCachePipeline` 모듈 (`src/engine/mla_twoaxis_vericache_pipeline.py`)
  2. **통합 처리 흐름**:
     - **Step 1 (MLA 2축 압축, C-1)**: `MLATwoAxisCompressionCodec.compress(full_mla_kv)` → 위치 + 깊이 축 중복 제거 압축 c_KV.
     - **Step 2 (VeriCache 드래프팅, 05-25 C-1)**: 압축 c_KV로 드래프트 토큰 생성 (HBM 대역폭 바운드).
     - **Step 3 (전체 KV 비동기 prefetch)**: DRAM/SSD에서 전체 MLA KV 비동기 로드 (PCIe/RDMA 바운드).
     - **Step 4 (VeriCache 검증)**: 드래프트 토큰을 전체 KV로 검증 → 결정론적 accuracy 보장.
  3. **MLA c_KV 드래프트 수락률 예측**:
     - 위치 축 중복 제거된 c_KV(정확 재사용)의 드래프트 수락률은 VeriCache 일반 압축 코덱보다 높을 것으로 예상 — c_KV 위치-자유성이 드래프팅 정확도 향상.
- **예상 복합 효과**: 처리량 +80~150% (2축 압축으로 드래프팅 속도 향상 + VeriCache 수락률 증가), 메모리 −70~85% (2축 압축 + 전체 KV 오프로딩), accuracy delta ±0.0% (VeriCache 결정론적 보장)
- **구현 난이도**: low (VeriCache 기구현 + MLATwoAxisCompressionCodec 신규 = 플러그인 연결만)
- **우선순위**: 2

### 아이디어 Cross-3: ObjectCacheIrminsulVeriCacheMLAAgenticFullPipeline (A+B+C) — ObjectCache S3 + Irminsul MLA-PIC + VeriCache 무손실 + 2축 압축 에이전틱 통합 파이프라인
- **조합 근거**: 오늘 트렌드 리포트(2026-05-26)의 A+B+C 3-way 시너지: (1) Irminsul(B)이 에이전틱 세션의 CDC 청크를 콘텐츠-해시로 인덱싱해 반복 청크 탐지, (2) ObjectCache(A)가 S3의 해당 MLA KV 청크를 레이어와이즈 RDMA로 GPU에 전달, (3) Irminsul(B)이 δ-회전으로 k_r 위치 수정 → 재사용, (4) MLATwoAxisCompressionCodec(C-1)이 위치 + 깊이 축 2축 c_KV 압축, (5) VeriCache(C, 05-25 기구현)가 압축 KV로 드래프팅 + 전체 KV 검증. 이 파이프라인이 MLA 에이전틱 서빙에서 A(원격 KV 오케스트레이션) + B(위치-독립 재사용) + C(다층 압축 보장) 세 Activity의 완전한 통합을 실현하는 최초의 구체적 구현 경로다.
- **구체 설계**:
  1. `MLAAgenticKVFullPipeline` 모듈 (`src/engine/mla_agentic_kv_full_pipeline.py`)
  2. **6단계 통합 처리 흐름** (트렌드 리포트 A+B+C 3-way 시너지 구체화):
     - **Step 1**: Irminsul CDC 청킹 + 콘텐츠-해시 세그먼트 감지 (B-1, B-2).
     - **Step 2**: ObjectCache S3 계층 조회 + 브레이크이븐 라우팅 결정 (A-1).
     - **Step 3**: S3→GPU 레이어와이즈 RDMA 전달 (A-1, ObjectCache 원논문).
     - **Step 4**: Irminsul δ-회전 k_r 위치 수정 + c_KV 재사용 (B-1).
     - **Step 5**: MLATwoAxisCompressionCodec 2축 c_KV 압축 (C-1, 깊이 축 추가 절감).
     - **Step 6**: VeriCache 압축 KV 드래프팅 + 전체 KV 비동기 RDMA 검증 (05-25 C-1).
  3. **배치 처리 통합**:
     - Step 1~4는 요청별 (세그먼트 단위).
     - Step 5~6은 배치 단위 (배치 내 전체 요청의 압축 KV를 병렬 드래프팅).
     - ObjectCache 레이어와이즈 오버랩: Step 3 레이어 N 전달 중 Step 4~5 레이어 N-1 처리 파이프라인.
- **예상 복합 효과**: 처리량 +100~200% (S3 용량 × 비연속 재사용 × 2축 압축 × VeriCache 드래프팅 복합), 메모리 −80~95% (S3 오프로딩 + 2축 압축), 비연속 히트율 +60~80% (에이전틱 세션 전체 최적화), accuracy delta ±0.0% (VeriCache 결정론적 보장 + δ-회전 수학적 정확성)
- **구현 난이도**: high
- **우선순위**: 3

## planner에게 전달할 요청사항

1. **Activity B 구현 시 MLA 아키텍처 감지 필수**:
   - B-1 (IrminsulMLASegmentCache): `detect_attention_arch(model_config)` 함수로 MLA 여부 확인 필수. MLA 감지 기준: `model_config`에 `kv_lora_rank` 및 `qk_rope_head_dim=64` 필드 존재. 감지 실패 시 기존 GQA/MHA 경로(AdapShot RoPE 재인코딩)로 자동 fallback.
   - CDC 청킹 파라미터: Rabin 핑거프린트 기반, 평균 청크 크기 256 토큰, YAML 외부화 필수.
   - δ-회전 정확성 검증: `assert_delta_rotation_correctness()` 단위 테스트 필수 — 위치 오프셋 δ를 적용한 k_r이 원래 위치에서 직접 계산한 k_r과 수학적으로 일치하는지 확인.

2. **Activity A 구현 시 브레이크이븐 테이블 사전 보정 필수**:
   - A-1 (ObjectCacheS3TierRouter): `objectcache_breakeven_calibration.py` 스크립트로 컨텍스트 길이별 T_s3, T_recompute를 측정해 `configs/objectcache_breakeven_table.yaml` 생성. 실제 클러스터 네트워크 환경에서 보정 필수.
   - S3 접근 없는 환경에서는 브레이크이븐 테이블 모의 값 사용 가능 (테스트 모드).

3. **Activity C 구현 시 accuracy-preserving 검증 방법 명시 필수**:
   - C-1 (MLATwoAxisCompressionCodec): WikiText-2 perplexity ±1% + LongBench 8개 서브태스크 + MLA 모델 전용(DeepSeek-V2-Lite 또는 동등 모델). 위치 축 단독 / 깊이 축 단독 / 2축 결합 3-way 비교 필수. `depth_sharing_threshold` 파라미터(0.85/0.90/0.95) 스윕.

4. **이번 사이클 측정 지표**:
   - Non-Contiguous Cache Hit Rate: B-1 Irminsul δ-회전으로 +77.2~82.7% 추가 회수 → 전체 히트율 30% 이상 목표 달성 여부 검증.
   - Effective Context Length: A-1 ObjectCache S3 4번째 계층으로 2× 이상 목표 달성 여부 검증.
   - Scheduling Overhead: A-1 TTFT p50 +5% 이내 (ObjectCache 5.6% 기준 + 브레이크이븐 로직 < 0.01ms).
   - KV Cache Memory Reduction: C-1 MLA 2축 압축으로 −50~70% 목표.
   - Compression Accuracy Delta: C-1 ±0.3~0.8% — ±1% 이내 검증 필수.

5. **구현 우선순위**: B-1 → A-1 → B-2 → Cross-1 → C-1 → Cross-2 → A-2 → Cross-3 순서.

6. **B-1 (IrminsulMLASegmentCache) 구현 시**: `src/cache/irminsul_mla_segment_cache.py` + `src/cache/arch_aware_noncontiguous_router.py` 신규 생성. `CacheStore` 인터페이스 구현. CDC 청킹: `cdc_chunk(tokens, avg_chunk_size=256)` 함수. δ-회전: `apply_delta_rotation(k_r_tensor, delta, rope_freqs)` 함수. SGLang Irminsul 구현체 참조 가능: arXiv 2605.05696 Appendix.
