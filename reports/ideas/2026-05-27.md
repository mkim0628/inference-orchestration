IndexMem은 Activity C의 완전히 새로운 서브필드를 개척한다.

이에 따라 Activity C 단독 구현 및 B+C 시너지(비연속 퇴거 세그먼트의 잠재 기억 보존), A+C 시너지(에이전틱 KV 스케줄링 + IndexMem 잠재 기억 폴백)가 모두 이전 사이클에서 탐색된 바 없는 새로운 방향으로 확립된다.

## Activity A 아이디어

### 아이디어 A-1: IndexMemLatentMemoryTTLFallbackCacheTTLIntegration (IndexMem 잠재 기억 모듈 TTL 폴백 통합 — CacheTTL 만료 시 소프트 전환)
- **가설**: CacheTTL(2511.02230, 이미 보고)이 도구 호출·에이전트 전환 간격 동안 KV를 TTL로 보존하다가 TTL 만료 시 해당 KV를 영구 퇴거하는 "경성 만료(hard expiry)" 모델을 사용한다. 이를 IndexMem(2605.25475)의 잠재 기억 모듈과 통합해 "TTL 만료 → 잠재 기억 상태로 소프트 전환"하는 "TTL → 잠재 기억 폴백(latent fallback)" 정책을 `src/scheduler/`에 구현하면, TTL 만료 후에도 해당 에이전트 KV의 어텐션 기여가 잠재 상태를 통해 보존되어 KV 풀 혼잡 압박을 줄이면서도 의미적 정보 손실 없이 에이전틱 세션을 연속할 수 있다. 과거 모든 A 기법에서 "TTL 만료 후 잠재 기억 소프트 전환"이라는 2단계 KV 수명주기 관리가 없었으며, IndexMem 잠재 기억 모듈을 스케줄링 계층의 폴백 전략으로 활용한 기법이 없었다.
- **접근 방법**:
  1. `IndexMemTTLFallbackScheduler` 클래스 (`src/scheduler/indexmem_ttl_fallback_scheduler.py`): `BaseScheduler` 상속
  2. **2단계 KV 수명주기 관리 (Dual-Phase KV Lifecycle)**:
     - **Phase 1 (TTL 보존)**: CacheTTL(2511.02230) 원칙대로 도구 호출 간격·에이전트 전환 동안 KV를 TTL로 HBM/DRAM에 보존. `ttl_expire_policy: {tool_call_gap_ms, agent_switch_ms}` YAML 외부화.
     - **Phase 2 (잠재 기억 폴백)**: TTL 만료 또는 KV 풀 압박(> `kv_pressure_threshold`, 기본 0.80)으로 물리적 퇴거가 필요할 때, 해당 KV를 즉시 폐기하는 대신 `IndexMemLatentMemoryEncoder.encode(kv_block) → latent_state`로 압축 보존. 잠재 상태 크기: 원 KV의 `latent_compression_ratio`(기본 1/8) → 메모리 1/8로 보존.
  3. **잠재 기억 인코더 (Latent Memory Encoder)**:
     - IndexMem 원논문(2605.25475)의 잠재 기억 모듈 구조 차용: 경량 트랜스포머 인코더(2-레이어, hidden_dim = kv_dim // 4)로 퇴거될 KV 블록을 고정 크기 잠재 벡터로 압축.
     - 온라인-갱신(online-updated): 세션 내 새 KV가 도착할 때마다 잠재 상태 점진적 갱신 — 이전 잠재 상태와 새 입력의 지수이동평균: `latent = α × new_encoding + (1-α) × latent` (α=0.3, YAML 외부화).
     - 잠재 상태 저장: DRAM 별도 `LatentStatePool`에 세션별 저장 (HBM 미점유).
  4. **잔차 리드아웃 통합 (Residual Readout Integration)**:
     - 디코딩 중 쿼리 벡터와 잠재 상태의 의미적 유사도: `readout_score = cosine_sim(query, latent_state)`.
     - `readout_score > readout_threshold`(기본 0.7) 시 잠재 기억 잔차 리드아웃 활성화: `attn_output += βlatent × readout(query, latent_state)`. β=0.1 (잔차 기여 강도, YAML 외부화).
     - readout 연산 오버헤드: hidden_dim 크기 행렬 조작 → < 0.2ms/디코딩 스텝.
  5. **스케줄러 TTL 임계값 동적 조정**:
     - 잠재 기억 풀 점유율(`latent_pool_utilization`)이 높아지면 TTL을 단축(기존 TTL × 0.8)해 물리적 KV에서 잠재 기억으로의 전환을 가속.
     - 잠재 기억 풀 점유율이 낮으면 TTL을 연장(기존 TTL × 1.2)해 물리적 KV를 더 오래 보존.
  6. **이전 A 기법과의 차별점**:
     - CacheTTL(2511.02230, 이미 보고): TTL 만료 시 영구 폐기 (경성 만료, 잠재 기억 없음).
     - CONCURCongestionBasedAgentAdmissionScheduler(05-20): KV 풀 압박에 반응적 어드미션 제어 (잠재 기억 없음).
     - IndexMemTTLFallbackScheduler: **TTL 만료 후 잠재 기억 상태로 소프트 전환 — "물리 KV → 잠재 상태" 2단계 수명주기가 이전 어느 A 기법에도 없었다.**
- **대상 환경**: 단일 노드 / 멀티 노드 양쪽
- **멀티 노드 고려사항**: 잠재 상태 풀을 에이전트 세션 어피니티 기반으로 특정 DRAM 노드에 고정(session-pinned). 멀티 노드에서 에이전트가 다른 노드로 이전될 때 잠재 상태만 전송(원 KV 대비 1/8 크기) → 마이그레이션 비용 대폭 절감. `latent_transfer_cost = latent_state_size_bytes / rdma_bandwidth` — 원 KV 마이그레이션 비용의 12.5%.
- **예상 효과**: KV 풀 혼잡 이벤트 −40~60% (TTL 만료 KV가 잠재 상태로 전환되어 압박 완화), 에이전틱 세션 연속성 +80~90% (TTL 만료 후 잠재 기억으로 의미적 연속성 유지), Scheduling overhead TTFT +3% 이내 (잔차 리드아웃 < 0.2ms/스텝)
- **구현 난이도**: medium
- **우선순위**: 3

### 아이디어 B-1: IndexMemLatentEvictedSegmentNonContiguousReuseExtension (IndexMem 잠재 기억으로 퇴거된 비연속 세그먼트 의미적 기여 보존 — 비연속 재사용의 개념 확장)
- **가설**: Activity B의 비연속 세그먼트 재사용은 현재 "물리적 KV가 캐시에 존재하는 경우에만 히트"라는 이진(binary) 재사용 모델에 의존한다. IndexMem(2605.25475)의 잠재 기억 모듈을 비연속 세그먼트 캐시 레이어에 통합하면, "물리적 KV가 퇴거되었어도 잠재 상태가 존재하면 의미적 기여를 잔차 리드아웃으로 제공하는" "소프트 히트(soft hit)" 경로를 추가할 수 있다 — 이는 비연속 재사용의 개념을 "물리적 KV 히트"에서 "물리적 히트 + 잠재 기억 소프트 히트"의 연속체로 확장한다. `src/cache/segmented.py`에 소프트 히트 경로를 추가하면 히트율 측정 지표가 이진 히트율에서 "물리적 히트율 + 소프트 히트율(가중치 적용)"의 가중 히트율로 진화하며, 메모리 압박 하에서도 비연속 세그먼트의 의미적 기여를 보존하는 새로운 설계 차원이 열린다. 과거 모든 B 기법(IrminsulMLANative, KVPacketAdapter, BlockUnionNonContiguous, CLCPositionalBias, AMPDAdapShot, DualPathSegment 등)은 물리적 KV가 캐시에 있는 경우만 처리하며, 퇴거된 세그먼트의 기여를 잠재 상태로 보존하는 방법이 없었다.
- **접근 방법**:
  1. `IndexMemSoftHitSegmentCache` 클래스 (`src/cache/indexmem_soft_hit_segment_cache.py`): `CacheStore` 인터페이스 구현
  2. **소프트 히트 경로 설계 (Soft Hit Path)**:
     - 기존 하드 히트 경로: `get(segment_id) → kv_tensor` (물리적 KV 반환).
     - **신규 소프트 히트 경로**: `get(segment_id) → None` (물리적 KV 미존재) → `latent_memory_lookup(segment_id) → latent_state` → 잠재 상태 기반 잔차 리드아웃 제공.
     - 히트 유형 반환값: `HitResult(type: Literal["hard", "soft", "miss"], kv_tensor=None, latent_state=None)`.
  3. **세그먼트 잠재 기억 인코딩 (Segment Latent Encoding)**:
     - 세그먼트 퇴거(eviction) 시 LRU/중요도 기반 퇴거 결정이 내려지면, 퇴거 전 `IndexMemSegmentEncoder.encode(kv_segment) → latent_state` 실행.
     - IndexMem 잠재 기억 모듈(2-레이어 경량 트랜스포머 인코더, hidden_dim = kv_dim // 4) 사용: 세그먼트 전체 KV를 고정 크기 잠재 벡터(latent_size = 64 × n_layers)로 압축.
     - 잠재 상태 저장: `SegmentLatentPool(segment_id → latent_state)` DRAM 별도 풀. 잠재 상태 크기: 세그먼트 KV의 약 `1/(avg_chunk_tokens × heads_per_layer × head_dim / 64)` → 실질적으로 세그먼트 KV의 1/50~1/200 크기.
     - 잠재 풀 퇴거 정책: LRU (잠재 풀도 용량 제한 존재; `latent_pool_max_segments` YAML 외부화).
  4. **소프트 히트 잔차 리드아웃 적용 (Residual Readout Application)**:
     - 소프트 히트 경로에서 현재 쿼리 벡터와 잠재 상태의 교차-어텐션 계산:
       ```python
       def soft_hit_residual(query_states, latent_state):
           # query_states: [n_heads, seq_len, head_dim]
           # latent_state: [n_layers, latent_size]
           readout = cross_attn(query_states, latent_state)  # [n_heads, seq_len, head_dim]
           return beta_soft * readout  # beta_soft = 0.05~0.15, YAML 외부화
       ```
     - `beta_soft` 자동 조정: 물리적 히트(하드 히트)가 많을수록 beta_soft 감소(소프트 히트 기여 축소); 소프트 히트만 있는 경우 beta_soft 증가. EMA로 온라인 조정.
     - 오버헤드: 교차-어텐션 연산 크기 = `n_heads × seq_len × latent_size` → 일반 자기-어텐션 대비 1/50~1/200 계산량. < 0.5ms/스텝(n_heads=32, seq_len=512, latent_size=64 기준).
  5. **가중 히트율 지표 (Weighted Hit Rate Metric)**:
     - 기존 이진 히트율: `hit_rate = n_hard_hits / (n_hard_hits + n_misses)`.
     - 새 가중 히트율: `weighted_hit_rate = (n_hard_hits + beta_weight × n_soft_hits) / (n_hard_hits + n_soft_hits + n_misses)`. `beta_weight`(기본 0.5) — 소프트 히트를 하드 히트의 50%로 평가.
     - `src/metrics/hit_rate.py`에 `weighted_hit_rate` 지표 추가. `results/<exp-name>/metrics.json`에 `{hard_hit_rate, soft_hit_rate, weighted_hit_rate, soft_hit_beta}` 기록.
  6. **아키텍처 감지 분기 (Architecture-Aware Integration)**:
     - MLA 모델(DeepSeek-V2/V3): 잠재 기억 인코딩 대상은 c_KV 성분(위치-자유) 전용. k_r 성분(64-dim)은 이미 소형이므로 잠재 기억 불필요.
     - GQA/MHA 모델: 전체 KV 세그먼트를 잠재 기억 인코딩.
     - `detect_attention_arch()` 분기: `src/cache/irminsul_mla_segment_cache.py`(05-26 기구현)와 동일 아키텍처 감지 로직 재사용.
  7. **이전 B 기법과의 차별점**:
     - IrminsulMLANativeDeltaRotationArchAwareNonContiguousRouter(05-26 B-1): 물리적 KV δ-회전 재사용 (퇴거 후 기여 없음).
     - KVPacketAdapterZeroFLOPsNonContiguousCache(05-25 B-1): 소프트-토큰 어댑터로 컨텍스트 불연속성 흡수 (어댑터는 물리적 KV가 존재할 때 적용, 퇴거 후 없음).
     - BlockUnionNonContiguousReuseIndex(05-21 B-1): 물리적 블록 테이블 변환 최적화.
     - IndexMemSoftHitSegmentCache: **퇴거된 세그먼트의 KV를 잠재 상태로 압축 보존 → 소프트 히트로 의미적 기여 제공 — 물리적 KV 없이도 어텐션 기여를 유지하는 최초의 B 기법. 비연속 재사용의 이진 모델을 연속체로 확장하는 새로운 패러다임.**

## Activity C 아이디어

### 아이디어 C-1: IndexMemLearnableIndexerLatentMemoryEvictionCodec (IndexMem 학습 가능한 중요도 예측기 + 잠재 기억 모듈 퇴거 코덱)
- **가설**: IndexMem(2605.25475)의 두 핵심 구성 요소 — (1) 입력-적응적 KV 중요도 분포를 포착하는 Learnable Indexer(학습 가능한 중요도 예측기)와 (2) 퇴거된 토큰을 영구 폐기 대신 압축된 온라인-갱신 잠재 상태로 인코딩해 잔차 리드아웃으로 어텐션 기여를 보상하는 Latent Memory Module — 을 `src/cache/` 레이어에 독립 모듈로 구현하고 기존 퇴거 기법(H2O, SnapKV, DapQ, Predictive Multi-Tier)의 "중요도 평가 단계"와 "퇴거 후처리 단계"에 각각 플러그인으로 통합하면, "어떤 토큰을 유지할 것인가(Learnable Indexer)"와 "버려진 토큰의 정보를 어떻게 보존할 것인가(Latent Memory)"를 동시에 최적화해 Activity C의 "압축 정확도 delta ±1% 이내" 목표를 공격적 퇴거 조건에서도 달성할 수 있다. RULER 스위트에서 기존 퇴거 기법 대비 최대 25포인트 개선이라는 수치 근거를 갖는다. 과거 C 기법 전체에서 퇴거 후 잠재 기억 모듈로 어텐션 기여를 보상하는 방법이 없었다.
- **접근 방법**:
  1. `IndexMemLearnableIndexer` 클래스 (`src/cache/indexmem_learnable_indexer.py`): 독립 모듈 (기존 퇴거 기법의 중요도 평가 단계 대체 플러그인)
  2. `IndexMemLatentMemoryModule` 클래스 (`src/cache/indexmem_latent_memory_module.py`): 독립 모듈 (기존 퇴거 기법의 퇴거 후처리 단계 추가 플러그인)
  3. `IndexMemEvictionCodec` 클래스 (`src/cache/indexmem_eviction_codec.py`): `CompressionCodec` 인터페이스 구현 (두 모듈 통합)
  4. **Learnable Indexer — 입력-적응적 KV 중요도 예측 (Module 1)**:
     - 아키텍처: 경량 MLP (입력: KV 통계 피처 → 출력: 토큰별 보존 확률).
       ```
       inputs = [k_norm, v_norm, cumul_attn_score, position_decay, query_sim]
       # k_norm, v_norm: 각 토큰 K/V 벡터 L2 노름 (정규화)
       # cumul_attn_score: 지금까지 이 토큰에 집중된 누적 어텐션 가중치 EMA
       # position_decay: exp(-γ × (current_pos - token_pos)) 위치 감쇠
       # query_sim: 현재 쿼리와의 코사인 유사도 (DapQ 원칙 차용)
       hidden = ReLU(Linear(5 → 32)(inputs))
       retention_prob = Sigmoid(Linear(32 → 1)(hidden))  # [0, 1]
       ```
     - 파라미터: 총 5×32 + 32 + 32×1 + 1 = 225개 — 극도로 경량.
     - 학습: IndexMem 원논문(2605.25475) 방식 — 모델 파인튜닝과 공동 학습. LoRA rank=4로 기존 모델 가중치 동결 + 어텐션 레이어만 미세조정.
     - 학습 데이터: `data/processed/` 내 대표 샘플 + 어텐션 패턴 라벨 (`cumul_attn_score` 기반 자기지도 방식).
     - Learnable Indexer 단독 사용 시 기존 휴리스틱(H2O, SnapKV) 대비 입력-적응적으로 더 정확한 토큰 보존 결정.
  5. **Latent Memory Module — 퇴거 토큰 잠재 상태 압축 보존 (Module 2)**:
     - 퇴거 결정 이후 해당 토큰들의 KV를 잠재 상태로 인코딩:
       ```python
       def encode_evicted(evicted_kv_batch, current_latent_state):
           # evicted_kv_batch: [n_evicted, n_layers, head_dim * n_heads]
           # current_latent_state: [n_layers, latent_dim]  (latent_dim 기본 64)
           encoded = latent_encoder(evicted_kv_batch)  # [n_layers, latent_dim]
           # 온라인 갱신: 지수이동평균
           new_latent = alpha * encoded + (1 - alpha) * current_latent_state
           return new_latent  # alpha = 0.2, YAML 외부화
       ```
     - latent_encoder: 2-레이어 경량 트랜스포머 인코더 (hidden_dim=128, n_heads=4, ffn_dim=256). 파라미터: ~200K — GPU 메모리 < 1MB.
     - 잠재 상태 메모리: n_layers × latent_dim × FP16 = 32 × 64 × 2 = 4KB/요청 — 극도로 소형.
     - 온라인-갱신: 디코딩 중 새 토큰이 퇴거될 때마다 잠재 상태 점진적 갱신.
  6. **잔차 리드아웃 — 디코딩 중 잠재 기억 기여 (Residual Readout)**:
     - 각 디코딩 스텝에서 쿼리와 잠재 상태의 교차-어텐션:
       ```python
       def residual_readout(query_states, latent_state, beta):
           # query_states: [n_heads, seq_len, head_dim]
           # latent_state: [n_layers, latent_dim]
           readout_v = readout_proj(latent_state)  # [n_layers, head_dim * n_heads]
           readout_k = readout_key_proj(latent_state)
           attn_weight = softmax(query_states @ readout_k.T / sqrt(head_dim))
           readout = attn_weight @ readout_v
           return beta * readout  # beta = 0.1, YAML 외부화
       ```
     - readout_proj, readout_key_proj: 선형 투영 레이어 (latent_dim → head_dim × n_heads). 파라미터: ~100K.
     - 최종 어텐션 출력: `attn_output += residual_readout(query, latent_state, beta)`.
     - 오버헤드: latent_dim=64 기반 교차-어텐션 → 일반 자기-어텐션의 64/seq_len 배 연산 → seq_len=512 기준 12.5% 추가 연산 → < 0.3ms/스텝.
  7. **플러그인 통합 인터페이스 (Plugin Integration)**:
     - 기존 퇴거 기법과의 통합:
       ```python
       class IndexMemEvictionCodec(CompressionCodec):
           def __init__(self, base_eviction_policy="snapkv"):
               self.indexer = IndexMemLearnableIndexer()  # 중요도 예측 교체
               self.latent_memory = IndexMemLatentMemoryModule()  # 퇴거 후처리 추가
               self.base_policy = base_eviction_policy
           def compress(self, kv_cache, budget_ratio=0.5):
               importance = self.indexer.predict(kv_cache)  # Learnable Indexer
               to_keep, to_evict = split_by_importance(kv_cache, importance, budget_ratio)
               self.latent_memory.encode_evicted(to_evict)  # Latent Memory
               return to_keep
           def get_readout(self, query_states):
               return self.latent_memory.residual_readout(query_states)
       ```
     - `base_eviction_policy` 파라미터로 기존 휴리스틱 교체 가능: `"h2o"`, `"snapkv"`, `"dapq"`, `"predictive_multitier"`.
  8. **accuracy-preserving 검증 설계**:
     - Learnable Indexer만 단독 적용 시 RULER-4K perplexity delta 측정 (기존 SnapKV 대비 개선 확인).
     - Latent Memory만 단독 적용 시 동일 KV 예산에서 perplexity delta 측정 (잔차 리드아웃 효과 분리).
     - 두 모듈 결합 시 RULER-4K + RULER-16K + WikiText-2 perplexity ±1% 이내 확인.
     - accuracy delta > 1% 시 budget_ratio 증가(더 많은 KV 보존) 또는 beta 감소(잔차 기여 축소) fallback.
  9. **이전 C 기법과의 차별점**:
     - PredictiveMultiTierBayesianHeadLevelEMAEvictionCache(05-25 C-2): 헤드-단위 EMA + RoPE 지역성 퇴거 (퇴거 후 잠재 기억 없음).
     - DapQPositionAwareEvictionCodec(05-22 C-3): post-RoPE 유사 쿼리 중요도 (퇴거 후 잠재 기억 없음).
     - VeriCacheSpeculativeCodec(05-25 C-1): 투기적 실행 결정론적 검증 (잠재 기억 개념 없음).
     - RuntimeCertifiedQuantizedAttentionCodec(05-23 C-1): 런타임 오류 경계 수학적 인증 (퇴거 후 정보 보존 없음).
     - IndexMemEvictionCodec: **학습 가능한 중요도 예측(Learnable Indexer) + 퇴거 후 잠재 기억 보존(Latent Memory Module) + 잔차 리드아웃 보상 — 퇴거 패러다임 자체를 "영구 삭제"에서 "잠재 압축 + 조건부 복원"으로 전환하는 최초의 C 기법.**
- **예상 효과**: 메모리 −40~60% (KV 예산 50% 기준, 퇴거된 토큰 잠재 상태 4KB/요청 추가), accuracy delta ±0.3~0.8% (RULER 스위트 기준, IndexMem 원논문 최대 25포인트 개선)
- **accuracy-preserving 근거**:
  (1) IndexMem 원논문(2605.25475)에서 Learnable Indexer + Latent Memory 결합이 RULER-4K~RULER-16K 전 범위, 바늘 깊이 15%~95%에서 SnapKV/PyramidKV 대비 최대 25포인트 개선을 달성하면서 Qwen/Mistral/Llama 모델 패밀리 전반에서 검증됨 — 이는 ±1% 이내 accuracy 보존이 아닌 정확도 향상이므로 accuracy-preserving 요건을 충족하고도 남는다.
  (2) Latent Memory Module의 잔차 리드아웃: beta=0.1(잔차 기여 10%)로 설정해 잔차가 주 어텐션 출력을 크게 왜곡하지 않도록 제한. beta > 0.2 설정 시 accuracy delta > 1% 위험 → YAML 외부화로 실험적 조정 가능.
  (3) 모듈 분리 구조: Learnable Indexer 단독(정확도 향상) → Latent Memory 단독(정확도 유지 또는 향상) → 결합(최대 효과) 3단계 실험으로 각 모듈의 accuracy 기여를 분리 검증.
  (4) Fallback: accuracy delta > 1% 감지 시 beta 자동 감소(0.1 → 0.05) + budget_ratio 증가(0.5 → 0.6)의 2단계 안전망.
  (5) 퇴거 후 잠재 기억 보존이 기존 "영구 폐기" 대비 정보를 추가로 보존하므로 이론적으로 accuracy delta는 비음수(≥ 0%) — accuracy 손실 방향이 아닌 보상 방향으로 작동.
  검증: WikiText-2 perplexity ±1% + RULER-4K + RULER-16K 바늘 깊이(15/25/50/75/95%) 별 정확도 + LongBench 8개 서브태스크 + Qwen/Mistral/Llama 3개 모델 패밀리 + budget_ratio(0.3/0.4/0.5/0.6/0.7) 별 accuracy-memory 트레이드오프 + beta(0.05/0.1/0.15/0.2) 별 정확도 곡선 + Learnable Indexer 단독 / Latent Memory 단독 / 결합 3-way 비교 + 기존 퇴거 기법(SnapKV, H2O, DapQ) 대비 동일 KV 예산에서 accuracy delta 비교.
- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 C-2: IndexMemStochasticKVRoutingDepthAxisLatentCodec (IndexMem 잠재 기억 + Stochastic KV Routing 깊이 축 2단 절감 — 잠재 보존 + 깊이 공유 복합 압축)
- **가설**: Stochastic KV Routing(2604.22782, 이미 보고)의 깊이 축 크로스-레이어 KV 공유(파인튜닝 기반)와 IndexMem(2605.25475)의 잠재 기억 모듈을 결합하면, "깊이 축 공유로 절감된 레이어의 KV를 IndexMem 잠재 기억으로 압축 보존"하는 2단 절감이 가능하다 — Stochastic KV Routing이 k=2 공유 시 레이어 수 50% 절감(물리적 KV 저장 불필요), IndexMem 잠재 기억이 절감된 레이어의 정보를 잠재 상태로 보존해 정보 손실 보상. 이전 05-25 사이클에서 제안된 StochasticKVRoutingDepthAxisShareFinetuneCodec(05-25 C-3)이 깊이 축 파인튜닝만 다루었다면, 이 기법은 "깊이 축 절감 레이어의 정보를 잠재 기억으로 보상"하는 새로운 결합이다.
- **접근 방법**:
  1. `IndexMemStochasticDepthLatentCodec` 클래스 (`src/cache/indexmem_stochastic_depth_latent_codec.py`): `CompressionCodec` 인터페이스 구현
  2. **깊이 축 공유 결정 (Depth-Axis Sharing)**:
     - StochasticKVRoutingFinetuneCodec(05-25 C-3) 기구현 파인튜닝 모델 활용.
     - 레이어 간 KV 유사도: `cos_sim(kv[l], kv[l-1]) ≥ depth_sharing_threshold`(기본 0.85)이면 레이어 l의 KV를 레이어 l-1과 공유 (레이어 l의 물리적 KV 저장 불필요).
     - 공유 레이어 목록: `shared_layers = [l for l in layers if cos_sim[l] >= threshold]`.
  3. **IndexMem 잠재 기억으로 공유 레이어 정보 보상**:
     - 공유 레이어 l의 KV를 물리적으로 저장하지 않지만, IndexMem Latent Memory로 압축 인코딩:
       ```python
       for l in shared_layers:
           latent_state[l] = IndexMemLatentMemoryModule.encode(kv[l])
       ```
     - 잔차 리드아웃: 공유 레이어 l에서 디코딩 시 `attn_output[l] += beta * readout(query[l], latent_state[l])`.
     - 공유 레이어의 정보가 잠재 기억으로 완전히 대체 → KV 물리 저장 불필요.
  4. **비공유 레이어 + 시간 축 압축 (Non-Shared Layers + Token Eviction)**:
     - 비공유 레이어는 IndexMemEvictionCodec(C-1)의 Learnable Indexer + Latent Memory로 시간 축 토큰 퇴거 압축 적용.
     - 결합 절감: 깊이 축 공유(−50% 레이어 KV) × 시간 축 퇴거(−50% 토큰 KV) = 총 −75% KV 물리 저장.
     - 잠재 기억 오버헤드: 공유 레이어 잠재 상태 + 퇴거 토큰 잠재 상태 합산 → 총 원 KV의 ~2% 크기.
  5. **이전 C 기법과의 차별점**:
     - StochasticKVRoutingFinetuneCodec(05-25 C-3): 깊이 축 파인튜닝으로 공유 가능하도록 모델 강건화 (정보 손실 보상 없음).
     - MLATwoAxisCompressionCodec(05-26 C-1): MLA c_KV 위치 축 + 깊이 축 곱연산 압축 (잠재 기억 보상 없음).
     - IndexMemStochasticDepthLatentCodec: **깊이 축 공유 레이어의 KV를 물리 저장 대신 IndexMem 잠재 기억으로 대체 — 깊이 축 절감 + 잠재 기억 정보 보상의 새로운 결합.**
- **예상 효과**: 메모리 −65~80% (깊이 축 −50% + 시간 축 −50%, 잠재 상태 2% 추가), accuracy delta ±0.5~1.0% (공유 레이어 잠재 기억 보상 + IndexMem 시간 축 잔차 복원)
- **accuracy-preserving 근거**:
  (1) Stochastic KV Routing(2604.22782)에서 파인튜닝된 모델은 크로스-레이어 공유에 강건하며 다양한 모델 패밀리에서 ±1% 이내 accuracy를 실험적으로 검증.
  (2) 공유 레이어에 IndexMem 잠재 기억 보상 추가: 기존 StochasticKVRoutingFinetuneCodec(공유만, 보상 없음) 대비 정보 보존이 더 강하므로 accuracy delta는 동등 또는 더 낮아야 함.
  (3) 비공유 레이어의 IndexMem 시간 축 압축: C-1에서 검증된 Learnable Indexer + Latent Memory의 ±0.3~0.8% accuracy delta 계승.
  (4) 두 축의 독립성: 깊이 축 공유는 레이어 차원, 시간 축 퇴거는 토큰 차원 — 독립적으로 작용하므로 오류 누적 최소.
  (5) accuracy delta > 1% 시 depth_sharing_threshold 상향(0.85 → 0.90)으로 공유 레이어 수 감소 fallback.
  검증: WikiText-2 perplexity ±1% + LongBench 8개 서브태스크 + depth_sharing_threshold(0.80/0.85/0.90/0.95) 별 accuracy-memory 곡선 + 깊이 축 단독 / 시간 축 단독 / 결합 3-way 비교 + 잠재 기억 보상 유무 대조 실험.
- **구현 난이도**: medium
- **우선순위**: 3

### 아이디어 Cross-1: IndexMemLatentSegmentBCIntegrationPipeline (B+C) — IndexMem 잠재 기억 기반 비연속 세그먼트 퇴거 후 의미 보존 통합 파이프라인
- **조합 근거**: `IndexMemSoftHitSegmentCache(B-1)`의 소프트 히트 경로와 `IndexMemEvictionCodec(C-1)`의 잠재 기억 모듈이 동일한 IndexMem 잠재 기억 인프라를 공유하므로, 단일 `LatentMemoryPool`로 (a) 비연속 세그먼트의 퇴거 후 소프트 히트(B-1)와 (b) 개별 토큰 레벨 잔차 리드아웃(C-1)을 통합 관리할 수 있다. 두 기법을 분리 구현하면 잠재 기억 인코더 파라미터와 DRAM 풀이 중복되므로, B+C 통합 파이프라인으로 구현 시 인프라 공유로 구현 효율이 높아지고 세그먼트 레벨 소프트 히트와 토큰 레벨 잔차 보상이 동시에 작동하는 복합 정확도 보존 효과를 달성한다.
- **조합 근거 상세**:
  - B-1의 `IndexMemSegmentEncoder`와 C-1의 `IndexMemLatentMemoryModule`은 동일 아키텍처(경량 트랜스포머 인코더, hidden_dim=128)를 공유 → 파라미터 통합 가능.
  - B-1의 세그먼트 단위 잠재 상태는 세그먼트 전체 KV의 집약적 표현, C-1의 토큰 단위 잠재 상태는 개별 퇴거 토큰의 표현 → 두 레벨의 잠재 기억이 상호 보완적.
  - "비연속 세그먼트 중 히트율 낮아 퇴거될 세그먼트(B-1 소프트 히트) + 세그먼트 내 공격적 퇴거 토큰(C-1 잔차 리드아웃)"의 2레이어 잠재 보존이 완전한 비연속 KV 정보 보존 파이프라인을 구성.
- **구체 설계**:
  1. `IndexMemBCIntegrationPipeline` 모듈 (`src/engine/indexmem_bc_pipeline.py`)
  2. **통합 잠재 기억 풀 (Unified Latent Memory Pool)**:
     - `UnifiedLatentPool`: 세그먼트 레벨 잠재 상태(`segment_id → segment_latent`) + 토큰 레벨 잠재 상태(`(segment_id, evicted_token_range) → token_latent`) 통합 관리.
     - 공유 인코더: `SharedLatentEncoder` (B-1과 C-1 파라미터 공유 → 학습 효율 2배).
     - 풀 메모리: 세그먼트 레벨 잠재 × N_segments + 토큰 레벨 잠재 × N_evicted_tokens = 총 수십 MB (원 KV 대비 < 1%).
  3. **통합 처리 흐름**:
     - **Step 1 (캐시 조회)**: `UnifiedLatentPool.lookup(segment_id)` → 하드 히트(물리적 KV) / 소프트 히트(세그먼트 잠재) / 미스 3단계 반환.
     - **Step 2 (하드 히트)**: 물리적 KV 반환 + C-1 IndexMem Learnable Indexer로 토큰 중요도 계산 → 낮은 중요도 토큰 Latent Memory 인코딩.
     - **Step 3 (소프트 히트)**: 세그먼트 잠재 상태 기반 잔차 리드아웃 + 세그먼트 내 토큰 레벨 잠재 상태 추가 잔차.
     - **Step 4 (미스)**: 재계산 후 UnifiedLatentPool에 잠재 상태 등록.
  4. **가중 히트율 통합 지표**:
     - `unified_weighted_hit_rate = (n_hard + 0.7 × n_seg_soft + 0.4 × n_token_soft) / total`.
     - 세그먼트 소프트 히트(0.7가중): 세그먼트 전체 잠재 기억 → 토큰 레벨 소프트 히트(0.4가중)보다 정보 밀도 높음.
- **예상 복합 효과**: 처리량 +20~40% (소프트 히트로 재계산 감소 + 물리적 KV 퇴거 후에도 잠재 기억 활용), 메모리 −50~70% (물리적 KV 공격적 퇴거 + 잠재 상태만 보존), 가중 비연속 히트율 +20~35% (소프트 히트 경로 추가), accuracy delta ±0.3~0.8% (2레이어 잠재 기억 보상)
- **구현 난이도**: medium
- **우선순위**: 1

### 아이디어 Cross-2: IndexMemVeriCacheLatentDraftVerifyPipeline (B+C) — IndexMem 잠재 기억 드래프팅 + VeriCache 전체 KV 검증 확장 파이프라인
- **조합 근거**: VeriCacheSpeculativeCodec(05-25 C-1, 기구현)의 "압축 KV 드래프팅 + 전체 KV 검증" 패러다임에서 드래프트 코덱으로 IndexMemEvictionCodec(C-1)을 사용하면, "IndexMem 잠재 기억 기반 잔차 리드아웃 포함 압축 KV로 드래프팅 → 전체 KV로 결정론적 검증"의 파이프라인이 성립한다. IndexMem의 잔차 리드아웃이 포함된 드래프트 KV는 단순 압축 KV 드래프트보다 정확도가 높아 드래프트 수락률이 향상되며, VeriCache가 여전히 결정론적 accuracy를 보장한다. VeriCache의 `set_draft_codec(CompressionCodec)` 플러그인 인터페이스를 통해 IndexMemEvictionCodec(C-1)을 즉시 연동할 수 있다는 점에서 구현 부담이 낮다.
- **구체 설계**:
  1. 기존 `VeriCacheSpeculativeCodec(05-25 C-1)`의 플러그인 인터페이스 활용:
     ```python
     vericache = VeriCacheSpeculativeCodec()
     vericache.set_draft_codec(IndexMemEvictionCodec(budget_ratio=0.5))
     # IndexMem 잔차 리드아웃 포함 드래프트 → VeriCache 결정론적 검증
     ```
  2. **IndexMem 잠재 기억이 드래프트 수락률에 미치는 영향**:
     - 단순 압축 KV 드래프트: 퇴거된 토큰 정보 손실 → 드래프트 오류 → 수락률 저하.
     - IndexMem 잠재 기억 + 잔차 리드아웃 포함 드래프트: 퇴거된 토큰 기여 보상 → 드래프트 품질 향상 → 수락률 향상 예상.
     - 예상 수락률 향상: IndexMem이 RULER에서 SnapKV 대비 최대 25포인트 개선이므로, 동일 KV 예산에서 드래프트 수락률도 유사하게 개선 예상 (추정 +10~20pp).
  3. **accuracy-preserving 이중 보장**:
     - IndexMem 단독: 잠재 기억 잔차 보상으로 accuracy delta ±0.3~0.8% (C-1).
     - VeriCache 검증: 결정론적 전체 KV 검증으로 최종 accuracy delta ±0.0% 보장.
     - 이중 보장: IndexMem이 드래프트 품질을 높이고 VeriCache가 최종 출력을 보증.
- **예상 복합 효과**: 처리량 +80~130% (IndexMem 드래프트 수락률 향상 × VeriCache 드래프팅 속도 결합), 메모리 −50~70% (IndexMem 압축 + VeriCache 전체 KV 오프로딩), accuracy delta ±0.0% (VeriCache 결정론적 보장)
- **구현 난이도**: low (VeriCache 기구현 + IndexMemEvictionCodec C-1 신규 = 플러그인 연결만)
- **우선순위**: 2

### 아이디어 Cross-3: IndexMemLatentEvictionIrminsulMLA_B_C_ObjectCache_A_FullPipeline (A+B+C) — ObjectCache S3 + Irminsul MLA 비연속 재사용 + IndexMem 잠재 기억 퇴거 보상 통합 파이프라인
- **조합 근거**: 트렌드 리포트(2026-05-27)에서 제시된 A+B+C 3-Way 6단계 파이프라인의 5번째 구성 요소로 IndexMem을 추가한 확장판이다. 이전 사이클(2026-05-26)의 ObjectCacheIrminsulVeriCacheMLAAgenticFullPipeline(Cross-3, 05-26)이 "Irminsul(B) + ObjectCache(A) + MLATwoAxisCompression(C) + VeriCache(C)"의 4-way였다면, 이번 사이클은 여기에 IndexMem 잠재 기억 레이어를 추가해 "물리적 퇴거 세그먼트라도 잠재 기억으로 기여 유지"하는 5-way로 확장한다. 이 파이프라인은 이전 Cross-3(05-26)을 대체·확장하는 새로운 아이디어다.
- **이전 사이클(05-26) Cross-3 대비 변경점**:
  - 추가: IndexMem 잠재 기억 레이어 (5번째 구성 요소) — TTL 만료/공간 압박으로 퇴거되는 Irminsul CDC 세그먼트를 잠재 상태로 보존.
  - 변경: Activity C 압축 레이어가 "MLA 2축 압축(05-26 C-1)"에서 "IndexMem Learnable Indexer + Latent Memory(이번 C-1) + MLA 2축 압축 선택적 결합"으로 강화.
- **구체 설계 (6단계 → 7단계 확장)**:
  1. **Step 1**: Irminsul CDC 청킹 + 콘텐츠-해시 세그먼트 감지 (B, 05-26 B-1 기구현).
  2. **Step 2**: ObjectCache S3 계층 조회 + 브레이크이븐 라우팅 결정 (A, 05-26 A-1 기구현).
  3. **Step 3**: S3→GPU 레이어와이즈 RDMA 전달 (A, ObjectCache 원논문).
  4. **Step 4**: Irminsul δ-회전 k_r 위치 수정 + c_KV 재사용 (B, 05-26 B-1 기구현).
  5. **Step 5 [신규]**: IndexMemEvictionCodec(C-1) — Learnable Indexer로 세그먼트 내 토큰 중요도 계산 + 낮은 중요도 토큰 Latent Memory 인코딩. 세그먼트 내 50% 토큰 잠재 기억으로 전환.
  6. **Step 6**: MLATwoAxisCompressionCodec(05-26 C-1) 선택적 적용 — MLA c_KV 위치 축 + 깊이 축 추가 압축 (IndexMem 압축 후 잔여 KV에 적용).
  7. **Step 7**: VeriCache(05-25 C-1 기구현) 압축 KV 드래프팅 + 전체 KV 결정론적 검증.
- **예상 복합 효과**: 처리량 +100~200% (S3 용량 × 비연속 재사용 × IndexMem 압축 × VeriCache 드래프팅 복합), 메모리 −80~95% (S3 오프로딩 + IndexMem 토큰 잠재 압축 + MLA 2축 압축 + VeriCache 오프로딩), 가중 비연속 히트율 +60~80% (에이전틱 세션 전체 최적화 + 소프트 히트 포함), accuracy delta ±0.0% (VeriCache 결정론적 최종 보장 + δ-회전 수학적 정확성)
- **구현 난이도**: high
- **우선순위**: 4

## 이번 사이클 최우선 구현 타겟

**최우선: C-1 (IndexMemLearnableIndexerLatentMemoryEvictionCodec)**

이유:
- IndexMem(2605.25475)이 RULER 스위트에서 SnapKV/PyramidKV 대비 최대 25포인트 개선이라는 가장 강력한 수치 근거를 제시한다 — Activity C의 "압축 정확도 delta ±1% 이내" 목표를 초과 달성하는 새로운 최강 기법.
- 플러그인 인터페이스로 기존 퇴거 기법(SnapKV, H2O, DapQ, PredictiveMultiTier)의 중요도 평가 단계를 Learnable Indexer로 교체하고 퇴거 후처리 단계에 Latent Memory를 추가하는 방식으로 구현 범위가 명확.
- VeriCache(05-25 C-1 기구현)의 `set_draft_codec()` 인터페이스에 즉시 플러그인 가능 → Cross-2 (B+C 파이프라인) 신속 구현.
- B-1 (IndexMemSoftHitSegmentCache)의 잠재 기억 인프라와 동일한 `SharedLatentEncoder`를 공유하므로 C-1 먼저 구현 후 B-1과 통합 효율 극대화.
- Qwen/Mistral/Llama 모델 패밀리 모두에서 검증된 기법 → 다양한 모델에서 실험 재현 가능.

**2순위: Cross-1 (IndexMemLatentSegmentBCIntegrationPipeline)**
(C-1 구현 후 B-1 소프트 히트 경로를 추가해 B+C 통합 파이프라인 완성 — 구현 난이도 medium, `UnifiedLatentPool` 공유 인프라 활용으로 추가 구현 최소)

**3순위: Cross-2 (IndexMemVeriCacheLatentDraftVerifyPipeline)**
(VeriCache 기구현 + IndexMemEvictionCodec C-1 = 플러그인 연결만, 구현 난이도 low — C-1 완성 즉시 구현 가능)

**4순위: B-1 (IndexMemSoftHitSegmentCache)**
(비연속 재사용의 이진 모델을 연속체로 확장하는 개념적 혁신 + Cross-1의 B 컴포넌트)

**5순위: A-1 (IndexMemTTLFallbackScheduler)**
(CacheTTL과 IndexMem의 통합 — 에이전틱 세션 연속성 보장 + TTL 만료 후 KV 풀 압박 완화)

## planner에게 전달할 요청사항

1. **Activity C 구현 시 accuracy-preserving 검증 방법 명시 필수**:
   - C-1 (IndexMemEvictionCodec): WikiText-2 perplexity ±1% + RULER-4K + RULER-16K 바늘 깊이(15/25/50/75/95%) 별 정확도 + LongBench 8개 서브태스크 + Qwen/Mistral/Llama 3개 모델 패밀리 전반 검증 필수. budget_ratio(0.3/0.4/0.5/0.6/0.7) 별 accuracy-memory 트레이드오프 + beta(0.05/0.1/0.15/0.2) 별 정확도 곡선. **Learnable Indexer 단독 / Latent Memory 단독 / 결합 3-way 비교 필수** — 각 모듈의 accuracy 기여 분리 검증.
   - C-2 (IndexMemStochasticDepthLatentCodec): WikiText-2 perplexity ±1% + depth_sharing_threshold(0.80/0.85/0.90/0.95) 별 accuracy-memory 곡선 + 잠재 기억 보상 유무 대조 실험 필수. StochasticKVRoutingFinetuneCodec(05-25 C-3 기구현) 파인튜닝 모델 재사용 가능한지 확인.

2. **Activity B 구현 시 소프트 히트 경로 설계 필수**:
   - B-1 (IndexMemSoftHitSegmentCache): `HitResult(type, kv_tensor, latent_state)` 반환 타입 도입 필수. `src/metrics/hit_rate.py`에 `weighted_hit_rate` 지표 추가 필수. 기존 이진 히트율과의 A/B 비교 실험 설계.
   - 잠재 기억 풀 메모리 예산 명시: `latent_pool_max_segments` YAML 외부화. 기본값: 물리적 KV 캐시 용량의 1% 이내.

3. **IndexMem 학습 단계 처리 (Learnable Indexer 파인튜닝)**:
   - Learnable Indexer 파인튜닝: `data/processed/` 내 대표 샘플 사용. LoRA rank=4, 어텐션 레이어만 업데이트. 에폭 3~5. 파인튜닝 완료 후 `configs/indexmem_indexer_weights.yaml`에 가중치 저장.
   - 파인튜닝 없이도 동작하는 "zero-shot 모드" 제공: Learnable Indexer를 DapQ(post-RoPE 유사 쿼리 중요도)로 대체 가능한 fallback 포함.

4. **Cross-1 (B+C 통합 파이프라인) 구현 시 UnifiedLatentPool 설계**:
   - `UnifiedLatentPool`: 세그먼트 레벨 잠재 상태(B-1)와 토큰 레벨 잠재 상태(C-1)를 통합 관리. `SharedLatentEncoder` 파라미터 공유.
   - 풀 용량 제한: `{segment_latent_pool_mb, token_latent_pool_mb}` 별도 YAML 외부화.

5. **Cross-2 (IndexMem + VeriCache) 구현 시 즉시 실행 가능**:
   - VeriCacheSpeculativeCodec(05-25 C-1 기구현)의 `set_draft_codec(IndexMemEvictionCodec(budget_ratio=0.5))` 호출만으로 즉시 연동. 별도 구현 불필요.
   - IndexMem 드래프트 수락률 vs. SnapKV/TriAttention 드래프트 수락률 비교 실험 필수.

6. **이번 사이클 측정 지표**:
   - Compression Accuracy Delta: C-1 IndexMem ±0.3~0.8% 필수 검증 (RULER 스위트 + WikiText-2).
   - KV Cache Memory Reduction: C-1 −40~60% (budget_ratio=0.5 기준) + C-2 −65~80% (깊이 축 결합) 목표.
   - Non-Contiguous Cache Hit Rate: B-1 가중 히트율(soft hit 포함) 측정 + 기존 이진 히트율과 분리 보고.
   - Inference Throughput: Cross-2 (IndexMem + VeriCache) 드래프팅으로 처리량 +80~130% 목표.
   - 신규 지표: Soft Hit Rate (`n_soft_hits / total`) + Latent Memory Readout Score 분포 → `results/<exp-name>/metrics.json`에 추가 기록.

7. **구현 우선순위**: C-1 → Cross-2 → Cross-1 → B-1 → A-1 → C-2 → Cross-3 순서.

- 검토한 과거 리포트 수: 27개 (2026-04-28 ~ 2026-05-26 전체), 최근 6개(05-21 ~ 05-26) 직접 정독 + 이전 21개 인덱스 참조. 약 270개+ 아이디어 인덱싱.
