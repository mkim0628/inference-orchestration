### 아이디어 A-1: HexAGeTWorkflowHorizonAwareKVCapacityScheduler (HexAGenT 워크플로우 완료 지평선 인식 KV 용량 통합 스케줄러)
- **가설**: 에이전틱 LLM 워크로드를 처리할 때 기존 스케줄러들은 개별 요청 단위의 캐시 히트율 또는 큐 길이를 최적화하지만, 다단계 워크플로우에서 핵심 병목은 워크플로우 전체의 SLO 완료 시간(workflow completion horizon)이다. HexAGenT(2605.16637)의 핵심 원리 — (1) 워크플로우를 온라인-공개 DAG로 모델링해 독립 완료 시간 지평선을 실시간 추정, (2) SLO 위험 가중 우선순위(SLO-risk-weighted priority)로 ready 호출을 스케줄링, (3) KV 캐시 용량 제약과 이기종 GPU 전송 지연을 스케줄링 목적함수에 명시적 포함 — 을 `src/scheduler/`에 구현하면, 에이전틱 워크플로우의 SLO 달성률을 95% 기준 평균 20.1%, 99% 기준 33.0% 향상시키면서 KV 캐시 용량 낭비(조기 퇴거 후 재계산)를 구조적으로 줄일 수 있다. 과거 28개 사이클의 모든 에이전틱 A 기법(CacheTTL, PBKV, CONCUR, ThunderAgent, SideQuest, TokenDance, IndexMemTTLFallback)은 워크플로우 완료 시간 지평선을 목적함수로 사용하지 않았으며, KV 캐시 용량 제약과 이기종 GPU 전송 지연을 통합한 3-way 최적화도 없었다.
- **접근 방법**:
  1. `HexAGeTWorkflowScheduler` 클래스 (`src/scheduler/hexagent_workflow_scheduler.py`): `BaseScheduler` 상속
  2. **온라인-공개 DAG 모델링 (Online-Revealed DAG)**:
     - 에이전틱 세션 수신 시 초기 DAG 구조 추론: 요청 메타데이터(`task_type: [planning, tool_call, synthesis, refine]`, `dependency_ids`)로 초기 DAG 구성.
     - 런타임 DAG 갱신: 각 단계 완료 시 새로 공개되는 의존성을 DAG에 추가 (브랜칭, 합성 노드 등).
     - DAG 자료구조: `WorkflowDAG(nodes: Dict[task_id, TaskNode], edges: List[Tuple[task_id, task_id]])`. `TaskNode(task_id, task_type, kv_demand_estimate, gpu_type_preference, status: [pending, ready, running, done])`.
  3. **독립 완료 시간 지평선 추정 (Standalone Completion Horizon)**:
     - 각 ready 태스크에 대해 독립 완료 시간 지평선 계산:
       ```
       horizon(task) = current_time + T_prefill(task) + T_decode(task) + T_kv_transfer(task)
       ```
       - `T_prefill(task)`: 태스크의 프리필 지연 추정 (입력 길이 × GPU 처리량 역수).
       - `T_decode(task)`: 출력 길이 추정 × 디코딩 속도 역수. 온라인 EMA로 갱신.
       - `T_kv_transfer(task)`: 이기종 GPU 간 KV 전송 지연 추정 = `kv_size_bytes / rdma_bandwidth(src_gpu, tgt_gpu)`.
     - 이기종 GPU 전송 속도 테이블: `configs/gpu_rdma_bandwidth_table.yaml` — A100/H100/H200 간 RDMA 대역폭 사전 측정값.
  4. **SLO 위험 가중 우선순위 배정 (SLO-Risk-Weighted Priority)**:
     - SLO 위험 점수: `risk(task) = max(0, horizon(task) - slo_deadline(workflow)) / slo_deadline(workflow)`.
     - 우선순위: `priority(task) = base_priority + risk_weight × risk(task)`. `risk_weight`(기본 2.0) YAML 외부화.
     - 동시에 ready 상태인 태스크들을 `priority` 내림차순으로 정렬해 prefill/decode 배치에 배정.
     - 배치 주기: `schedule_cycle_ms`(기본 50ms) — 50ms마다 ready 태스크 재정렬 및 배치 결정.
  5. **KV 캐시 용량 인식 배치 결정 (KV-Capacity-Aware Batching)**:
     - 각 태스크의 KV 용량 수요 추정: `kv_demand(task) = input_tokens × kv_size_per_token × n_layers`.
     - 현재 GPU HBM 여유 확인: `kv_available = hbm_total - hbm_in_use`.
     - 배치 구성 시 KV 용량 제약 명시적 반영:
       ```python
       batch = []
       remaining_kv = kv_available
       for task in sorted(ready_tasks, key=priority, reverse=True):
           if kv_demand(task) <= remaining_kv:
               batch.append(task)
               remaining_kv -= kv_demand(task)
           else:
               # KV 용량 부족 → 해당 태스크를 위해 저우선순위 기존 KV 퇴거 시도
               if can_evict_to_fit(task, current_kv_pool):
                   evict_lowest_priority_kv(current_kv_pool)
                   batch.append(task)
                   remaining_kv -= kv_demand(task)
       ```
     - 퇴거 대상 결정: IndexMemTTLFallbackScheduler(05-27 A-1)와 연동 — TTL 만료 임박 KV 또는 잠재 기억 전환 가능 KV를 우선 퇴거.
  6. **이기종 GPU 전송 지연 반영 (Heterogeneous GPU Transfer Delay)**:
     - 태스크가 실행될 GPU 유형 선호도: `gpu_preference(task) = argmin_{g in available_gpus} [T_exec(task, g) + T_kv_transfer_to(g)]`.
     - A100/H100/H200 이기종 클러스터에서 KV 전송 비용이 낮은 GPU로 우선 배정.
     - `gpu_affinity_score(task, gpu) = -T_kv_transfer_to(gpu) - α × T_exec(task, gpu)` — 음수가 작을수록 선호. `α`(기본 0.5) YAML 외부화.
  7. **이전 A 기법과의 차별점**:
     - TokenDanceAllGatherScheduler(05-25 A-2): All-Gather 동기화 라운드 KV 집합적 공유 + Diff-Aware Storage (단일 라운드 패턴, 워크플로우 DAG 없음).
     - IndexMemTTLFallbackScheduler(05-27 A-1): TTL 만료 후 잠재 기억 소프트 전환 (세션 수명주기 관리, 워크플로우 DAG 없음).
     - PBKV(이미 보고): KV 예측 기반 에이전트 KV 관리 (예측, DAG 스케줄링 없음).
     - HexAGeTWorkflowScheduler: **워크플로우 완료 시간 지평선 실시간 추정 + SLO 위험 가중 우선순위 + KV 용량 제약 + 이기종 GPU 전송 지연을 통합한 온라인-공개 DAG 기반 3-way 에이전틱 스케줄러 — 이전 어느 A 기법에도 없었다.**
- **대상 환경**: 멀티 노드 (이기종 GPU 클러스터 환경 — A100/H100/H200 혼합)
- **멀티 노드 고려사항**: `gpu_rdma_bandwidth_table.yaml`에 노드 간 RDMA 대역폭 사전 측정값 등록 필수. 마스터 스케줄러가 클러스터 전체 GPU HBM 가용량을 gRPC heartbeat(100ms 주기)로 집계. DAG 상태는 마스터 스케줄러에 중앙 집중 관리 (세션-노드 어피니티 유지). 이기종 GPU 간 KV 전송은 RDMA 전용 채널로 모델 실행 통신과 분리.

### 아이디어 A-2: PegaFlowRustKVConnectorRDMACrossNodeSegmentRouter (PegaFlow Rust 외부 KV 커넥터 RDMA 크로스-노드 세그먼트 라우터)
- **가설**: PegaFlow(novitalabs/pegaflow)의 Rust 코어 GIL-free 외부 KV 캐시 서비스 — GPU 오프로딩(HBM→호스트 메모리)·SSD 캐싱·RDMA 크로스-노드 KV 공유를 단일 drop-in 커넥터로 제공 — 를 `src/scheduler/` 및 `src/cache/` 레이어와 연동하면, 현재 Python 기반 KV 오프로딩 경로의 GIL 병목을 완전히 제거하면서 호스트 메모리→SSD→RDMA 전 계층에 걸친 KV 저장·검색 처리량을 향상시킬 수 있다. ObjectCacheS3TierRouter(05-26 A-1)가 S3를 4번째 연구 프로토타입 계층으로 추가했다면, PegaFlow는 운영 환경에서 즉시 사용 가능한 Rust 드롭인 구현체이며 "GIL-free 핫 패스"라는 새로운 엔지니어링 설계 축을 도입한다. 과거 28개 사이클의 모든 A 기법에서 Python GIL을 완전히 배제한 외부 KV 캐시 프로세스를 연동한 기법이 없었다.
- **접근 방법**:
  1. `PegaFlowKVConnector` 클래스 (`src/cache/pegaflow_kv_connector.py`): `CacheStore` 인터페이스 구현
  2. `PegaFlowRDMACrossNodeRouter` 클래스 (`src/scheduler/pegaflow_rdma_router.py`): `BaseScheduler` 상속
  3. **PegaFlow 연동 설계 (GIL-free Rust 연동)**:
     - PegaFlow 프로세스와의 통신: Unix 소켓 + 공유 메모리 (zero-copy) — Python GIL 경유하지 않는 IPC 채널.
     - vLLM KV 커넥터 API 호환: PegaFlow가 vLLM KV 커넥터 인터페이스를 구현하므로, `src/cache/pegaflow_kv_connector.py`는 해당 인터페이스의 경량 Python 래퍼 역할.
     - 래퍼 설계:
       ```python
       class PegaFlowKVConnector(CacheStore):
           def __init__(self, pegaflow_socket_path: str):
               self.socket = UnixSocket(pegaflow_socket_path)  # GIL-free IPC
           def get(self, segment_id: bytes) -> Optional[Tensor]:
               return self.socket.send_recv(OpCode.GET, segment_id)  # zero-copy
           def put(self, segment_id: bytes, kv_tensor: Tensor) -> None:
               self.socket.send(OpCode.PUT, segment_id, kv_tensor)  # async
           def delete(self, segment_id: bytes) -> None:
               self.socket.send(OpCode.DELETE, segment_id)
       ```
     - 비동기 put: `put()` 호출은 Python 측에서 즉시 반환 (Rust 측 비동기 처리) → 메인 추론 루프 블로킹 없음.
  4. **RDMA 크로스-노드 세그먼트 라우팅 (RDMA Cross-Node Segment Routing)**:
     - PegaFlow의 RDMA 인터페이스를 활용해 원격 노드의 SSD/DRAM에서 직접 KV 세그먼트 조회:
       ```python
       class PegaFlowRDMACrossNodeRouter(BaseScheduler):
           def route_segment_request(self, segment_id: bytes, local_instance_id: str):
               # 로컬 PegaFlow 인스턴스에서 조회
               kv = self.local_connector.get(segment_id)
               if kv is not None:
                   return kv, "local"
               # 원격 노드 PegaFlow 인스턴스에서 RDMA 조회
               for remote_id in self.peer_instances:
                   if self.peer_registry.has_segment(remote_id, segment_id):
                       kv = self.remote_connectors[remote_id].get(segment_id)  # RDMA
                       return kv, "remote"
               return None, "miss"
       ```
     - `PeerRegistry`: 노드별 세그먼트 인덱스 스냅샷(Bloom Filter 기반, 거짓 양성 허용) — 원격 조회 전 불필요한 RDMA 연결 방지.
     - Bloom Filter 갱신 주기: `bloom_sync_interval_ms`(기본 500ms) YAML 외부화. gRPC로 피어 노드에 Bloom Filter 비트맵 전파.
  5. **KV 계층 관리 (GPU→호스트→SSD→RDMA 원격)**:
     - 계층 퇴거 정책: GPU HBM 압박 시 `PegaFlowKVConnector.put(segment_id, kv)` 호출 → PegaFlow가 호스트 메모리→SSD 계층화 자동 처리 (PegaFlow 내부 정책).
     - 계층 조회 순서: GPU HBM → `PegaFlowKVConnector.get()` (호스트/SSD 포함) → `PegaFlowRDMACrossNodeRouter.route_segment_request()` (원격 노드) → 재계산.
     - Prometheus 메트릭 연동: PegaFlow 내장 Prometheus 익스포터 → `src/metrics/memory.py`에서 `{hbm_usage, host_usage, ssd_usage, rdma_transfers}` 지표 수집.

     - KVDriveAttentionPipelineScheduler(05-19 A-1): 3-티어 I/O-컴퓨트 오버랩 파이프라인 (Python 기반, GIL 포함).
     - PegaFlowKVConnector + RDMACrossNodeRouter: **GIL-free Rust 외부 KV 프로세스 연동 + Bloom Filter 기반 원격 세그먼트 인덱스 + RDMA 크로스-노드 조회 — Python GIL 완전 배제와 운영 수준 RDMA 크로스-노드 공유가 이전 어느 A 기법에도 없었다.**
- **대상 환경**: 멀티 노드 (RDMA 가능 환경: InfiniBand 또는 RoCE 100Gbps 이상)

- **예상 효과**: KV 오프로딩 처리량 +30~60% (GIL 경합 제거 + Rust 비동기 I/O), 원격 KV 히트율 +10~20% (RDMA 크로스-노드 조회 활성화), Scheduling overhead TTFT +2% 이내 (비동기 put + Bloom Filter O(1) 조회), 호스트/SSD/RDMA 계층 투명 통합

### 아이디어 A-3: HexAGeTDAGKVDemandPrefetchIrminsulSegmentScheduler (HexAGenT DAG KV 수요 선행 예측 + Irminsul 비연속 세그먼트 선제 확보 스케줄러)
- **가설**: HexAGenT의 온라인-공개 DAG 스케줄러가 각 워크플로우 단계별 KV 수요를 미리 예측할 수 있다는 통찰을, Irminsul(2605.05696, B 기법)의 MLA 비연속 세그먼트 재사용과 결합하면 — DAG의 다음 ready 태스크가 필요로 할 비연속 KV 세그먼트를 현재 태스크 실행 중에 미리 선제 확보(prefetch)하는 "A→B 선제 캐시 워밍(proactive cache warming)" 파이프라인 — 을 구성할 수 있다. 현재 사이클에서 B 기법(Irminsul)은 세그먼트 히트 요청이 도착한 후에야 세그먼트를 검색하지만, DAG 스케줄러가 다음 단계의 세그먼트 수요를 미리 알면 HBM 또는 PegaFlow(A-2) 계층에 선제 로드해 TTFT를 대폭 줄일 수 있다. 과거 28개 사이클의 모든 A 기법 중 "에이전틱 워크플로우 DAG의 다음 단계 KV 세그먼트 수요를 선행 예측해 비연속 세그먼트를 선제 HBM으로 확보"하는 기법이 없었다.
- **접근 방법**:
  1. `HexAGeTDAGSegmentPrefetcher` 클래스 (`src/scheduler/hexagent_dag_segment_prefetcher.py`): `BaseScheduler` 상속
  2. **DAG 기반 다음 단계 세그먼트 수요 예측**:
     - `WorkflowDAG`(A-1 기구현)에서 현재 실행 중인 태스크의 후속 ready 태스크 목록 추출: `next_tasks = dag.successors(current_task)`.
     - 각 후속 태스크의 입력 컨텍스트 예측: 에이전틱 워크플로우 패턴에서 후속 태스크는 현재 태스크 출력 + 공유 시스템 프롬프트 + 이전 태스크 결과 조합.
     - 예측된 입력 컨텍스트에 대해 Irminsul CDC 청킹 + SHA256 세그먼트 ID 계산: `predicted_segments = irminsul_cdc_chunk(predicted_context)`.
     - 예측 신뢰도: `confidence(next_task) = 1 - dag_branch_factor(current_task)` — 브랜칭이 없으면 신뢰도 1.0, 브랜칭이 많으면 낮음.
  3. **선제 세그먼트 확보 (Proactive Segment Prefetch)**:
     - `confidence(next_task) > prefetch_confidence_threshold`(기본 0.7) 시 선제 확보 트리거.
     - 확보 경로 (우선순위 순):
       1. HBM에 이미 있으면 확보 완료.
       2. PegaFlow 호스트/SSD 계층에 있으면 `PegaFlowKVConnector.get(segment_id)` 비동기 호출 → HBM으로 선행 이동.
       3. 원격 노드 PegaFlow에 있으면 `PegaFlowRDMACrossNodeRouter.route_segment_request()` 비동기 호출.
       4. 없으면 prefetch 요청 취소 (재계산 경로).
     - 비동기 선제 확보: `asyncio.create_task(prefetch_segment(segment_id))` — 현재 태스크 실행을 블로킹하지 않음.
     - 선제 확보 HBM 예약 공간: `prefetch_hbm_budget_ratio`(기본 0.10) — HBM의 10%를 선제 확보 공간으로 예약. 초과 시 가장 낮은 신뢰도 선제 확보 세그먼트 제거.
  4. **이전 A 기법과의 차별점**:
     - AMPDLazySegmentFetchScheduler(05-18 A-1): pull-on-demand — 세그먼트 집합 확정 후 KV 페치 (사후 반응적).
     - PredictiveMultiTierKVCache(05-25 C-2): Bayesian Beta prior 기반 블록 재사용 예측 + 프리페치 (블록 유형 기반 통계적 예측, DAG 없음).
     - HexAGeTDAGSegmentPrefetcher: **에이전틱 워크플로우 DAG 구조를 활용한 다음 단계 비연속 세그먼트 선행 예측 + PegaFlow 계층 연동 선제 확보 — DAG 인식 선제 비연속 캐시 워밍이 이전 어느 A 기법에도 없었다.**
- **대상 환경**: 멀티 노드 (PegaFlow RDMA 인프라 + Irminsul 비연속 캐시)
- **멀티 노드 고려사항**: HexAGeTWorkflowScheduler(A-1)와 PegaFlowRDMACrossNodeRouter(A-2)를 전제로 동작. 선제 확보 세그먼트가 원격 노드에 있는 경우 A-2의 RDMA 경로로 전송. 선제 확보 타이밍: 현재 태스크 실행 초기(prefill 완료 직후) — 디코딩 중 선제 확보 완료 목표.
- **예상 효과**: TTFT −20~40% (선제 확보로 비연속 세그먼트 검색 지연 제거), 비연속 캐시 히트율 +10~20% (선제 확보로 HBM 세그먼트 가용성 향상), Scheduling overhead TTFT +3% 이내 (비동기 선제 확보 + 신뢰도 계산)
- **구현 난이도**: medium
- **우선순위**: 3

### 아이디어 B-1: PegaFlowRDMADistributedIrminsulNonContiguousSegmentReuse (PegaFlow RDMA 분산 인프라 기반 Irminsul MLA 비연속 세그먼트 원격 재사용 확장)
- **가설**: Irminsul(2605.05696)의 MLA c_KV/k_r 분리 + δ-회전 위치 수정이 로컬 HBM/DRAM 내 비연속 세그먼트를 수학적으로 보장하며 재사용하지만, 세그먼트가 다른 노드에 캐시된 경우 재계산을 수행한다는 한계가 있다. PegaFlow(novitalabs/pegaflow)의 RDMA 크로스-노드 KV 공유 인프라와 Irminsul의 CDC 콘텐츠 해시 세그먼트 인덱싱을 결합하면, "Irminsul이 세그먼트를 콘텐츠 해시로 인덱싱 → PegaFlow RDMA가 원격 노드에서 해당 세그먼트를 직접 전송 → Irminsul δ-회전으로 위치 수정 → 재사용"의 완전한 분산 비연속 세그먼트 재사용 스택이 가능하다. 과거 28개 사이클의 모든 B 기법(IrminsulMLASegmentCache 05-26, CDCContentHashUnifiedSegmentIDInterface 05-26, KVPacketAdapterCache 05-25, IndexMemSoftHitSegmentCache 05-27 등)은 로컬 계층(HBM/DRAM/SSD)에서만 비연속 세그먼트를 검색하며, RDMA를 통한 원격 노드 비연속 세그먼트 조회를 구현한 기법이 없었다.
- **접근 방법**:
  1. `PegaFlowIrminsulDistributedSegmentCache` 클래스 (`src/cache/pegaflow_irminsul_distributed_cache.py`): `CacheStore` 인터페이스 구현
  2. **분산 세그먼트 인덱스 설계**:
     - 로컬 인덱스: `IrminsulMLASegmentCache`(05-26 기구현)의 `{segment_id → IrminsulKVEntry}` 그대로 활용.
     - 원격 인덱스: `PegaFlowRDMACrossNodeRouter`(A-2)의 Bloom Filter 기반 피어 세그먼트 인덱스 활용.
     - 조회 순서:
       ```python
       def get(self, segment_id: bytes, target_position: int):
           # 1. 로컬 HBM/DRAM 조회 (Irminsul 기존 경로)
           entry = self.local_cache.get(segment_id)
           if entry:
               return self._apply_delta_rotation(entry, target_position), "local"
           # 2. PegaFlow 로컬 호스트/SSD 조회
           entry = self.pegaflow_local.get(segment_id)
           if entry:
               return self._apply_delta_rotation(entry, target_position), "pegaflow_local"
           # 3. PegaFlow RDMA 원격 노드 조회
           entry = self.pegaflow_rdma_router.route_segment_request(segment_id, self.node_id)
           if entry:
               return self._apply_delta_rotation(entry, target_position), "rdma_remote"
           return None, "miss"
       ```
  3. **δ-회전 위치 수정 원격 적용 (Delta Rotation for Remote KV)**:
     - 원격 노드에서 수신된 `IrminsulKVEntry(segment_id, c_kv_tensor, k_r_tensor, source_position)` 그대로 사용.
     - `source_position`은 원격 세그먼트의 원래 위치 → `δ = target_position - source_position` 계산.
     - `k_r_corrected = RoPE(k_r, δ)` 로컬 적용 (δ-회전은 수신 후 로컬 GPU에서 처리, 전송 데이터 추가 불필요).
     - c_KV는 위치-자유이므로 원격 수신 즉시 재사용 가능 — 전송 데이터 그대로 사용.
  4. **원격 세그먼트 전송 비용 추정 및 재사용 여부 결정**:
     - 전송 비용 추정: `rdma_transfer_latency(segment_size_bytes, rdma_bandwidth_gbps)`.
     - 재계산 비용 추정: `recompute_latency(segment_token_count, gpu_throughput)`.
     - 재사용 결정: RDMA 전송 비용 < 재계산 비용 × `rdma_reuse_discount`(기본 0.8) 이면 원격 재사용 선택.
     - `rdma_reuse_discount` YAML 외부화 — 네트워크 가변성 허용 마진.
  5. **분산 비연속 히트율 지표 (Distributed Non-Contiguous Hit Rate)**:
     - 기존 `{hard_hit, soft_hit, miss}` → 확장: `{local_hard_hit, pegaflow_local_hit, rdma_remote_hit, miss}` 4단계.
     - `src/metrics/hit_rate.py`에 `distributed_hit_rate = (local + pegaflow_local + rdma_remote) / total` 추가.
     - `results/<exp-name>/metrics.json`에 계층별 히트율 분리 기록.
  6. **이전 B 기법과의 차별점**:
     - IrminsulMLASegmentCache(05-26 B-1): 로컬 HBM/DRAM 내 δ-회전 재사용만 지원 (원격 없음).
     - CDCContentHashUnifiedSegmentIDInterface(05-26 B-2): S3 오브젝트 스토리지 계층까지 확장했으나 RDMA 크로스-노드 직접 전송 없음.
     - IndexMemSoftHitSegmentCache(05-27 B-1): 퇴거 후 잠재 기억 소프트 히트 경로 (원격 노드 조회 없음).
     - PegaFlowIrminsulDistributedSegmentCache: **PegaFlow RDMA로 원격 노드의 Irminsul MLA 비연속 세그먼트를 δ-회전 위치 수정과 함께 직접 재사용 — 원격 노드 비연속 세그먼트 조회가 이전 어느 B 기법에도 없었다.**
- **예상 효과**: 비연속 히트율 +15~30% (로컬 히트 외 원격 RDMA 히트 추가, 클러스터 세그먼트 풀 활용), TTFT ±3% (RDMA 전송 지연 vs. 재계산 대비 이득 상쇄), 분산 비연속 히트율 새 지표 도입
- **구현 난이도**: medium
- **우선순위**: 2

### 아이디어 C-1: VLLMFlexibleBlockSizeIndexMemLayerwiseBudgetCodec (vLLM XPU 유연 블록 크기 + IndexMem 레이어별 차등 KV 예산 압축 코덱)

  1. `FlexBlockLayerwiseBudgetCodec` 클래스 (`src/cache/flexblock_layerwise_budget_codec.py`): `CompressionCodec` 인터페이스 구현
  2. **레이어별 블록 크기 결정 (Layer-wise Block Size Assignment)**:
     - 레이어별 어텐션 엔트로피 측정: `attn_entropy[l] = -Σ_h Σ_i p_i^h log p_i^h` — 레이어 l의 헤드별 어텐션 가중치 분포 엔트로피 평균. (KVSculpt 05-23의 레이어 압축 난이도 측정 원칙 차용)
     - 블록 크기 할당 규칙:
       ```
       엔트로피 상위 25% 레이어: block_size = 16 (세밀한 토큰 단위 제어)
       엔트로피 중상위 25% 레이어: block_size = 32
       엔트로피 중하위 25% 레이어: block_size = 64
       엔트로피 하위 25% 레이어: block_size = 128 (큰 블록, 낮은 오버헤드)
       ```
     - 블록 크기는 오프라인 프로파일링으로 초기화 + 런타임 어텐션 엔트로피 EMA로 온라인 갱신.
     - `configs/flexblock_layer_config.yaml`: `{layer_id → block_size}` 매핑 저장.
  3. **레이어별 차등 KV 예산 (Layer-wise Budget Allocation)**:
     - IndexMem Learnable Indexer(05-27 C-1 기구현)의 레이어별 토큰 중요도 예측값 활용.
     - 레이어별 budget_ratio 결정:
       - 엔트로피 높은 레이어(중요, 세밀 블록): `budget_ratio_high = 0.7` — 70% 토큰 보존.
       - 엔트로피 낮은 레이어(덜 중요, 큰 블록): `budget_ratio_low = 0.3` — 30% 토큰 보존.
       - 선형 보간: `budget_ratio[l] = budget_ratio_low + (budget_ratio_high - budget_ratio_low) × normalized_entropy[l]`.
     - 전체 KV 예산 제약: `Σ_l (budget_ratio[l] × n_tokens) ≤ total_kv_budget` — 라그랑주 멀티플라이어로 글로벌 제약 만족.
  4. **vLLM XPU 커널 통합**:
     - vLLM KV 캐시 블록 관리자에 레이어별 블록 크기 설정: `vllm_block_manager.set_layer_block_size(layer_id, block_size)`.
     - 레이어별 블록 크기는 vLLM XPU 커널(2026-05-08)의 유연 블록 크기 API를 통해 설정.
     - `src/cache/flexblock_layerwise_budget_codec.py`에서 vLLM API 호출 래퍼 구현.
  5. **IndexMem 잠재 기억 통합**:
     - 작은 블록 레이어(엔트로피 높은): 퇴거된 블록은 IndexMem Latent Memory Module(05-27 C-1)로 잠재 상태 압축 보존 → 잔차 리드아웃으로 정보 복원.
     - 큰 블록 레이어(엔트로피 낮은): 퇴거 후 잠재 기억 선택적 적용 (낮은 중요도이므로 잠재 기억 오버헤드 절감 목적으로 생략 가능).
     - 잠재 기억 적용 여부: `use_latent_memory[l] = (attn_entropy[l] > entropy_threshold)` (기본: 상위 50% 레이어에만 적용).
  6. **accuracy-preserving 근거**:
     - (1) 엔트로피 높은 레이어에 작은 블록 크기 할당: 세밀한 토큰 수준 퇴거 제어로 중요 레이어의 정보 손실 최소화. KVSculpt(05-23)에서 레이어 간 압축 난이도가 100× 차이나므로 균일 예산보다 레이어별 차등 예산이 동일 메모리에서 정확도를 더 잘 보존.
     - (2) IndexMem 잠재 기억 보상(C-1 05-27 기법의 근거 계승): 엔트로피 높은 레이어의 퇴거된 블록 정보를 잠재 상태로 복원 → accuracy delta 감소.
     - (3) vLLM XPU 유연 블록 크기는 연산 결과를 변경하지 않고 메모리 배치만 변경 — 블록 크기 자체는 정확도에 영향 없음.
     - (4) 레이어별 budget_ratio의 글로벌 제약 만족: 동일 총 KV 예산 내에서 중요 레이어에 더 많은 예산 배분 → 기존 균일 budget_ratio 대비 accuracy delta ≤ 기존 방식 accuracy delta.
     - Fallback: accuracy delta > 1% 시 `budget_ratio_low` 증가(0.3 → 0.4) 후 재시도.
     검증: WikiText-2 perplexity ±1% + RULER-4K/16K + LongBench 8개 서브태스크 + 레이어별 블록 크기 균일 vs. 차등 3-way 비교 (균일 16 / 균일 64 / 차등 16~128) + budget_ratio 차등 vs. 균일 비교 + 레이어별 어텐션 엔트로피 분포 측정.
- **예상 효과**: 메모리 −40~60% (레이어별 차등 예산으로 균일 예산 대비 추가 절감 +5~10%), accuracy delta ±0.3~0.8% (IndexMem 잠재 기억 보상 포함, 중요 레이어 집중 보존)
- **구현 난이도**: medium
- **우선순위**: 3

### 아이디어 Cross-2: PegaFlowRDMAIndexMemLatentACPipeline (A+C) — PegaFlow RDMA 외부 KV + IndexMem 잠재 압축 KV 오프로딩 통합 파이프라인
- **조합 근거**: 트렌드 리포트(2026-05-28)에서 제시된 A+C 시너지를 구체화한다. IndexMemEvictionCodec(05-27 C-1)이 퇴거 토큰을 잠재 상태(4KB/요청)로 압축 보존한다면, 이 압축된 잠재 상태를 PegaFlow의 SSD 캐싱 또는 RDMA 크로스-노드 공유 계층에 오프로딩해 — "원 KV 대신 잠재 상태를 외부 KV 캐시로 관리"하는 A+C 통합 파이프라인 — 을 구성할 수 있다. 잠재 상태는 원 KV의 1/50~1/200 크기이므로 PegaFlow 외부 계층의 유효 용량이 50~200× 증가한다. 이전 사이클의 Cross-3(05-27, ObjectCache S3 + IndexMem 7단계 파이프라인)이 원 KV를 S3에 오프로딩하는 방식이었다면, 이 아이디어는 잠재 상태를 PegaFlow에 오프로딩해 전송 데이터량을 1/50~1/200로 줄이는 새로운 결합이다.
- **구체 설계**:
  1. `PegaFlowLatentStateOffloadPipeline` 모듈 (`src/engine/pegaflow_latent_offload_pipeline.py`)
  2. **잠재 상태 PegaFlow 오프로딩 설계**:
     - IndexMemEvictionCodec(05-27 C-1)의 퇴거 후 처리에 훅 추가:
       ```python
       def encode_evicted_with_offload(evicted_kv_batch, pegaflow_connector):
           latent_state = IndexMemLatentMemoryModule.encode(evicted_kv_batch)
           # PegaFlow에 잠재 상태 오프로딩 (4KB/요청, 비동기)
           segment_id = sha256(evicted_kv_batch.token_ids)
           pegaflow_connector.put(f"latent:{segment_id}", latent_state)
           return latent_state  # 로컬 LatentStatePool에도 캐시
       ```
     - `"latent:{segment_id}"` 키 네임스페이스: 원 KV 오프로딩과 분리.
  3. **잠재 상태 원격 조회 + 잔차 리드아웃**:
     - 세그먼트 miss 시: 로컬 잠재 상태 풀 → PegaFlow 로컬 → PegaFlow RDMA 원격 → 재계산 순으로 잠재 상태 조회.
     - 원격 잠재 상태 수신 시 잔차 리드아웃 적용 (IndexMem C-1 방식).
     - 데이터 전송량: 잠재 상태 4KB vs. 원 KV 수십 MB → RDMA 전송 부담 1/50~1/200.
  4. **이전 Cross 기법과의 차별점**:
     - IndexMemLatentEvictionIrminsulMLAObjectCacheFullPipeline(05-27 Cross-3): 원 KV를 S3/ObjectCache에 오프로딩 + IndexMem 잠재 기억 레이어 추가 (전송 대상: 원 KV).
     - PegaFlowLatentStateOffloadPipeline: **잠재 상태만 PegaFlow에 오프로딩 — 전송 데이터를 1/50~1/200으로 줄이는 새로운 결합. 잠재 상태 원격 조회 + 잔차 리드아웃 경로가 이전 Cross 기법에 없었다.**
- **예상 복합 효과**: 처리량 +25~50% (잠재 상태 오프로딩으로 HBM 해방 + 원격 잠재 상태 잔차 복원 처리량 향상), 메모리 −80~95% (잠재 상태 1/50~1/200 크기 + PegaFlow SSD/RDMA 전 계층 오프로딩), accuracy delta ±0.3~0.8% (IndexMem 잔차 리드아웃 보상)
- **구현 난이도**: medium
- **우선순위**: 2
